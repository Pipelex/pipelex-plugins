# Validation hooks

The plugin runs a validation hook against `.mthds` files after every edit, on all three targets — and all three are now **CLI-free**: nothing shells out to `plxt` or `mthds-agent`. The pipeline is identical everywhere (lint → format → validate, same Stage-3 decision model); only the wiring and the block/deny vocabulary differ per harness.

## The wasm+API pipeline (all targets)

Two layers ship in each target's `hooks/`:

- **A thin wrapper script** (`check-mthds.sh` on Claude, `check-mthds-codex.sh` on Codex, `check-mthds-vibe.sh` on Vibe) — fast `.mthds` pre-filter on the stdin JSON (on Codex, a patch header line naming a `.mthds` file and a mention of the patch program, since its matcher also admits every shell command), `command -v node` guard (no Node → silent pass), then `exec node check.mjs --platform=<claude|codex|vibe>` with stdin passed through. It is the fail-open guard and the per-platform seam; it contains no validation logic. The Claude wrapper additionally promotes plugin user-config credentials (`CLAUDE_PLUGIN_OPTION_API_KEY` / `CLAUDE_PLUGIN_OPTION_BASE_URL`, exported by Claude Code from the manifest's `userConfig`) to `PIPELEX_API_KEY` / `PIPELEX_BASE_URL` when non-empty — a set option wins over inherited session env; an empty one leaves the session env untouched.
- **`check.mjs`** — one vendored, dependency-free ~5 MB ESM bundle shared by all targets (built in the `js/` directory of `pipelex-sdk`, provenance header at the top; the `--platform` flag selects the input parser and the stdout dialect) holding the whole pipeline:
  1. **Local lint** via `@pipelex/tools-wasm` — the same Rust engine as `plxt lint` / `/v1/lint`, compiled to WASM and inlined into the bundle. Fully offline, no credentials. Any diagnostic **blocks** with line/col spans.
  2. **Local format** (same engine) — writes the canonical formatting back in place, exactly like `plxt fmt` did. A format failure only warns on stderr.
  3. **API validate** — `POST /v1/validate` through `@pipelex/sdk` with `allow_signatures: true`, sending the method's tree as the MTHDS protocol's `files` map, the tree a run of the method would send: the edited file's directory listed by the `mthds` package's lister under the standard's membership rule, rooted at the nearest `METHODS.toml` at or above that directory, else at the directory itself. The tree holds every file the rule keeps under the tree root, up to the caps below, and not only the method's bundles and the files its steps read, such as the template a `PipeDocGen` step names in `template_file`, each at its tree path. The rule leaves out names starting with a dot, `node_modules`, `__pycache__`, a run's inputs file (`inputs.json` or `inputs.toml`), what a `.gitignore` file inside the tree keeps out and what the manifest's `[package] exclude` lists. It reads no other ignore file: a `.gitignore` above the tree root, such as a repository's root one when the tree is rooted in a subdirectory, which it is whenever no `METHODS.toml` lies above the edited file, keeps nothing out, and neither does `.git/info/exclude` or git's global excludes file. **Before anything is sent, the hook reads every file of the tree once and screens it for secrets**, by the workshop's secret-guard rule. A file named like a secret file (a `.key` file that is no Keynote deck, a certificate or key store, a PuTTY key, a KeePass database, an SSH private key under its default name, a `credentials` file, an OAuth client-secret export) or holding a well-known key format in its text (a PEM private key block, such as the one a cloud service-account export carries, or the prefixed keys of the cloud providers, the code hosts and the model providers, a Pipelex key among them) stays home, and the method is validated without it: the verdict carries a note naming each file kept home and why, never what it holds, as context after a pass or inside a block's reason, and a step that reads such a file, as its template or its Python module, reports it missing until the secret is moved out. When the file is a bundle or the `METHODS.toml` manifest, which every validation reads, nothing is sent at all, not even the version handshake, and a non-blocking note says so in place of a verdict. The screen is a tripwire for those well-known shapes and never a promise that a tree holds no secret: a password in prose, a scanned contract or a file the repository's root `.gitignore` lists goes through it, since the hook still reads no `.gitignore` above the tree root. So a method that fills a template validates as it would load from disk and its template is checked by the dry run, and a step whose template file the tree does not hold makes the verdict say so, which blocks until the file is written. The client asks the API's version handshake (`GET /v1/version`) first, then sends the tree inline when it is small or the API keeps no blob store, and by hash otherwise, uploading the files the API lacks; the handshake, the blob route, the uploads and the validation together run under one ten-second deadline. The hook caps the tree at 100 files, 5 MiB for one file or 12 MiB in all, each checked while the tree is listed and before any file is read, and past a cap the stage reads as unavailable rather than risking a false block on an under-supplied method. The verdict is the **200 body discriminated on `is_valid`**, never the transport:
     - `is_valid: true` → **pass**; unimplemented `PipeSignature` placeholders emit a non-blocking `additionalContext` nudge listing `pending_signatures`.
     - `is_valid: false` → **block**. The hook always asks for the server's Markdown (`render: ["markdown"]`) and forwards the `rendered_markdown` it gets verbatim as the reason. A runner that speaks the MTHDS problem document carries the verdict's faults as problem items in `errors[]`, each with its own `code`, `detail`, `params` and `location`, and sometimes a `suggested_fix`, in place of the `validation_errors[]` of the older shape, and its Markdown renders those items, so they reach the agent whichever shape the server speaks.
     - `is_valid: false` with no `rendered_markdown`, from a server that ignores the `render` request → **block** all the same, with a reason the bundle builds from the verdict's `message` and its problem items: one line for each item of `errors[]`, naming its `code`, its `detail` and where it happened, its pipe, its file and the other members of its `location` as the `mthds` package's `formatLocation` words them, with the item's `suggested_fix` on a line of its own beneath it when it carries one, worded by `formatSuggestedFix`. An entry lacking a `code` or a `detail` is skipped, and a `location` or `suggested_fix` the bundle cannot read is left out of its item rather than failing the block. The bundle no longer reads `validation_errors[]`, so a server of the older shape that also ignores `render` gets a reason holding the verdict's message alone.

A validation that produced no verdict is not `is_valid: false`. A runner speaking the problem document answers it with a non-2xx problem document, such as a dry run meeting a model the deployment does not serve, and the hook reads that as no verdict, so the validate stage is skipped (the failure posture below).

Note the tree scope means a broken **sibling** `.mthds` file fails the verdict too — same as the plxt-era `-L` behavior; the block reason names the offending file through each problem item's `location.file`, which the server's Markdown renders and the reason the bundle builds without it repeats (a server of the older shape names it by each fault's `source` in its Markdown).

Per-platform input handling inside the bundle: Claude reads one file from `tool_input.file_path`; **Codex** parses the `apply_patch` envelope in `tool_input.command`, whether the call is the patch tool's or a shell command's (`*** Update File: / Add File: / Move to:` headers — one patch can touch several `.mthds` files; each runs the full pipeline and the outcomes merge, any block wins; a relative path is resolved against the payload's `cwd`, and in a patch run through the shell against the directory the script had moved to, see "Patches run through the shell" below); **Vibe** reads the `post_tool` payload (`tool_status: "success"` gate, path from `tool_output.file`/`.path` or `tool_input.file_path`/`.path`, resolved against `cwd`). Output dialects: Claude/Codex `{"decision":"block",…}` + `hookSpecificOutput.additionalContext`; Vibe `{"decision":"deny",…}` + `{"decision":"allow","hook_specific_output":{"additional_context":…}}`.

### Failure posture (fail-open)

| Condition | Behavior |
|---|---|
| Not a `.mthds` edit / unparseable stdin | silent pass (wrapper pre-filter) |
| Claude and Vibe: a `.mthds` file written or changed through the shell (a heredoc, `sed`, a script) | no hook runs, since the matcher admits only the file tools; the MTHDS language reference tells the agent to write and edit with those tools for that reason |
| Codex: a shell command that patches no `.mthds` file, or only writes patch text without running the patch program | silent pass (wrapper pre-filter, no Node started) |
| Codex: a patch Codex applies itself from a shell `apply_patch` heredoc | no hook runs: Codex emits no `PostToolUse` for it |
| Codex: a shell patch naming a `.mthds` file by a relative path the bundle cannot place or confirm | that file is not checked; a non-blocking note names it and asks for its absolute path or the patch tool |
| No `node` on PATH | silent pass (wrapper) |
| `check.mjs` missing beside the wrapper | silent pass + stderr note (broken install) |
| WASM engine fails to load | silent pass (whole hook unavailable) |
| No `PIPELEX_API_KEY` | lint/format verdicts apply; **validate stage skipped silently** |
| A method tree holding a symbolic link or a special file, or a directory the lister cannot read | same: the standard's lister refuses the tree, so nothing is sent |
| An edited file the membership rule keeps out of its own tree, such as one in a hidden directory or one a `.gitignore` keeps out | same: no tree holds it to validate |
| A tree past the hook's caps: 100 files, 5 MiB for one file or 12 MiB in all | same, decided while the tree is listed, before any file is read |
| A file of the tree that fails to upload | same: the validation is not sent |
| A file of the tree named like a secret file or holding a well-known key format | that file stays home and the method is validated without it; the verdict carries a note naming the file and why, never what it holds |
| A bundle or the `METHODS.toml` manifest that looks like a secret | nothing is sent; a non-blocking note names the tree and the file in place of a verdict |
| API unreachable, the ten-second deadline running out over the handshake, the blob route, the uploads and the validation, or any non-2xx, a problem document answering a validation that produced no verdict included | same — local verdicts apply, validate skipped |

A machine consumer branches on the structured verdict, never on transport — an invalid bundle is a produced verdict on a 200; a non-2xx means *no verdict*, which for a write gate degrades to the local stages.

### Environment

- `PIPELEX_API_KEY` — required **for the validate stage only**; lint/format work offline with no key. Without it the hook is a local lint+format gate.
- `PIPELEX_BASE_URL` — optional; defaults to the hosted `https://api.pipelex.com`. Point it at a local `pipelex-api` (`http://localhost:8081`) to validate against your own runner.

On Claude Code, both variables can come from the **plugin configuration** instead of the shell: the manifest's `userConfig` prompts for them when the plugin is enabled (the key is stored in the OS keychain), and the wrapper promotes the delivered `CLAUDE_PLUGIN_OPTION_*` values as described above. This is the supported channel for GUI launches (Claude Desktop), which carry no shell environment at all — see `docs/decisions.md` ("Claude credentials move to plugin userConfig").

**Privacy note:** with a key set, the method's tree leaves the machine on every validate call: every file the MTHDS membership rule keeps under the tree root, up to the hook's caps, and not only the `.mthds` files and their templates — something the plxt-era hook never did. Names starting with a dot, such as a `.env` file, and a run's inputs file never travel, and neither does a file the hook's secret screen finds: one named like a key or credentials file, or holding a private key block or a provider's key, such as a `key.pem` holding a key or a cloud `service-account.json`, stays home and is named in a note on the verdict. The screen finds only those well-known shapes, so it is a tripwire rather than a promise. A `.gitignore` is honoured only inside the method tree, together with the manifest's `exclude`: a repository-root `.gitignore` above the tree keeps nothing home, so a file it lists that the screen does not recognize, a `secrets.yaml` of plain values among them, is sent. To keep a file home for certain, list it in a `.gitignore` inside the method tree or in `METHODS.toml`'s `[package] exclude`, keep it out of the directory the tree is rooted at, or unset `PIPELEX_API_KEY`, which keeps everything local. The skills write no test document into the tree at all: `/pipelex-inputs` uploads a user's file from where it lies and writes its address into `inputs.json`, and `/pipelex-synthetic-inputs` renders into a temporary directory. A bundle an earlier release prepared may still hold an `inputs/` folder of copies and an `inputs.prepared.json`, which nothing migrates: `/pipelex-run` marks both in the way above, `*` in that folder's `.gitignore` and `/inputs.prepared.json` in the bundle directory's, before its first call, so such a bundle sends them only until it is next run.

**Schema pinning:** the WASM engine embeds the MTHDS schema frozen at `@pipelex/tools-wasm` build time, so plugin releases are the local schema update cadence; the server-side validate is the authoritative verdict when the two skew.

**Where the embedded schema comes from.** It crosses four repositories, each step a build or a publish. `pipelex` generates it as `derived/mthds_schema.json`. `vscode-pipelex` copies it into `crates/taplo-common/schemas/mthds_schema.json`, which the engine compiles in with `include_str!`, and publishes the engine to npm as `@pipelex/tools-wasm`. The `js/` directory of `pipelex-sdk` pins that version as a devDependency and bundles it into `check.mjs` with `npm run build:hook`. This repository then vendors the bundle with `make vendor-hook`. So a language form reaches the hook only after a `@pipelex/tools-wasm` release and a pin bump in `pipelex-sdk`, and a corpus copy synced before then turns the corpus sweep below red on every entry using the form. An engine built from an unreleased `vscode-pipelex` can be tried locally through `PIPELEX_TOOLS_WASM_PATH`, but `make check` refuses to ship the bundle it produces ("Re-vendoring check.mjs" below).

### Re-vendoring check.mjs

`check.mjs` is a **static hook asset** (`templates/hooks/assets/check.mjs` — copied verbatim by the build, never rendered through Jinja). It is MIT code inside an ELv2 plugin, so a second static asset, `templates/hooks/assets/THIRD-PARTY-NOTICES.md`, ships beside it in every target with the MIT notice and the list of packages it inlines. When the hook source in `pipelex-sdk`'s `js/` changes (or its `@pipelex/tools-wasm` npm dependency is bumped):

```bash
make vendor-hook   # npm run build:hook in ../pipelex-sdk/js + copy into templates/hooks/assets/
make build         # propagate to pipelex/hooks/check.mjs
make check         # freshness + packaging gates, and the provenance guard
make check-hook-fresh  # the release gate: npm's latest engine, and a rebuild changes nothing
```

`make vendor-hook` builds in `SDK_JS_DIR`, which defaults to `../pipelex-sdk/js`, the `js/` directory of the sibling `pipelex-sdk` checkout, and takes an override for a checkout elsewhere. The wasm engine comes from the published `@pipelex/tools-wasm` npm package. Setting `PIPELEX_TOOLS_WASM_PATH` to a `vscode-pipelex/js/tools-wasm` checkout (with a `RELEASE=true make tools-wasm` build) bundles an unreleased engine instead, which is for trying one locally: `make check` refuses to let such a bundle ship. The provenance header (SDK version + commit, tools-wasm version + origin) identifies any vendored copy, and two guards read it. A third guard reads the bundle's code instead.

- **`make check` refuses a bundle no published source can reproduce.** `scripts/check.py` reads the template copy's provenance line and fails when its tools-wasm origin is anything but `(npm)`, which is what `PIPELEX_TOOLS_WASM_PATH` produces, or when its SDK commit is not a commit, which is the `unknown` a build outside a git checkout writes. It also fails when the third line is not a provenance line at all. It needs neither the sibling checkout nor the network, so `Checks` runs it on every pull request, and it reads only the template copy because the freshness check already holds every target's copy to it byte for byte.
- **`make check-hook-fresh` refuses a bundle that is behind its sources, and the release skill runs it.** It answers two questions, both on every run. First, is the vendored tools-wasm version the one `npm view @pipelex/tools-wasm version` reports as latest? Second, would re-vendoring change the bundle? It runs `npm ci` and `npm run build:hook` in `SDK_JS_DIR` and compares everything below the three-line banner with the vendored bundle, byte for byte; the banner is left out because its SDK commit moves with every commit to `pipelex-sdk`, including those that never touch the hook. It refuses to answer unless that checkout is on `dev`, clean everywhere and not only in `js/`, and level with `origin/dev` after a fetch, since a rebuild of anything else says nothing about what re-vendoring would produce; `npm ci` rewrites that checkout's `node_modules` and the build writes its `dist-hooks/`, both ignored by git, exactly as `make vendor-hook` does. The rebuild runs with `PIPELEX_TOOLS_WASM_PATH` removed from its environment, so it always bundles the npm engine `npm ci` installed, even in a shell that is trying a local one. A stale bundle fails with the cure: `make vendor-hook` then `make build` on a branch into `dev`, preceded by a pin bump in `pipelex-sdk`'s `js/` when it still pins an older engine than npm's latest. It is a release gate rather than a CI check because CI has no sibling checkout, and it exits 0 when the bundle is current, 1 when it is behind and 2 when it could not answer.

- **`make check` refuses a bundle that inlines a package its notices file does not name.** esbuild writes a comment naming each module it inlines from a dependency, `// node_modules/mthds/dist/…`, and `scripts/check.py` reads the package names from those comments and fails when one of them is not in backticks in `THIRD-PARTY-NOTICES.md`. A re-vendor that brings in a new dependency therefore fails until that dependency's licence and copyright are added to the notice.

The second question relies on the build being deterministic: two consecutive builds of one commit were measured byte-identical when the gate was written, in the `pipelex-sdk-js` repository the hook was built in then, and again after the hook's source moved into `pipelex-sdk`. If that ever stops holding, the gate reports a stale bundle that a re-vendor does not cure, and the build is what to look at.

## Per-platform wiring

| Platform | Config | Script | Event / matcher |
|---|---|---|---|
| Claude Code | `hooks/hooks.json` (bundled, auto-loaded; 15 s timeout) | `hooks/check-mthds.sh` → `hooks/check.mjs` | `PostToolUse` over `Write\|Edit`, gated to `*.mthds` |
| Codex | `hooks/codex-hooks.json`, referenced from the manifest `hooks` field (15 s timeout) | `hooks/check-mthds-codex.sh` → `hooks/check.mjs --platform=codex` | `PostToolUse` over `apply_patch` and `Bash` (`^(apply_patch\|Bash)$`) |
| Mistral Vibe | `hooks/vibe-hooks.toml`, the entry the user appends to `~/.vibe/hooks.toml` (15 s timeout) | `hooks/check-mthds-vibe.sh` → `hooks/check.mjs --platform=vibe` | `post_tool` over `edit\|write_file` |

**Every hook command quotes the plugin root.** Each harness hands a hook's `command` to a shell: Claude Code runs a shell-form command with `sh -c`, Codex replaces the plugin root placeholder in the command text and runs the result with the user's shell, and Vibe runs its command with `/bin/sh -c`. A plugin root whose path holds a space therefore splits an unquoted command into two words, the shell exits 127, and every edit passes unchecked. So the Claude command is `"${CLAUDE_PLUGIN_ROOT}"/hooks/check-mthds.sh`, the Codex command is `"${PLUGIN_ROOT}"/hooks/check-mthds-codex.sh`, and the Vibe command, which reaches the script through the plugin's link in Vibe's home, is `"${VIBE_HOME:-$HOME/.vibe}/plugins/pipelex/hooks/check-mthds-vibe.sh"`, so a home directory holding a space stays one word too. Claude Code also offers an exec form, a command with an `args` array that runs with no shell at all; the hooks keep the quoted shell form, for the reason recorded in [decisions.md](decisions.md) ("Hook commands quote the plugin root"). `claude plugin validate` warns about an unquoted `${CLAUDE_PLUGIN_ROOT}` from Claude Code 2.1.281, and `tests/unit/test_hook_commands.py` runs every rendered command from a root whose name holds a space.

Codex's hook engine replaces `${PLUGIN_ROOT}` (and `${CLAUDE_PLUGIN_ROOT}`, for compatibility) with the installed plugin root by a plain text replacement before its shell runs the command, and runs the hook from the session's directory, the payload's `cwd`; Codex 0.144+ also provides `${PLUGIN_DATA}` / `${CLAUDE_PLUGIN_DATA}` (per-plugin data dir), unused here. A Codex session may run network-sandboxed; the validate stage then reads as unavailable (its in-bundle 10 s ceiling keeps a blocked call from hanging the hook) while lint/format still gate locally.

## The Codex hook — loading and trust

Verified against **Codex 0.142.5**, re-verified — including **in live sessions** — against **Codex 0.144.4** (block with lint diagnostics relayed to the model, format-in-place on pass, silence on non-`.mthds` patches). The hook engine graduated out of "under development" across 0.139 → 0.142: the `hooks` feature is `Stage::Stable` and **enabled by default**, so the plugin-bundled hook is discovered from the manifest and loads on its own — there is no `[features] hooks = true` line to set (`codex_hooks` is an honored deprecated alias, still present in 0.144.4; set `hooks = false` only to disable). Note that `plugin_hooks` is **not** an alias of `hooks` — it was an independent opt-in for plugin-bundled hooks, removed in Codex 0.134 and ignored since (formally `Stage::Removed` in 0.144); a stale `plugin_hooks = false` line is a harmless leftover on supported Codex versions but should be removed. The one manual step is trust:

- **Trust** the plugin hook when Codex asks, which is at the start of the first session after the install (Codex persists trusted hashes under `[hooks.state]`). The session that installed the plugin through `/plugins` asks for no trust and does not run the hook, while its skills and MCP tools already work: observed on Codex 0.156.1, where a `.mthds` file written in that session stayed exactly as `apply_patch` wrote it, and the next session's edit of it, after the trust, came out formatted. For automation, `--dangerously-bypass-hook-trust` bypasses the prompt. The trusted hash covers the hook's matcher and command, so an update that changes either is trusted again once.

`PostToolUse` officially fires for `apply_patch` edits and MCP tool calls, so the `.mthds`-on-edit hook fires on every edit made with the patch tool; a patch run through the shell is the exception, described in the next section. The standardized block protocol (`{"decision":"block","reason":…}` or exit 2 + stderr) maps cleanly onto the stage-3 domain-based block/context decision model above. See [decisions.md](decisions.md) for the full finding, including the plugin **cache model** on 0.144.x: installed plugins run from a cache copy, so after `make build` propagate local edits with `make codex-refresh` (an idempotent `codex plugin add`).

Dev-machine note: if the CLI-era `mthds@mthds-plugins` plugin is also installed, both hooks fire on the same `.mthds` edit and Codex concatenates the block reasons — expected coexistence, not a bug.

## Patches run through the shell (Codex)

A Codex model can write a file in three ways, and the hook sees two of them. This was verified against **Codex 0.153.4** in a live headless session, with a hook logging every `PostToolUse` payload, and read in the codex-rs source.

- **The patch tool.** A call to `apply_patch` reaches the hook as `apply_patch`, with the patch in `tool_input.command`.
- **A shell patch Codex applies itself.** Sent through the `exec_command` tool, a script that is exactly `apply_patch <<'EOF' … EOF`, or exactly `cd <dir> && apply_patch <<'EOF' … EOF`, is intercepted and applied in process, and Codex emits no `PostToolUse` event for it at all: the intercepted branch of `core/src/tools/handlers/unified_exec/exec_command.rs` returns an output that carries no hook command, so no payload is built. No matcher can reach such a patch, and a `.mthds` file written that way stays unchecked until a later edit touches it.
- **Any other shell patch.** A script in any other form, such as `apply_patch <<'EOF' … EOF && echo done` or `cd sub; apply_patch <<'EOF' … EOF`, runs the `apply_patch` executable Codex puts on the `PATH`, and reaches the hook as `Bash`, with the whole script in `tool_input.command`. The matcher admits `Bash` for this case, and `check.mjs` reads the patch headers from the script as it reads them from the patch tool's call, then finds the files the patch wrote as the next paragraphs describe.

Every other shell command reaches the wrapper too, and ends in its pre-filter: unless a patch header line names a `.mthds` file and the payload mentions the patch program (`apply_patch`, `applypatch` or `apply-patch`), the wrapper exits before starting Node. The second condition drops a command that only writes patch text, such as a heredoc into a notes file or a commit message quoting a patch: it applied nothing, and the bundle would otherwise read the header as a patch it could not place and send a note asking the model to act on a file nobody touched. A script that writes such text and also runs the patch program still gets that note, which only the bundle can tell apart (L-260925-5ca416). That costs one shell start per command, measured at about 14 ms when the matcher was widened, well under the 300 ms after which Codex's interface shows a running hook, so no status message appears for it.

**A relative path in a shell patch is read where the script had moved, and checked only when its file holds what the patch added.** The patch tool's paths are relative to the session's directory, the payload's `cwd`, so `check.mjs` checks and formats each file there. A shell patch's paths are relative to wherever the script stood when `apply_patch` ran, so for a `Bash` call the bundle reads the script as a POSIX shell script, follows its `cd` commands from the payload's `cwd`, and places each patch at the directory of the `apply_patch` command that reads it; a directory it cannot follow, such as `cd "$DIR"` or `pushd`, leaves the path unplaced rather than read from the session's directory. That reading can still be wrong, because a script run in the `workdir` the model passed to `exec_command` looks exactly like one run in the session's directory: the payload carries the script but never the `workdir`. So before checking a file that a shell patch names by a relative path, the bundle confirms that the file holds the lines the patch added, in order, and skips it otherwise, rather than blocking on a same-named file the patch never touched or rewriting that file through the format stage. This narrows the wrong-file case without closing it: a same-named file that already holds every added line passes, which an update adding one common line, such as `output = "Text"`, makes likely, and that file is then checked and reformatted in the patch's place while the edited file goes unchecked. It takes a script run in a `workdir` other than the session's directory, or a `cd` the reading misfollows, and a file of the same name where the reading lands; tightening the confirmation belongs to the bundle (L-260925-94f96c). A relative path the bundle skips, because it could not place it, because its file lacks the added lines, or because no file exists where it resolves, is named in a non-blocking note that asks the model to name the file by its absolute path or to edit it with the patch tool, so that the hook's silence is never read as a clean check. An absolute path is checked wherever the patch ran, unless its file lacks the lines the patch added, which shows the script never wrote it. The wrapper takes no part in this and runs `check.mjs` from the directory Codex started it in. The full reading, with the shell constructs it follows, how quoting enters the comparison and its known limits, is [`js/docs/hook-bundle.md`](https://github.com/Pipelex/pipelex-sdk/blob/main/js/docs/hook-bundle.md) in `pipelex-sdk`, where the bundle is built. `tests/unit/test_hook_commands.py` pins the behaviour with crafted payloads: a patch after `cd sub` blocks on `sub/broken.mthds` and leaves a valid but unformatted `broken.mthds` in the session's directory byte for byte unchanged, and a script with no `cd` whose same-named file in the session's directory lacks the added lines gets the note and no block.

## The Vibe hook — loading and payload

Verified against **Mistral Vibe 2.21.0**, the release that shipped stable hooks, and read again in the source of **Mistral Vibe 2.26.1**, whose default unified harness builds the payload anew (`mistralai_vibe_local_harness/vibe/_foreign_hooks.py`) while its legacy harness, behind `--legacy-harness`, keeps 2.21.0's (`vibe/core/hooks/`). On 2.21.0 the payload contract was checked in the installed source, and payloads serialized by Vibe's own `PostToolInvocation.model_dump_json()` were run end to end through the shipped `check-mthds-vibe.sh`: deny on lint errors, format write-back in place, silent pass on `tool_status: "failure"` and on valid files, relative paths resolved against the payload `cwd`. On 2.26.1 the entry was loaded by Vibe's own `load_hooks_file`, selected by both harnesses' matchers, and run by both executors, the legacy `HookExecutor` and the unified `_run_command`, from a Vibe home and a project whose paths hold a space: a legacy `edit` payload and a unified `file_system.search_replace` one naming the file under `tool_input.path` were both denied on a lint error. The payload a live unified session sends is the proving campaign's to check. Findings, all matching what the bundle expects:

- **Only the user's and a trusted project's hooks files run.** Both harnesses load `~/.vibe/hooks.toml`, or `$VIBE_HOME/hooks.toml`, and a trusted project's `.vibe/hooks.toml` (`vibe/core/hooks/config.py`, `load_hooks_from_fs`). Vibe 2.26.1 parses a plugin's `ai.mistral.vibe/hooks.toml` and lists its hooks, but neither harness runs them: the unified harness withholds a plugin's hook bindings, which have no execution adapter yet (`vibe/app_server/_plugins.py`, `core_plugins`). So the hook ships as the entry the user appends ([install.md](install.md#the-hook)), and a later release moves it into the plugin once Vibe runs plugin hooks.
- **The command runs through the shell, from the session's directory, with Vibe's environment.** Both harnesses spawn it with `create_subprocess_shell` in the project directory, so a relative command would resolve against the project, not against the hooks file. The entry instead reaches the wrapper through `${VIBE_HOME:-$HOME/.vibe}/plugins/pipelex`, the link the install makes, in double quotes inside a single-quoted TOML string, since the shell would split a path holding a space.
- `hook_event_name` is `"post_tool"`, and a successful call sends `tool_status: "success"`. The legacy harness's `ToolStatus` is `"success" | "failure" | "cancelled"`, and the unified harness sends `"success"` or `"failure"`; the extractor's success gate skips everything but a success.
- **The matcher selects both file tools on either harness.** The legacy harness names a tool by its snake-cased class, exactly `edit` and `write_file`. The unified harness names it by its group, `file_system.search_replace` and `file_system.write_file`, but tests `match` against the leaf and the name the model calls as well (`_hook_matcher.py`, `candidate_names`), so `re:^(edit|write_file)$` selects both.
- **The file is found in either payload.** On the legacy harness `tool_output` is the tool result's `model_dump()`: `edit` yields `{file, message, old_string, new_string}` with `file` the resolved absolute path, and `write_file` yields `{file_path, bytes_written, content}`, while `tool_input.file_path` is present for both. On the unified harness `tool_input` is translated back to the legacy argument names, `path` becoming `file_path` for `write_file`, and `tool_output` is the tool's structured content. The extractor tries `tool_output.file`, `tool_output.path`, `tool_input.file_path` and `tool_input.path` in turn, keeps the first that ends in `.mthds`, resolves a relative one against the payload's `cwd`, and never reads `tool_name`.
- Response handling is the same on both harnesses (`hooks/_post_tool.py`, and `_interpret_post_tool_stdout` in the unified one): a deny **replaces** the tool output the model sees with our `reason`, plus `additional_context` if present, and an allow with `additional_context` **appends** it — matching the dialect the bundle emits.

## Checks

`scripts/check.py` enforces the Vibe hook artifacts (`check_vibe_target_artifacts`): a Mistral Vibe target must emit `hooks/vibe-hooks.toml` (one `post_tool` hook, matching `edit|write_file`, whose command reaches `check-mthds-vibe.sh` through the plugin's link in Vibe's home) and an executable `hooks/check-mthds-vibe.sh`, and carry no `ai.mistral.vibe/hooks.toml`, which Vibe would list and never run, no Claude or Codex plugin manifest, and no Claude or Codex hook artifacts (`check.mjs` is a shared asset, allowed everywhere). The renderer marks all three wrapper scripts executable, and the freshness check fails if the exec bit is lost. Static hook assets (`check.mjs`) are declared per platform in `gen_skill_docs.py` (`STATIC_HOOK_ASSETS_BY_PLATFORM`); a missing asset fails the build, a stale vendored copy in a target fails the freshness check, and a template copy built from an unreleased engine or outside a git checkout fails the provenance guard ("Re-vendoring check.mjs" above).

**The unit tests run every hook command the way its harness does.** `tests/unit/test_hook_commands.py` renders each target's hook configuration from the real templates under a directory whose name holds a space and runs every shell-form command through `sh -c`, with the plugin root both expanded by the shell and substituted into the text, and the Vibe entry's command through a Vibe home that links to that root, once with `VIBE_HOME` set to a directory holding a space and once without it from such a home directory, and fails when a command does not start its script. It also runs the rendered Codex wrapper, with the vendored `check.mjs`, on the payloads its matcher admits: a patch run through the shell and reported as `Bash` blocks on a lint error and passes a valid method silently when it names the file by absolute path, the patch tool's call still blocks and formats a relative path in the session's directory, a shell command that patches no `.mthds` file, or only writes patch text, ends without starting Node, a shell patch's relative path is checked in the directory the script moved to, leaving a same-named file in the session's directory untouched, and a relative path the bundle cannot confirm gets a non-blocking note instead of a check. The Codex half needs `node`, and like the corpus sweep below it fails rather than skips under `CI` when there is none; the shared fixture is in `tests/unit/conftest.py`.

**The unit tests read what the validate stage sends.** `tests/unit/test_hook_method_tree.py` runs `templates/hooks/assets/check.mjs` as a Claude `PostToolUse` `Write` against a stand-in API on a loopback port, given a placeholder key it never checks, and reads the requests it receives. The stand-in answers the version handshake as a runner keeping no blob store, so the tree travels inline and every file sent is in the body. A bundle whose `PipeDocGen` step names a template file sends its tree as `files`, the `.mthds` file, the template and the `method-graph.html` page beside them each at its tree path, and neither of the retired `mthds_contents` and `resources`; an edit in a package's subdirectory sends the whole package, rooted at its `METHODS.toml`, and leaves home a run's inputs file, a hidden `.env` and a file the `.gitignore` keeps out; two steps naming one path in two directories each send their own file; a manifest holding a private key block sends nothing, not even the handshake, and leaves a non-blocking note naming it; key and credentials files beside a bundle stay home under a note that names them and quotes nothing, while a plain file the repository's root `.gitignore` lists still travels; the documents copied into `inputs/` beside a bundle and its `inputs.prepared.json` travel when unmarked, whatever the repository's root `.gitignore` says, and stay home once `inputs/` holds a `.gitignore` of `*` and the bundle directory's `.gitignore` holds `/inputs.prepared.json`; and a tree holding a symbolic link sends nothing and passes silently, although the stand-in would refuse anything sent. The fake secrets are assembled at run time from repeated characters, as the SDK's own suites build theirs, so no literal in the repository looks like a key. Like the sweep below, it needs `node` and fails rather than skips under `CI` without one.

**The unit tests read the verdicts the validate stage gets back.** `tests/unit/test_hook_validate_verdict.py` runs the same bundle against the same stand-in, answering each shape a runner speaking the problem document sends: an invalid verdict whose faults are problem items blocks with the server's Markdown verbatim, and without that Markdown still blocks with the verdict's message and names each item by its code and its sentence, while a validation that produced no verdict, answered as a non-2xx problem document, passes silently. A re-vendor onto a hook source that does not read `errors[]`, such as that of the `@pipelex/sdk` 0.50.0 release and every earlier one, fails the test that reads the items. The stand-in and the run of the hook against it are in `tests/unit/stub_api.py`.

**The unit tests sweep the hook over the MTHDS Test Corpus.** `tests/unit/test_hook_corpus.py` runs `templates/hooks/assets/check.mjs`, the copy every target carries byte for byte, as a Claude `PostToolUse` `Write` of every `.mthds` file of every entry in the vendored corpus at `tests/data/mthds-corpus/`. Each entry is copied to a temporary directory first, because the format stage writes back in place, and `PIPELEX_*` and `CLAUDE_PLUGIN_OPTION_*` are removed from the hook's environment, so only the offline lint and format stages run. The rule is the corpus contract's: an entry whose `error.*` tag has `fails_at = "schema"` in the vendored `vocabulary.toml` must block with a schema diagnostic, and every other entry must pass with nothing on stdout or stderr. The sweep never branches on `validity` and keeps no list of entries of its own, so an entry the sync adds is swept with no change here, and three more tests keep it from passing vacuously: the copy holds entries, every entry holds a `.mthds` file, and the corpus holds entries on both sides of the rule. This is the check that fails when the vendored bundle's schema is behind the standard, which the bundle before 0.8.0 does on `feature_intent_hints_reading_circle`, but only once the corpus carries the feature and the copy has been refreshed. The copy is refreshed by the workspace's corpus sync when a `pipelex` release changes the corpus, and never edited here. Without `node` the sweep skips on a developer machine and fails under `CI`, where `tests.yml` installs Node 22, the bundle's build target. The Codex and Vibe flags change only how the payload is read and how the verdict is spelled, which the bundle's own tests in `pipelex-sdk`'s `js/` cover.

**The unit tests pin the hook's verdict on a `PipeFunc`'s `function_name`.** The corpus has no `PipeFunc` entry and leaves the step to a consumer's own fixtures, so the sweep cannot see the rule that a `function_name` is an import path from the root of the method's tree. `tests/unit/test_hook_pipe_func.py` runs the same bundle, offline in the same way, on a method whose one `PipeFunc` names a bare function (`capitalize`) or holds an empty segment (`funcs..capitalize`, `funcs.`, `.funcs`), each of which must block with a schema diagnostic on `function_name`, and on import paths (`text_utils.capitalize`, `funcs.text_utils.capitalize`), which must pass with nothing said. A re-vendor onto an engine that dropped the rule, as the bundles built on `@pipelex/tools-wasm` before 0.6.0 lack it, or that began refusing an import path, fails it. Like the sweep, it needs `node` and fails rather than skips under `CI` without one.
