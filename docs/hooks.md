# Validation hooks

The plugin runs a validation hook against `.mthds` files after every edit, on all three targets — and all three are now **CLI-free**: nothing shells out to `plxt` or `mthds-agent`. The pipeline is identical everywhere (lint → format → validate, same Stage-3 decision model); only the wiring and the block/deny vocabulary differ per harness.

## The wasm+API pipeline (all targets)

Two layers ship in each target's `hooks/`:

- **A thin wrapper script** (`check-mthds.sh` on Claude, `check-mthds-codex.sh` on Codex, `check-mthds-vibe.sh` on Vibe) — fast `.mthds` pre-filter on the stdin JSON (on Codex, a patch header line naming a `.mthds` file, since its matcher also admits every shell command), `command -v node` guard (no Node → silent pass), then `exec node check.mjs --platform=<claude|codex|vibe>` with stdin passed through (on Codex, from the wrapper's own directory for any call but the patch tool's, see "Patches run through the shell" below). It is the fail-open guard and the per-platform seam; it contains no validation logic. The Claude wrapper additionally promotes plugin user-config credentials (`CLAUDE_PLUGIN_OPTION_API_KEY` / `CLAUDE_PLUGIN_OPTION_BASE_URL`, exported by Claude Code from the manifest's `userConfig`) to `PIPELEX_API_KEY` / `PIPELEX_BASE_URL` when non-empty — a set option wins over inherited session env; an empty one leaves the session env untouched.
- **`check.mjs`** — one vendored, dependency-free ~4 MB ESM bundle shared by all targets (built in `pipelex-sdk-js`, provenance header at the top; the `--platform` flag selects the input parser and the stdout dialect) holding the whole pipeline:
  1. **Local lint** via `@pipelex/tools-wasm` — the same Rust engine as `plxt lint` / `/v1/lint`, compiled to WASM and inlined into the bundle. Fully offline, no credentials. Any diagnostic **blocks** with line/col spans.
  2. **Local format** (same engine) — writes the canonical formatting back in place, exactly like `plxt fmt` did. A format failure only warns on stderr.
  3. **API validate** — `POST /v1/validate` through `@pipelex/sdk` with `allow_signatures: true`, sending the `.mthds` files gathered recursively under the edited file's parent directory (the old `-L "$PARENT_DIR/"` scope; dot-dirs and the runtime's excluded dirs are skipped; capped at 50 files / 2 MiB — on overflow the stage reads as unavailable rather than risking a false block on an under-supplied bundle). The verdict is the **200 body discriminated on `is_valid`**, never the transport:
     - `is_valid: true` → **pass**; unimplemented `PipeSignature` placeholders emit a non-blocking `additionalContext` nudge listing `pending_signatures`.
     - `is_valid: false` → **block**, forwarding the server-rendered `rendered_markdown` verbatim as the reason (falling back to a client-side rendering of `validation_errors[]` with locators).

Note the bundle scope means a broken **sibling** `.mthds` file fails the verdict too — same as the plxt-era `-L` behavior; the block reason names the offending file via its `source` attribution.

Per-platform input handling inside the bundle: Claude reads one file from `tool_input.file_path`; **Codex** parses the `apply_patch` envelope in `tool_input.command`, whether the call is the patch tool's or a shell command's (`*** Update File: / Add File: / Move to:` headers — one patch can touch several `.mthds` files; each runs the full pipeline and the outcomes merge, any block wins; a relative path is resolved against the hook's working directory, which the wrapper sets so that only the patch tool's relative paths are read, see "Patches run through the shell" below); **Vibe** reads the `post_tool` payload (`tool_status: "success"` gate, path from `tool_output.file`/`.path` or `tool_input.file_path`/`.path`, resolved against `cwd`). Output dialects: Claude/Codex `{"decision":"block",…}` + `hookSpecificOutput.additionalContext`; Vibe `{"decision":"deny",…}` + `{"decision":"allow","hook_specific_output":{"additional_context":…}}`.

### Failure posture (fail-open)

| Condition | Behavior |
|---|---|
| Not a `.mthds` edit / unparseable stdin | silent pass (wrapper pre-filter) |
| Codex: a shell command that patches no `.mthds` file | silent pass (wrapper pre-filter, no Node started) |
| Codex: a patch Codex applies itself from a shell `apply_patch` heredoc | no hook runs: Codex emits no `PostToolUse` for it |
| Codex: a shell patch naming a `.mthds` file by a relative path | silent pass: that file is not checked, since the directory the patch ran in is unknown |
| No `node` on PATH | silent pass (wrapper) |
| `check.mjs` missing beside the wrapper | silent pass + stderr note (broken install) |
| WASM engine fails to load | silent pass (whole hook unavailable) |
| No `PIPELEX_API_KEY` | lint/format verdicts apply; **validate stage skipped silently** |
| API unreachable / timeout (10 s) / any non-2xx | same — local verdicts apply, validate skipped |

A machine consumer branches on the structured verdict, never on transport — an invalid bundle is a produced verdict on a 200; a non-2xx means *no verdict*, which for a write gate degrades to the local stages.

### Environment

- `PIPELEX_API_KEY` — required **for the validate stage only**; lint/format work offline with no key. Without it the hook is a local lint+format gate.
- `PIPELEX_BASE_URL` — optional; defaults to the hosted `https://api.pipelex.com`. Point it at a local `pipelex-api` (`http://localhost:8081`) to validate against your own runner.

On Claude Code, both variables can come from the **plugin configuration** instead of the shell: the manifest's `userConfig` prompts for them when the plugin is enabled (the key is stored in the OS keychain), and the wrapper promotes the delivered `CLAUDE_PLUGIN_OPTION_*` values as described above. This is the supported channel for GUI launches (Claude Desktop), which carry no shell environment at all — see `docs/decisions.md` ("Claude credentials move to plugin userConfig").

**Privacy note:** with a key set, the gathered bundle contents leave the machine on every validate call — something the plxt-era hook never did. Unset `PIPELEX_API_KEY` to keep everything local.

**Schema pinning:** the WASM engine embeds the MTHDS schema frozen at `@pipelex/tools-wasm` build time, so plugin releases are the local schema update cadence; the server-side validate is the authoritative verdict when the two skew.

### Re-vendoring check.mjs

`check.mjs` is a **static hook asset** (`templates/hooks/assets/check.mjs` — copied verbatim by the build, never rendered through Jinja). When the hook source in `pipelex-sdk-js` changes (or its `@pipelex/tools-wasm` npm dependency is bumped):

```bash
make vendor-hook   # npm run build:hook in pipelex-sdk-js + copy into templates/hooks/assets/
make build         # propagate to pipelex/hooks/check.mjs
make check         # freshness + packaging gates, and the provenance guard
make check-hook-fresh  # the release gate: npm's latest engine, and a rebuild changes nothing
```

`make vendor-hook` accepts a `SDK_JS_DIR=` override for a non-sibling checkout. The wasm engine comes from the published `@pipelex/tools-wasm` npm package. Setting `PIPELEX_TOOLS_WASM_PATH` to a `vscode-pipelex/js/tools-wasm` checkout (with a `RELEASE=true make tools-wasm` build) bundles an unreleased engine instead, which is for trying one locally: `make check` refuses to let such a bundle ship. The provenance header (SDK version + commit, tools-wasm version + origin) identifies any vendored copy, and two guards read it.

- **`make check` refuses a bundle no published source can reproduce.** `scripts/check.py` reads the template copy's provenance line and fails when its tools-wasm origin is anything but `(npm)`, which is what `PIPELEX_TOOLS_WASM_PATH` produces, or when its SDK commit is not a commit, which is the `unknown` a build outside a git checkout writes. It also fails when the third line is not a provenance line at all. It needs neither the sibling checkout nor the network, so `Checks` runs it on every pull request, and it reads only the template copy because the freshness check already holds every target's copy to it byte for byte.
- **`make check-hook-fresh` refuses a bundle that is behind its sources, and the release skill runs it.** It answers two questions, both on every run. First, is the vendored tools-wasm version the one `npm view @pipelex/tools-wasm version` reports as latest? Second, would re-vendoring change the bundle? It runs `npm ci` and `npm run build:hook` in `SDK_JS_DIR` and compares everything below the three-line banner with the vendored bundle, byte for byte; the banner is left out because its SDK commit moves with every commit to `pipelex-sdk-js`, including those that never touch the hook. It refuses to answer unless that checkout is on `dev`, clean, and level with `origin/dev` after a fetch, since a rebuild of anything else says nothing about what re-vendoring would produce; `npm ci` rewrites that checkout's `node_modules` and the build writes its `dist-hooks/`, both ignored by git, exactly as `make vendor-hook` does. The rebuild runs with `PIPELEX_TOOLS_WASM_PATH` removed from its environment, so it always bundles the npm engine `npm ci` installed, even in a shell that is trying a local one. A stale bundle fails with the cure: `make vendor-hook` then `make build` on a branch into `dev`, preceded by a pin bump in `pipelex-sdk-js` when that repo still pins an older engine than npm's latest. It is a release gate rather than a CI check because CI has no sibling checkout, and it exits 0 when the bundle is current, 1 when it is behind and 2 when it could not answer.

The second question relies on the build being deterministic: two consecutive builds of one `pipelex-sdk-js` commit were measured byte-identical when the gate was written. If that ever stops holding, the gate reports a stale bundle that a re-vendor does not cure, and the build is what to look at.

## Per-platform wiring

| Platform | Config | Script | Event / matcher |
|---|---|---|---|
| Claude Code | `hooks/hooks.json` (bundled, auto-loaded; 15 s timeout) | `hooks/check-mthds.sh` → `hooks/check.mjs` | `PostToolUse` over `Write\|Edit`, gated to `*.mthds` |
| Codex | `hooks/codex-hooks.json`, referenced from the manifest `hooks` field (15 s timeout) | `hooks/check-mthds-codex.sh` → `hooks/check.mjs --platform=codex` | `PostToolUse` over `apply_patch` and `Bash` (`^(apply_patch\|Bash)$`) |
| Mistral Vibe | `hooks/vibe-hooks.toml` (15 s timeout) | `hooks/check-mthds-vibe.sh` → `hooks/check.mjs --platform=vibe` | `post_tool` over `edit\|write_file` |

**Every hook command quotes the plugin root.** Each harness hands a hook's `command` to a shell: Claude Code runs a shell-form command with `sh -c`, Codex replaces the plugin root placeholder in the command text and runs the result with the user's shell, and Vibe runs its command with `/bin/sh -c`. A plugin root whose path holds a space therefore splits an unquoted command into two words, the shell exits 127, and every edit passes unchecked. So the Claude command is `"${CLAUDE_PLUGIN_ROOT}"/hooks/check-mthds.sh`, the Codex command is `"${PLUGIN_ROOT}"/hooks/check-mthds-codex.sh`, and the Vibe command, which names the script by the absolute path the user writes in, keeps that path in double quotes too. Claude Code also offers an exec form, a command with an `args` array that runs with no shell at all; the hooks keep the quoted shell form, for the reason recorded in [decisions.md](decisions.md) ("Hook commands quote the plugin root"). `claude plugin validate` warns about an unquoted `${CLAUDE_PLUGIN_ROOT}` from Claude Code 2.1.281, and `tests/unit/test_hook_commands.py` runs every rendered command from a root whose name holds a space.

Codex's hook engine replaces `${PLUGIN_ROOT}` (and `${CLAUDE_PLUGIN_ROOT}`, for compatibility) with the installed plugin root by a plain text replacement before its shell runs the command, and runs the hook from the session's directory, the payload's `cwd`; Codex 0.144+ also provides `${PLUGIN_DATA}` / `${CLAUDE_PLUGIN_DATA}` (per-plugin data dir), unused here. A Codex session may run network-sandboxed; the validate stage then reads as unavailable (its in-bundle 10 s ceiling keeps a blocked call from hanging the hook) while lint/format still gate locally.

## The Codex hook — loading and trust

Verified against **Codex 0.142.5**, re-verified — including **in live sessions** — against **Codex 0.144.4** (block with lint diagnostics relayed to the model, format-in-place on pass, silence on non-`.mthds` patches). The hook engine graduated out of "under development" across 0.139 → 0.142: the `hooks` feature is `Stage::Stable` and **enabled by default**, so the plugin-bundled hook is discovered from the manifest and loads on its own — there is no `[features] hooks = true` line to set (`codex_hooks` is an honored deprecated alias, still present in 0.144.4; set `hooks = false` only to disable). Note that `plugin_hooks` is **not** an alias of `hooks` — it was an independent opt-in for plugin-bundled hooks, removed in Codex 0.134 and ignored since (formally `Stage::Removed` in 0.144); a stale `plugin_hooks = false` line is a harmless leftover on supported Codex versions but should be removed. The one manual step is trust:

- On first run, **trust** the plugin hook (Codex persists trusted hashes under `[hooks.state]`). For automation, `--dangerously-bypass-hook-trust` bypasses the prompt. The trusted hash covers the hook's matcher and command, so an update that changes either is trusted again once.

`PostToolUse` officially fires for `apply_patch` edits and MCP tool calls, so the `.mthds`-on-edit hook fires on every edit made with the patch tool; a patch run through the shell is the exception, described in the next section. The standardized block protocol (`{"decision":"block","reason":…}` or exit 2 + stderr) maps cleanly onto the stage-3 domain-based block/context decision model above. See [decisions.md](decisions.md) for the full finding, including the plugin **cache model** on 0.144.x: installed plugins run from a cache copy, so after `make build` propagate local edits with `make codex-refresh` (an idempotent `codex plugin add`).

Dev-machine note: if the CLI-era `mthds@mthds-plugins` plugin is also installed, both hooks fire on the same `.mthds` edit and Codex concatenates the block reasons — expected coexistence, not a bug.

## Patches run through the shell (Codex)

A Codex model can write a file in three ways, and the hook sees two of them. This was verified against **Codex 0.153.4** in a live headless session, with a hook logging every `PostToolUse` payload, and read in the codex-rs source.

- **The patch tool.** A call to `apply_patch` reaches the hook as `apply_patch`, with the patch in `tool_input.command`.
- **A shell patch Codex applies itself.** Sent through the `exec_command` tool, a script that is exactly `apply_patch <<'EOF' … EOF`, or exactly `cd <dir> && apply_patch <<'EOF' … EOF`, is intercepted and applied in process, and Codex emits no `PostToolUse` event for it at all: the intercepted branch of `core/src/tools/handlers/unified_exec/exec_command.rs` returns an output that carries no hook command, so no payload is built. No matcher can reach such a patch, and a `.mthds` file written that way stays unchecked until a later edit touches it.
- **Any other shell patch.** A script in any other form, such as `apply_patch <<'EOF' … EOF && echo done` or `cd sub; apply_patch <<'EOF' … EOF`, runs the `apply_patch` executable Codex puts on the `PATH`, and reaches the hook as `Bash`, with the whole script in `tool_input.command`. The matcher admits `Bash` for this case, and `check.mjs` reads the patch headers from the script exactly as it reads them from the patch tool's call, checking each file the patch names by absolute path.

Every other shell command reaches the wrapper too, and ends in its pre-filter: unless a patch header line names a `.mthds` file, the wrapper exits before starting Node. That costs one shell start per command, measured at about 14 ms when the matcher was widened, well under the 300 ms after which Codex's interface shows a running hook, so no status message appears for it.

**A shell patch is checked only where it names a file by absolute path.** `check.mjs` resolves each relative path against its own working directory, which Codex sets to the session's directory, the payload's `cwd`. The patch tool's paths are relative to that same directory, so for its call the wrapper keeps it, and a relative path there is checked and formatted. A shell patch may have run somewhere else, in the `workdir` the model passed to `exec_command` or after a `cd` in the script, and the payload carries the script but never the `workdir`, so the wrapper cannot tell where a relative path points. Read from the session's directory, such a path could name a file the patch never touched, which the hook would then block on, or rewrite in place through its format stage. So for any call other than the patch tool's, the wrapper runs `check.mjs` from its own `hooks/` directory, which ships no `.mthds` file: a relative path names no file there and goes unchecked, silently, the hook failing open, while an absolute path is checked wherever the patch ran. The wrapper reads the tool name from the payload's own `tool_name` field; quotes inside the command are escaped in the JSON, so a script cannot pass for the patch tool. Its own directory needs no creation and no cleanup, where a temporary one would be left behind whenever Codex kills a hook that outlives its timeout. **This run is a stopgap.** A bundle change in `pipelex-sdk-js` (L-260924-bdb054) resolves a Codex patch's relative path against the payload's `cwd` rather than the bundle's own working directory, follows a `cd` in a shell patch, checks a relative shell target only when the file holds the patch's added lines in order, and adds a non-blocking note otherwise; once that bundle is vendored here, the wrapper's change of directory has no effect, and removing it is L-260924-dd7bf2. `tests/unit/test_hook_commands.py` pins both readings with crafted payloads, including a same-named file in the session's directory that stays byte-identical.

## The Vibe hook — payload verification

Verified against **Mistral Vibe 2.21.0** (the release that shipped stable hooks): the payload contract was checked in the installed package source (`vibe/core/hooks/models.py`, `agent_loop/_loop.py`, builtin `edit.py` / `write_file.py`), and payloads serialized by Vibe's own `PostToolInvocation.model_dump_json()` were run end-to-end through the shipped `check-mthds-vibe.sh` — deny on lint errors, format write-back in place, silent pass on `tool_status: "failure"` and on valid files, relative paths resolved against the payload `cwd`. Findings, all matching what the bundle expects:

- `hook_event_name` serializes as `"post_tool"`; a successful call sends `tool_status: "success"` (`ToolStatus` is `"success" | "failure" | "cancelled"` — a cancelled tool sends `"cancelled"`, which the extractor's success gate correctly skips).
- Tool names are the snake_cased class names, so file edits are exactly `edit` and `write_file` — the `re:^(edit|write_file)$` matcher is right.
- `tool_output` is the tool result's `model_dump()`: `edit` yields `{file, message, old_string, new_string}` with `file` the **resolved absolute path**; `write_file` yields `{file_path, bytes_written, content}` — `file_path` is *not* in the extractor's `tool_output` fallback chain, so writes resolve through `tool_input.file_path` (present and identical for both tools). Both routes land on the same file.
- Hook commands run via `create_subprocess_shell` inheriting **Vibe's process cwd** (the project dir) — a relative `command` in `hooks.toml` resolves against the project, *not* the `hooks.toml` location. Hence the install page ([install.md](install.md#mistral-vibe)) instructs wiring the **absolute** script path when copying the generated `vibe-hooks.toml` into `~/.vibe/hooks.toml`, in double quotes inside a single-quoted TOML string, since the shell would split a path holding a space.
- Response handling (`hooks/_post_tool.py`): a deny **replaces** `tool_output_text` with our `reason` (plus `additional_context` if present); an allow with `additional_context` **appends** it — matching the dialect the bundle emits.

## Checks

`scripts/check.py` enforces the Vibe hook artifacts (`check_vibe_target_artifacts`): a Mistral Vibe target must emit `hooks/vibe-hooks.toml` (`post_tool`, matching `edit|write_file`, calling `check-mthds-vibe.sh`) and an executable `hooks/check-mthds-vibe.sh`, carry no Claude/Codex plugin manifest, and contain no Claude/Codex hook artifacts (`check.mjs` is a shared asset, allowed everywhere). The renderer marks all three wrapper scripts executable, and the freshness check fails if the exec bit is lost. Static hook assets (`check.mjs`) are declared per platform in `gen_skill_docs.py` (`STATIC_HOOK_ASSETS_BY_PLATFORM`); a missing asset fails the build, a stale vendored copy in a target fails the freshness check, and a template copy built from an unreleased engine or outside a git checkout fails the provenance guard ("Re-vendoring check.mjs" above).

**The unit tests run every hook command the way its harness does.** `tests/unit/test_hook_commands.py` renders each target's hook configuration from the real templates under a directory whose name holds a space and runs every shell-form command through `sh -c`, with the plugin root both expanded by the shell and substituted into the text, and fails when a command does not start its script. It also runs the rendered Codex wrapper, with the vendored `check.mjs`, on the payloads its matcher admits: a patch run through the shell and reported as `Bash` blocks on a lint error and passes a valid method silently when it names the file by absolute path, the patch tool's call still blocks and formats a relative path in the session's directory, a shell command that patches no `.mthds` file ends without starting Node, and a shell patch's relative path goes unchecked, leaving a same-named file in the session's directory untouched. The Codex half needs `node`, and like the corpus sweep below it fails rather than skips under `CI` when there is none; the shared fixture is in `tests/unit/conftest.py`.

**The unit tests sweep the hook over the MTHDS Test Corpus.** `tests/unit/test_hook_corpus.py` runs `templates/hooks/assets/check.mjs`, the copy every target carries byte for byte, as a Claude `PostToolUse` `Write` of every `.mthds` file of every entry in the vendored corpus at `tests/data/mthds-corpus/`. Each entry is copied to a temporary directory first, because the format stage writes back in place, and `PIPELEX_*` and `CLAUDE_PLUGIN_OPTION_*` are removed from the hook's environment, so only the offline lint and format stages run. The rule is the corpus contract's: an entry whose `error.*` tag has `fails_at = "schema"` in the vendored `vocabulary.toml` must block with a schema diagnostic, and every other entry must pass with nothing on stdout or stderr. The sweep never branches on `validity` and keeps no list of entries of its own, so an entry the sync adds is swept with no change here, and three more tests keep it from passing vacuously: the copy holds entries, every entry holds a `.mthds` file, and the corpus holds entries on both sides of the rule. This is the check that fails when the vendored bundle's schema is behind the standard, which the bundle before 0.8.0 does on `feature_intent_hints_reading_circle`, but only once the corpus carries the feature and the copy has been refreshed. The copy is refreshed by the workspace's corpus sync when a `pipelex` release changes the corpus, and never edited here. Without `node` the sweep skips on a developer machine and fails under `CI`, where `tests.yml` installs Node 22, the bundle's build target. The Codex and Vibe flags change only how the payload is read and how the verdict is spelled, which the bundle's own tests in `pipelex-sdk-js` cover.
