# The skills and the Pipelex tools

What each skill of the Pipelex plugin does, what it needs, and the tools it calls. The README lists the skills in one line each; this page carries the detail. The procedure itself is each skill's `SKILL.md`, under `templates/skills/`, and the reasons behind it are in [decisions.md](decisions.md).

## Build a method

**`pipelex-design`** designs a method contract-first and writes it as `.mthds` files. A method whose whole graph is understood and shallow is written directly as a coherent, runnable bundle; deep, uncertain, staged or resumable work goes through signature-driven refinement, validated at each step. A structural or contract change to an existing method, such as a new step or a new input, comes back here too, and the skill re-enters the affected region directly or through signatures according to its complexity. When the method is ready, the skill presents its flow, giving first the path of the flowchart page the Pipelex tools write beside the bundle.

**`pipelex-edit`** makes the edits that keep a method's contract: a prompt, a model reference, a mechanical rename. It proves each one with a validation before and after, and sends a structural or contract change to `/pipelex-design`.

**`pipelex-organize`** regroups a layout that construction left behind, or any awkward one, into coherent module files, or into a single file when the method is simple, and proves the result equivalent through the validation verdict. It follows `/pipelex-design` on its own only when the finished layout needs it, and it never changes what the method does.

Those three work on files, and each also takes a saved method's catalog id (`mt_…`): it finds the directory already linked to that method, or hands the pull to `/pipelex-catalog` first. When the directory is linked to a saved method, each ends by saving the change it has made as that method's draft, which changes nothing the method's callers run, and says that `mt_…@draft` runs it. None of them publishes: a draft becomes what callers run only when you ask `/pipelex-catalog` to publish it. A save the Pipelex tools refuse, because somebody saved the draft since the directory last synced or because the directory holds a published version pulled to read, is left to `/pipelex-catalog`, which asks you.

**`pipelex-explain`** explains a method in plain language: its contract, its flow and every pipe in it, saying first whether the method is complete or a scaffold with a backlog. It reads a bundle directory or a single file, fetches and explains a saved method's source the same way, since it belongs to the organization asking, saying whether it explained the draft or a published version, and explains a published method's address at the level of its contract, since its internals stay in the repository it names. It changes nothing in the method and writes nothing of its own: the one file it leaves is the method's flowchart, which the Pipelex tools write beside a bundle on disk when they validate it, and the explanation says where it is. For a bundle on disk the Pipelex tools are optional: they add a validation verdict and that flowchart.

## Prepare inputs

**`pipelex-inputs`** prepares a method's `inputs.json` from the input template the Pipelex tools derive: a placeholder template, synthetic data, your own files, or a mix. It works for a local bundle, a saved method's catalog id or a published method's `github.com/…` address, and for a catalog id says whether the template came from the draft or a published version. It keeps your own files and the prepared file out of git with a `.gitignore` entry, and waits for your say-so when git still does not ignore one, uploads local files to Pipelex storage and writes the run-ready values to `inputs.prepared.json` beside the source `inputs.json`, which it never rewrites, and it closes by offering the run, even when you said not to run, since the offer starts nothing until you say yes. A skill that hands it the work can ask it to stop at run-ready with no offer, as `pipelex-lab` does for a test case whose answer key is not written yet.

**`pipelex-synthetic-inputs`** makes the files a method needs when you have none: PDFs through reportlab; PNGs through Pillow and matplotlib, as charts, diagrams, scanned-looking pages with handwritten marks, or app screenshots; and Word and Excel files. `/pipelex-inputs` hands it every file-typed input. It renders from code, with no image-generation model, using only packages whose licences are compatible with MIT, and it installs them itself, through `uv`'s ephemeral environments or, when `uv` is absent, an isolated virtual environment under your cache directory. Nothing is installed into your project, and it always asks before installing a tool. Handwriting on a scanned form is simulated glyph by glyph from a handwriting-style font, and the skill tells you it reads more easily than a real hand. A photograph, which code cannot render convincingly, is generated by `gpt-image-2` through the Pipelex tools, with the facts the test needs planted in its description; that one file needs the API key and spends a little inference credit, and the skill waits for your go before generating it.

## Run and save

**`pipelex-run`** runs a method and follows a run, and does nothing else. It starts a run from a bundle directory, a catalog id or a published method's address, with inputs that are already run-ready, and prints the run id the moment the run starts. It checks the method before it reads any input. A request that changes one input, such as "run it on the sample with the question in French", is laid over the method's sample, a current `inputs.prepared.json` or else `inputs.json`, and every input the request does not name is kept; the line before the run says which inputs the request replaced. A run by catalog id finds its sample in `./<method_id>/`, where `pipelex-inputs` writes one, or in a directory whose `pipelex-method.json` links it to the id, says which it took, and asks when more than one holds a sample; only the inputs come from that directory, and the saved method is what runs. A bare id runs the method's latest published version, `mt_…@3` version 3 and `mt_…@draft` the draft, and the skill says which version ran; a method never published runs its draft, and the line before the run says so. A sample may leave out an optional input of the main pipe, and may write any input in the `{concept, content}` envelope. A pipe other than the main one is named by its qualified reference, its code prefixed by the domain of the file that defines it, as `domain.pipe_code`. Every completed run is saved into `runs/<run_id>/`, under the directory the agent was started in: its whole output as `main_stuff.json`, beside each file it produced, named after the field it fills. That output carries what the run read in your files, so in a git repository the skill makes sure `runs/` is ignored before it saves there, adding it to the nearest `.gitignore` when it is not and saying so; a path git still does not ignore waits for your say-so, and outside a repository nothing is done. It follows a run by its id alone, to its status, its results or a save of it, which works days later. A run of a directory linked to a saved method is filed under that method, so it appears in the method's history. A failure goes back to the skill that owns the repair. The skill never starts a run nobody asked for, and a dry run shows the method's flow, with the path of its flowchart page when the tools wrote one, and spends nothing.

**`pipelex-catalog`** carries a method between a bundle directory and your organization's Pipelex catalog: it lists what is saved, saves a directory as a new method or as the draft of the one its `pipelex-method.json` link names, publishes that draft as the method's next version, and pulls a saved method's draft or one of its versions back to disk. A save validates and stores the bundle as the draft in a single call, an invalid one included, and changes nothing a caller of the method's id runs, so it needs no confirmation. It sends the bundle's files by path, because the tools write the `pipelex-method.json` link only beside files they read from disk, and that link is what makes the next save an update rather than a second method; for a bundle outside the directory the agent was started in, which the tools cannot read by path, the skill says the link cannot be written and saves without it only if you say yes. On an update, that leaves the link behind the catalog, so the directory's next save is refused as a conflict with that save, which the skill recognises as its own; a pull into the same directory, once the tools can write there, brings the link up to date. A publish is made only when you ask for one: it saves the directory first, so what is published is what is on disk, says that every caller of the method's bare id runs the new version from its next call and that a published version is never taken back, and reports the version number, which `mt_…@<n>` then names for good. It never replaces a draft somebody else saved without asking you, restores a pulled version over the draft only on your request, and never deletes.

**`pipelex-lab`** is the experiment loop around a method. It frames a use case into candidate methods, with what the platform can and cannot do, and it is where a request to automate a piece of work starts: it frames the method's part and names what carries the rest, such as n8n or the agent's own mail and drive connectors. It writes each test case's answer key before its first run, and agrees a budget with you. Then it runs every case, scores each run against its key and logs it under `lab/<method>/` in your project, fixing the method round after round until it meets the pass bar or reaches a stop: the budget, a failing line traced to the inputs, or a round that scores worse than the best so far. It designs, prepares inputs, runs and edits through the skills that own those steps, and only its loop needs the Pipelex tools.

## Put a method in your code

**`pipelex-integrate`** wires a method into an existing TypeScript or Python codebase. The Pipelex tools write generated, drift-proof types into one directory per method; the skill excludes that tree from your formatters, records a `sources.json` sidecar, adds the offline drift check to your project's gate, and writes one typed call site that runs the method through the TypeScript SDK `@pipelex/sdk` or the Python SDK `pipelex-sdk`, naming its pipe by the qualified reference the validation returns, `domain.pipe_code`. For a saved method it recommends pinning a published version, `mt_…@<n>`, which never changes, so the committed types stay true. A project made from a Pipelex template keeps its own codegen harness.

**`pipelex-scaffold`** starts a project where none exists. A TypeScript web app around a method comes from the method-app template, created for the method by the template family's own initializer and left running by the template's `make serve`, with its URL reported. Every other project, a Python CLI or service included, comes from its language's own initializer, is committed and given its env file by the skill's own scripts, and is handed to `/pipelex-integrate`. On either branch, a project created inside another repository's work tree gets no repository and no commit of its own: its files are new files of that repository, for you to review and commit there. When that repository ignores the project's directory, as an ignored `tmp/` or a dotfiles repository ignoring `*` does, the project gets a repository of its own and its pristine commit, as it would outside every repository; when it ignores every file in the directory but not the directory itself, nothing versions the project, and the skill says so. And when the project's directory is itself a repository inside a work tree that does not ignore it, the skill commits nothing in it, and when an initializer made that repository, offers, without doing it, to remove it so the project's files belong to yours.

## Automations: the method and what carries it

A method reads the values and files it is given, and the public web, and returns its results. It does not fetch from your mail, drives or business systems, run on a schedule, or send and write back, on purpose: that is what keeps it testable, portable and easy for IT to approve. So when you ask for an automation, such as "summarise my unread mail every morning and post it to Slack", the skills build the part a method does, here a digest from a batch of emails, and name what carries the rest: n8n with the Pipelex node, the agent itself with your host's Gmail or Drive connectors for a one-off run, a method app for your team, or your own application through the SDK. They write no connector inside a method, and they write a client for another service around it only when you ask for one after hearing what it entails. The shared reference behind this is `skills/shared/fit.md`.

## What each skill needs

`pipelex-design`, `pipelex-edit`, `pipelex-organize`, `pipelex-inputs`, `pipelex-run`, `pipelex-catalog` and `pipelex-integrate` need the Pipelex tools, and stop with a setup instruction when the tools are absent. `pipelex-lab` needs them for its loop alone, and `pipelex-explain` uses them when they are there.

`pipelex-synthetic-inputs` needs no Pipelex tool and no key for anything but a photograph. `pipelex-scaffold` needs none either: git, the method-app family's initializer and `make serve`, the language initializers and its own two scripts are all it uses, although the method-app template's `make create` calls the hosted API with your key.

The skills share one reference for MTHDS, the language a method is written in: `pipelex-design` reads it before every write, and `pipelex-edit`, `pipelex-explain`, `pipelex-inputs` and `pipelex-integrate` read it for a syntax question. It says to leave a pipe's `model` out unless you ask for a model, a setting or a kind of behaviour, or the pipe reads an input the default model cannot, as an extraction over a web page does, and when you do ask, how `pipelex-design` and `pipelex-edit` look the reference up and check it with `mthds_models` rather than guess one. The language keeps the standard's name; Pipelex is the product that builds and runs it.

## The Pipelex tools

The tools reach the Pipelex API with your key, the same one the hook uses. Each tool that takes a method takes the files themselves, a saved method's catalog id as `method_id`, or a published method's address as `method_ref`; a call by id needs an API key, because the catalog belongs to an organization. A bare id names the method's latest published version, `mt_…@<n>` version n and `mt_…@draft` the draft, and every result says which one it read or ran. The tools read a file by path only inside the directory the agent was started in, an absolute path included; for a bundle outside it, start the agent from a directory that holds the bundle, or the skills send the files' contents instead. A version of the tools that draws the method graph also writes the method's flowchart, `method-graph.html`, beside files it validates by path, and rewrites it on each validation; `pipelex-explain`, `pipelex-design` when it hands over a method and `pipelex-run` on a dry run tell you where the page is, and the other skills leave it without a word.

- **`mthds_validate`** validates a method. Its verdict carries the main pipe's signature, from which `/pipelex-integrate` types a call site.
- **`mthds_inputs_template`** returns the input template of a pipe.
- **`mthds_models`** lists the model deck, the presets, aliases and waterfalls a pipe's `model` field can name, by category, or checks one reference and suggests the nearest names when it does not resolve. `/pipelex-design` and `/pipelex-edit` call it before they write a model you asked for. The deck is what the runner can serve, not what your account may use, so a listed model can still be refused when a run starts.
- **`mthds_codegen`** turns a method's concepts into typed code (`ts-zod`, `python-pydantic` or `python-structures`) and, given an `output_dir`, writes the tree to disk.
- **`mthds_prepare_inputs`** uploads the file values of a filled template to Pipelex storage, so a run can reach them.
- **`mthds_run`** starts a run, and **`mthds_run_status`**, **`mthds_run_results`** and the tools beside them follow it to its status, its results and its files.
- **`mthds_list_methods`**, **`mthds_save_method`** and **`mthds_get_method`** list the methods saved in your organization, save a method's draft, and fetch a draft or a published version.
- **`mthds_publish_method`** publishes a method's draft as its next version, which is what callers of its bare id run. Only `/pipelex-catalog` calls it, and only when you ask for a publish.

The full reference for each tool is in [`pipelex-mcp`'s tools reference](https://github.com/Pipelex/pipelex-mcp/blob/main/docs/tools.md).
