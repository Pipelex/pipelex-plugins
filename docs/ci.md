# Continuous integration

Everything this repo runs on GitHub lives in `.github/workflows/`. Most of it runs on pull requests, some of it only on a release-shaped one, the recipe suite stays off the ordinary pull request because it needs network and minutes, and one workflow runs on the merge to `main`, to tag the release. The table says which is which; the sections below say why.

| Workflow | Status check | Runs on | What it runs |
| --- | --- | --- | --- |
| `checks.yml` | `Checks` | every pull request | `make check` |
| `tests.yml` | `Unit tests` | every pull request | `make agent-test`, with Node 22 installed for the hook corpus sweep, then `make check-outside-smoke` |
| `windows.yml` | `Cross-OS tests (PowerShell, no bash)` | every pull request, and on demand | `uv run pytest -m cross_os` on `windows-latest`, in PowerShell, with bash off the `PATH` |
| `guard-branches.yml` | `Gate main` / `Gate release` / `Gate dev` | a pull request opened, edited, reopened or pushed to (`pull_request_target`) | the branch-flow rules, no checkout |
| `changelog-check.yml` | `Changelog entry` | a pull request into `main` | `CHANGELOG.md` carries the version being shipped |
| `version-check.yml` | `Version check` | a pull request into `main` or into `release/vX.Y.Z` | the version in the files is the version in the branch name |
| `recipes.yml` | `Recipes` | nightly, on demand, and on a pull request touching the recipe sources | `make test-recipes` |
| `release-tag.yml` | `Release tag` | a push to `main` | the annotated tag `vX.Y.Z` on the merge commit, when the push raised the version and the tag does not exist yet |

The status check column is the name GitHub reports, which is the job's name and not the workflow's — that is the string a branch ruleset has to name to make a gate blocking.

## The make targets on every pull request

Every job that installs Python takes its version from `.python-version`, through `actions/setup-python`'s `python-version-file`, so CI runs the interpreter a local `make` builds the environment on, and `make check` fails a workflow that names a version of its own.

**`Checks` runs `make check`, and template freshness is the part that matters.** The generated plugin trees — `pipelex/`, `pipelex-codex/`, `pipelex-vibe/` — are checked in, so a template edited without `make build` ships a plugin that disagrees with its own source. `scripts/gen_skill_docs.py --target all --check` re-renders every target and names each generated file that is missing or byte-different, the copied per-skill `references/` and `scripts/` included — a script whose executable bit differs from its source's is named too — and compares each target's whole directory, so a file no template or source produces, anywhere in it, is named as an orphan and a `.j2` file as a leaked template. `scripts/check.py` also fails a target that lost the credential wiring `targets/defaults.toml` declares, and a build-error marker in any generated file. The same target then runs the Claude and Codex marketplace consistency checks, `ruff format --check`, `ruff check`, a second `ruff check --select=F401 --no-fix` (the config ignores `F401`, so the plain run is blind to an unused import while `agent-check` quietly repairs one), `pyright` and `mypy`.

It is `make check` and deliberately not `make agent-check`: the agent target begins with `fix-unused-imports`, `format` and `lint`, which rewrite files. A check reports; it does not repair. Run `make agent-check` locally, before pushing, and let CI run the read-only half — which now reports everything the agent target would have fixed, the unused imports included.

`Checks` sees half of the **vendored hook bundle**. `make check` compares each target's `hooks/check.mjs` against `templates/hooks/assets/check.mjs`, so a target that fell behind the template goes red, and it reads the template copy's provenance line, refusing a bundle built from an unreleased `@pipelex/tools-wasm` or outside a git checkout of `pipelex-sdk` (`docs/hooks.md`, "Re-vendoring check.mjs"). What it cannot see is a bundle that is *behind*: that needs npm's latest engine and a rebuild in the `js/` directory of a sibling checkout of `pipelex-sdk`, and CI has no sibling checkout. `make check-hook-fresh` asks both questions, and it is a release gate, run by the release skill among its local gates, rather than a CI check. `Unit tests` also catches the failure a stale bundle produces wherever the MTHDS Test Corpus exercises it, a hook that refuses a form the standard allows, on every pull request, but only for what the corpus exercises.

**`Unit tests` runs `make agent-test`** — the pytest suite, quiet unless something fails, so a green run is a few lines rather than a screenful. The job installs Node 22 first, because `tests/unit/test_hook_corpus.py` runs the vendored hook bundle over the vendored MTHDS Test Corpus, and `tests/unit/test_hook_commands.py` runs the Codex wrapper and the bundle on the payloads its matcher admits, and both fail rather than skip under `CI` when no `node` is on the PATH: a gate skipped in CI is a green light for nothing. `docs/hooks.md` ("Checks") says what the sweep expects of each entry. `pyproject.toml`'s `addopts = "-m 'not recipes'"` deselects the recipe suite; `recipes.yml` is what runs that one.

**The same job then runs `make check-outside-smoke`, the outside render as a consumer runs it.** It builds the wheel from the checkout with `uv build`, installs it into a fresh environment with its bytecode compiled, as pip does by default, and runs its `pipelex-plugins-render` console command with `--check` on a copy of `tests/data/outside-target-smoke/` outside the checkout: the fixture's committed rendering must pass, and must fail once a byte of it has changed, so a check that passes on anything goes red too. It then renders every upstream skill from the checkout and runs the installed command's `--check` on that output: the installed render must produce the same files, bytes and executable bits alike, and nothing the installer compiled beside them. The wheel and the environment are new on every run, so no build cached by uv stands in for the checkout. That is the one check that reads the wheel rather than the checkout, since the installed command reads the templates, static assets and targets the wheel carries inside its `scripts` package, so a file the render needs and the wheel leaves out passes every unit test and fails here. The unit suite checks the same fixture first, from the checkout (`test_the_smoke_fixture_s_committed_rendering_is_current`), so a stale rendering, which an edit to the one upstream partial the fixture includes produces, fails `make agent-test` and names `make render-outside-smoke`, which re-renders it. The step needs the network on a cold `uv` cache, for hatchling and Jinja.

## The Windows job

**`windows.yml` runs the tests marked `cross_os` on `windows-latest`, under PowerShell, with no bash.** The first Windows machine the plugin targets has PowerShell and no Git Bash, so nothing the plugin runs for Claude Code may need bash, and this job reproduces that machine: every step runs in `pwsh`, the repository is checked out with `core.autocrlf=true` set before the checkout, as Git for Windows sets it by default, and before the tests a step removes from the `PATH` every directory holding a `bash.exe` or an `sh.exe`, Git's `bin` and `usr\bin` among them, while Git's `cmd` stays, since it holds `git.exe` alone and the tests call git. The next step proves it: it fails when a `bash` or `sh` still on the `PATH` runs a command, which leaves only `System32`'s WSL launcher, which runs nothing without a distribution. The job installs Python from `.python-version`, Node 22, uv and the Claude Code CLI from npm, then runs `uv run pytest -m cross_os`, with no make, since make's recipes need bash. `make test-cross-os` runs the same selection on a Mac, and the Ubuntu `Unit tests` job runs these tests too, inside `make agent-test`, so every one of them runs on the three platforms.

What it proves today:

- **The workshop starts as the manifest says** (`tests/unit/test_mcp_launcher.py`). The manifest's command line, `node` and the launcher's path with the plugin root substituted under a directory whose name holds a space, completes an MCP `initialize` with the real `@pipelex/mcp` from npm, and lists its tools, so the job needs the npm registry. The hermetic tests beside it run the launcher on a copy of the Node binary with a stand-in npm beside it: on Windows it must run npm's `npx-cli.js` beside the binary, or go through the shell when that file is absent, and on macOS and Linux it must spawn `npx` from the `PATH`; it promotes a filled option to the key and leaves an empty one alone, and passes its stdio and exit code through.
- **Claude Code connects the server.** `claude --plugin-dir <plugin> mcp list`, with a new and empty configuration directory, so no sign-in, must report the plugin's server connected. The job sets `PIPELEX_PLUGINS_REQUIRE_CLAUDE_CLI`, so a missing `claude` fails there; on a developer machine without the CLI the test skips.
- **The hook checks an edit with no shell** (`tests/unit/test_claude_hook.py`): it blocks a broken method and passes a clean one under a plugin root and a project whose paths hold a space and Windows's backslashes, and holds the pre-filter, the key promotion and the fail-open pass on a missing bundle.
- **The build writes LF on every OS** (`tests/unit/test_gen_skill_docs.py`), so a build on Windows produces the checked-in trees byte for byte.

What it cannot prove: a launch from Claude Desktop, whose environment comes from the desktop rather than a shell, and the behaviour of a real Claude Code session on Windows, such as how its Bash tool runs without Git Bash. Those are checked by hand on the PowerShell machine. Nothing runs on macOS in CI; macOS is covered by `make agent-test` and `make test-cross-os` on the developers' machines.

The `workflow_dispatch` trigger is read from the default branch, so it stays inert until this file has reached `main`; the pull-request trigger runs it from the day it lands.

## The branch-flow guard

`guard-branches.yml` enforces the workspace convention that a pull request targets `dev`, that only a `release/vX.Y.Z` branch targets `main`, and that a work branch is named with one of the closed set of prefixes — `fix`, `feature`, `refactor`, `chore`, `docs`, `ci-cd`, `changelog`, `codex`. It is convention enforcement and not security: what actually refuses a merge is the branch ruleset. It checks out nothing and reads every pull-request ref through an environment variable rather than interpolating it into a shell command, because a fork's branch name is text somebody else wrote.

Each of the three jobs is conditional on the base branch, so a pull request whose base is none of `dev`, `main` or `release/v*` runs no job and is refused nothing. That is deliberate: the workspace convention allows a stacked pull request, which targets the branch below it in the stack.

It triggers on `pull_request_target`, which means **GitHub runs the copy of the file that is on the repository's default branch — `main` — whatever branch the pull request targets.** It read the base branch's copy until GitHub changed that on 2025-12-08. That is what keeps a fork from editing its own gate, and it has a consequence worth knowing, because it is larger than it looks: the three gates report **nothing at all** — not a pass, not a skip, no check run — until `guard-branches.yml` has reached `main`, and `main` moves only when a release merges. So from the moment this workflow lands on `dev` until the first release after it, the branch convention is back to memory; and every later edit to the guard is inert in the same way, taking effect a release late. Whether `pull_request_target` is the right trade for a gate whose own header calls itself convention enforcement rather than security is a live question, not a settled one.

## The release-only gates

Neither `changelog-check.yml` nor `version-check.yml` does anything on an ordinary pull request into `dev`; both fire only where a version is being shipped.

The version of record is `targets/prod.toml`'s `[plugin].version`. `make check` is what holds the other targets and the Claude marketplace to it, so `Version check` checks the one relation nothing else can see: that the number in the files and the number in the branch name agree. Into `main` the version must also be strictly greater than the one `main` already carries; into or out of `release/vX.Y.Z` it must equal `X.Y.Z`. Both versions are required to be plain dotted integers before anything is compared, which matches `scripts/check.py` — there is no pre-release form here.

Both gates read the version out of the pull request's **merge commit**, not out of its head: neither checkout passes a `ref:`, so on a `pull_request` event what lands on disk is `refs/pull/<n>/merge`. That is worth knowing because it settles the one shape that looks like a contradiction. The release play itself opens only one pull request, from the release branch into `main` — the branch is cut from `dev` and bumped in place — but `Gate release` also allows a `dev → release/vX.Y.Z` pull request, for a fix going onto a release after the cut. That one carries `dev`'s older version on its head, so it looks as though `Version check` must fail it. It does not: only the release side ever touched `targets/prod.toml` since the branch was cut, so the three-way merge keeps the release branch's own bump, the equality check reads `X.Y.Z`, and it passes. The two gates agree about that pull request rather than disagreeing.

`Changelog entry` requires `CHANGELOG.md` to carry a `## [X.Y.Z] - …` heading for that version before the release reaches `main`. Note the shape: this repo's headings carry **no** `v`, which is where it departs from the sibling repos the workflow was ported from. The merge to `main` is the publish here — install is a marketplace add against the default branch — so that pull request is the last moment a release with no changelog entry can be stopped.

That last point is why this gate validates the version as plain dotted integers itself rather than leaning on `Version check` beside it, even though the two always run on the same pull request. The version becomes part of a regular expression here, and escaping its dots is not enough on its own: a version that is *itself* a pattern comes through the escaping still live and matches whichever heading the changelog already carries, so the gate would pass a release against somebody else's entry. A gate this late answers for its own question.

## The recipes

`make test-recipes` executes every runnable block the `pipelex-synthetic-inputs` references ship, on both rungs of the environment ladder, and it is the only thing that would catch a reference recipe rotting — the exact failure the suite was written for, after the predecessor's image recipe pointed at a bundle that no longer existed and nothing noticed. It needs network and downloads packages on a cold `uv` cache, so it stays off the ordinary pull request and runs on three triggers instead:

- **Nightly**, which is the backstop against a recipe that rots because a dependency moved rather than because anybody edited it.
- **On demand** (`workflow_dispatch`), for when a recipe is being worked on.
- **On a pull request that touches the recipe sources or the harness they run through** — `skills/pipelex-synthetic-inputs/references/`, `templates/skills/pipelex-synthetic-inputs/`, `tests/recipes/`, the workflow itself, and the `Makefile`, `pyproject.toml` and `uv.lock` the suite is invoked and resolved through. Those are the paths `tests/recipes/test_recipes.py` actually reads or depends on: renaming the `recipes` marker or editing the target breaks the suite as surely as editing a recipe does. That is the moment an edit can break a recipe, and the one case where waiting minutes for the answer is worth it.

GitHub reads `schedule` and `workflow_dispatch` from the default branch, so both of those stay inert until this file has reached `main` with a release; the path-filtered pull-request trigger works from the day it lands on `dev`. Two things follow from the default branch being where the cron lives. What it tests is `main`, not `dev`, so a recipe broken on `dev` is not caught nightly until it is released — defensible, since `main` is the published artifact, but worth knowing. And GitHub disables a scheduled workflow in a repository that has seen no activity for sixty days, which is exactly the stretch in which a nightly backstop earns its keep; it comes back by hand, from the Actions tab.

## No usage statistics

Every workflow sets `DO_NOT_TRACK: "1"` in its workflow-level `env:`, as the workspace's usage-statistics specification requires of every repository's CI (`conformance/specs/usage-statistics.md`, rule R8), so that no check or test run reports anonymous usage statistics: a CI run is not a use of the tools, and every event sent is billed. No job here starts pipelex, `plxt` or the `mthds` CLIs today, since the hook bundle reports nothing; the launcher's tests start the real workshop from npm and the Claude Code CLI, each with `DO_NOT_TRACK=1` in its environment, and the switch is what keeps a later test that starts anything else from reporting. Set at the workflow level, it reaches a job added later the day that job appears. `tests/unit/test_ci_workflows.py` holds every workflow to it: the workflow-level value must be `1`, and no job, step, container, service or script may set it to anything else or unset it. `guard-branches.yml` and the `schedule` and `workflow_dispatch` triggers of `recipes.yml` run the copy on `main`, so for them the switch takes effect with the next release.

## Requiring a check

No ruleset on `dev`, `main` or `release/v*` requires a status check, so every gate above advises and none of them blocks a merge; `make check-github-rules` at the workspace root is what says whether that is still so, rather than this page. Making one blocking means naming its status check in the branch's ruleset on GitHub. Those *names* are deliberately absent from the workspace's `github-rules.toml` — which does govern this repository, as `pipelex-plugins = {}` — because the policy file carries each repository's *shape*, and the `github-rules` tool reads the required check names from the live ruleset and the branch's classic protection and carries them over unchanged. Adding a requirement is therefore an edit to the ruleset and never to that file; the workspace's `docs/workspace/github-rules.md` says why.

It also warns of the other direction, and two of the checks here walk straight into it: a required check that nothing posts leaves every merge pending while the branch looks perfectly healthy. `Recipes` posts nothing on a pull request that leaves the recipe sources alone, and the three `Gate *` checks post nothing at all until `guard-branches.yml` is on `main`. Require either before that is true and nothing merges.

The opposite trap is just as quiet. A job that GitHub *skips* because its `if:` was false counts as satisfying a required check, and each `Gate *` job is gated on the base branch — so requiring `Gate main` on `dev` would pass every pull request without testing anything. Require `Gate dev` on `dev`, `Gate main` on `main`, `Gate release` on `release/v*`, and no other pairing.

## The merge to `main` tags the release

The repository is the artifact: on Claude and Codex install is `plugin marketplace add Pipelex/pipelex-plugins`, which serves the default branch, so the merge to `main` is the publish, and nothing is deployed or sent to a registry. What runs on that merge is `release-tag.yml`. It reads `targets/prod.toml`'s `[plugin].version`, and when the push raised that version and the tag `vX.Y.Z` does not exist yet, it pushes the annotated tag on the merge commit. A push that leaves the version alone or lowers it tags nothing, even with the tag missing, so no later commit or revert can take a release's tag, and a raising push that finds the tag already at another commit fails. A failed run is re-run from the Actions page, which repeats the release's own push; the release skill names the tag cut by hand at the merge commit for what a re-run cannot cure, followed by one more re-run, which finds the tag on its commit and succeeds, since `/ledger-land` needs the run to succeed as well as the tag. A missing `## [X.Y.Z] - ` heading in `CHANGELOG.md` is a warning there, not a refusal, since the merge has already published the version; what stops a release for it is the release skill reading `Changelog entry` on the release pull request, which, like every check here, no ruleset requires. The workflow runs on that push alone, with no manual trigger and no concurrency group, so it can never tag another branch's commit and GitHub never cancels a release's run as superseded, and its job asks for `contents: write`, since the organization's default token is read-only.

The tag is the pin an outside target renders the skills at, `uvx --from git+https://github.com/Pipelex/pipelex-plugins@vX.Y.Z pipelex-plugins-render` ([development.md](development.md), "Rendering for an outside target"), and the release skill's **What ships** section names the workflow and the tag, which `/ledger-land` reads to verify a release. No GitHub Release is made.
