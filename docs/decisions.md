# pipelex-plugins — foundational decisions

This records the decisions that shaped the repo, for anyone joining later. The build-system architecture doc (`build-targets.md`) arrives with the build system itself.

## What this repo is

**Pipelex plugins** — skills and hooks for working with MTHDS methods — built with the same multi-target scaffolding as `mthds-plugins` (Jinja2 templates → per-platform outputs, served through a marketplace), but for the hosted-API / MCP generation. They ship **no local-CLI dependency and none of the install/upgrade/env-check machinery** that `mthds-plugins` carries.

`mthds-plugins` stays published and untouched. This is a new sibling repo, not a fork of it.

## Brand boundaries

The **plugins** are Pipelex's product surface: marketplace `pipelex-plugins`, plugin `pipelex`, outputs `pipelex/`, `pipelex-codex/`, `pipelex-vibe/`. The **language** stays MTHDS inside the docs — MTHDS is the standard; Pipelex is the tooling, product, and service. Skills are renamed `mthds-*` → `pipelex-*`; language-reference content keeps its MTHDS vocabulary.

## Targets

Per-platform targets: **Claude Code**, **Codex**, **Mistral Vibe**. The `dev` and `sandbox` targets from `mthds-plugins` are left behind — `dev` exists to test container-local CLI install paths (exactly what a CLI-free plugin doesn't need); `sandbox` can be added later if the app chatbot migrates.

## Hooks — CLI-free posture

The `.mthds` validation hooks ship on all targets. Their behavior differs from `mthds-plugins` in one way: when the MTHDS CLIs (`plxt` / `mthds-agent`) are **absent**, the hook **passes silently** instead of blocking with an install hint — this plugin does not manage CLI installation. When the CLIs happen to be present, the full validation pipeline runs unchanged. This is a deliberate transitional state; the iteration path swaps the CLI invocations for hosted-API / MCP calls, at which point the missing-CLI branch disappears.

## Codex hooks — verified against Codex 0.142.5 (2026-07-06), re-verified in-session on 0.144.4 (2026-07-14)

The Codex hook engine matured across 0.139 → 0.142 (out of `Stage::UnderDevelopment`):

- The canonical feature key is now **`hooks`**, marked `Stage::Stable` and **enabled by default** (`codex_hooks` is a deprecated alias — still honored on 0.144.4, confirmed from the source's legacy-feature map after binary strings suggested it might be gone). `plugin_hooks` is *not* an alias: it was an independent opt-in for plugin-bundled hooks that disabled them on Codex ≤ 0.133, removed in 0.134, ignored since, and formally `Stage::Removed` in 0.144 (semantics pinned down in mthds-js v0.18.0, which hard-errors on all three hook-disabling keys in its `apply-config`/`doctor` — machinery this CLI-free plugin deliberately doesn't carry).
- Native per-source **trust model**: persisted `[hooks.state]` trusted hashes; `--dangerously-bypass-hook-trust` for automation. Trust keys are per plugin hook config (`pipelex@pipelex-plugins:hooks/codex-hooks.json:post_tool_use:0:0`) and survive plugin re-installs as long as the hook config's hash is unchanged.
- `PostToolUse` officially fires for **`apply_patch` edits and MCP tool calls**, not just Bash — which de-risks the whole `.mthds`-on-edit validation hook.
- Standardized block protocol: `{"decision":"block","reason":...}` (or exit 2 + stderr); Codex replaces the tool result with the feedback and continues. This maps cleanly onto the Stage 3 domain-based block/context decision model.
- Hook commands get `${PLUGIN_ROOT}` / `${CLAUDE_PLUGIN_ROOT}` substituted with the installed plugin root; 0.144 adds `${PLUGIN_DATA}` / `${CLAUDE_PLUGIN_DATA}` (a per-plugin data dir under `$CODEX_HOME/plugins/data/`). Substitution is a plain string replace — no `${VAR:-default}` form.

Consequence: the old "enable `[features] plugin_hooks` + sandbox network access" manual step is gone entirely — hooks are on by default, so the bundled hook loads on its own and the only step is trusting it on first run. (This plugin is CLI-free, so there was never a sandbox-network step to keep anyway.)

**In-session verification (Codex 0.144.4, 2026-07-14):** the shipped wasm+API hook was exercised in live headless Codex sessions (`codex exec --dangerously-bypass-hook-trust`): an `apply_patch` writing a broken `.mthds` was **blocked** and the hook's lint diagnostics (line/col spans) reached the model verbatim as the replaced tool result; a valid-but-non-canonical `.mthds` write **passed** and was canonically formatted in place; non-`.mthds` patches stayed silent. On a dev machine with the CLI-era `mthds@mthds-plugins` plugin also installed, both hooks fire on the same edit and Codex concatenates the block reasons — expected coexistence, not a bug; disable one side per-invocation with `-c 'plugins."mthds@mthds-plugins".enabled=false'` when isolating.

## Codex plugin lifecycle — cache model on 0.144.x (2026-07-14)

Installed plugins run from a **cache copy** (`$CODEX_HOME/plugins/cache/<marketplace>/<plugin>/<version>/`) taken at `codex plugin add` time — `codex plugin list`'s PATH column shows the marketplace *source*, not the runtime copy, which is misleading when dogfooding a local checkout. `codex plugin marketplace upgrade` now refreshes **Git marketplace snapshots only** and errors on a local-path marketplace; the way to propagate local edits is an idempotent re-`add` (`codex plugin add pipelex@pipelex-plugins`), which re-copies the cache. `make codex-refresh` and both `make codex-use-*` targets do exactly that.

## Build system (Phases 1–2)

The build system (`docs/build-targets.md`) was ported from `mthds-plugins` and trimmed. A few deliberate choices for anyone joining mid-way:

- **`frontmatter.md.j2` is an include-only partial.** It is `{% include %}`-d by skill templates for their YAML frontmatter but is *not* in `SHARED_TEMPLATES`, so it is never rendered standalone. (The predecessor rendered it standalone; with `min_mthds_version` dropped it would only ship a near-empty artifact.)
- **Hooks are wired (Phase 4).** `HOOK_TEMPLATES_BY_PLATFORM` renders the `.mthds` validation hooks per target (Claude `hooks.json` + `check-mthds.sh`; Codex `codex-hooks.json`; Vibe `vibe-hooks.toml` + `check-mthds-vibe.sh`), and `.codex-plugin/plugin-base.json` carries the `hooks` field. See [hooks.md](hooks.md).
- **Dropped from the predecessor's checker:** the stale-install-reference check and the `min_mthds_version` frontmatter check (both CLI-coupled). The Vibe hook-artifact check landed with the hooks (Phase 4).

## MCP server declaration (2026-07-14)

> **Superseded in part (2026-07-21):** the transport flipped from the baked hosted URL to the local workshop launcher — see "Dual-MCP flip" below. What stands from this section: the inline-`mcpServers`-in-the-manifest location (D1), the server key `pipelex`, and the tool-naming consequences. The http-URL shape and the literal-URL amendment below remain as history of why a baked URL can carry no per-user key — the very fact that made it unbakeable under BYOK.

The plugin declares the **`pipelex-mcp`** server (streamable HTTP; tools `mthds_validate`, `mthds_inputs_template`, `mthds_prepare_inputs`, and the `mthds_run` family) so the MCP-backed skills (`pipelex-design`, `pipelex-organize`, `pipelex-edit`, `pipelex-inputs`) can call it natively — no vendored script, no `curl` recipes.

- **Location: inline `mcpServers` in the generated Claude `plugin.json`** (not a plugin-root `.mcp.json` — both are supported by Claude Code; inline keeps everything in the one generated manifest). The build injects `{"pipelex": {"type": "http", "url": "<mcp_server_url>"}}` for Claude-platform targets, sourced from the `mcp_server_url` template variable (`targets/defaults.toml`, overridable per target). Claude Code connects plugin-declared servers automatically at session start; the tools reach the model as `mcp__plugin_pipelex_pipelex__<tool>`.
- **The URL is literal — no `${PIPELEX_MCP_URL:-<url>}` wrapper (amended 2026-07-16).** The original design wrapped the URL so a session-start env var switched dev/prod without a rebuild, and the Claude Code CLI does expand `${VAR:-default}` in plugin MCP config (verified in the Phase 3 live sessions). But the **Claude desktop app performs no such expansion** (open upstream bugs — the server receives the wrapper string verbatim and the connection breaks), and desktop sessions can't set env vars anyway, so the wrapper could never help there and actively broke the primary install target. Dev override on Claude is now the local-marketplace dogfood loop: edit `mcp_server_url` in `targets/defaults.toml` + `make build` (local dev server: `http://localhost:3000/mcp` via `make dev` in `../pipelex-mcp`).
- **The baked default is currently the `pipelex-mcp` Alpic dev tunnel** — an interim so marketplace installs reach a live server; switch it to the stable URL when `pipelex-mcp` deploys.
- **Codex gets a baked entry too** since the 0.144.4 verification (see the dedicated section below); its manifest carries the literal URL because Codex does no env expansion in MCP config. **Vibe still gets no entry**: plugin-bundled MCP declarations remain unverified there (same empirical-verification bar). Interim for Vibe: manual registration, TBD in the README.
- **Auth is server-side.** The MCP holds the upstream API key (`MTHDS_API_KEY` in its hosting env); `PIPELEX_API_KEY` is a hook-only concern and plays no role in the skills' validation path.

## Codex plugin-bundled MCP declaration — verified against Codex 0.144.4 (2026-07-14)

> **Superseded in part (2026-07-21):** the Codex entry is now a stdio command, not a URL — see "Dual-MCP flip" below. What stands: the inline camelCase `mcpServers` object in `.codex-plugin/plugin.json`, the `mcp__<server>__<tool>` flattened naming, the no-trust-gate observation, and config-tier precedence as the dev override (re-verified for the command shape).

Codex 0.144.x loads MCP servers from installed plugins; verified both from the `rust-v0.144.4` source and hands-on with the installed plugin (server listed by `codex mcp list`, and a live session round-tripped `mthds_validate` against a running `pipelex-mcp`). The wiring decision:

- **Shape: inline camelCase `mcpServers` object in `.codex-plugin/plugin.json`** — same one-manifest posture as Claude (D1). Codex accepts either this inline object or a plugin-root `.mcp.json` file referenced as `"mcpServers": "./.mcp.json"` (both verified working); inline avoids a second generated artifact. The build injects `{"pipelex": {"url": "<mcp_server_url>"}}` for Codex-platform targets. No `type` field: Codex picks the streamable-HTTP transport structurally from the bare `url` (a `type` key is Claude-compat-tolerated but stripped).
- **The URL is literal — Codex performs no `${VAR}` / `${VAR:-default}` expansion anywhere in MCP config** (its only `${…}` substitution is hook-command-only). The dev/prod switch instead relies on precedence: a same-named user entry (`[mcp_servers.pipelex]` in `~/.codex/config.toml`, or `-c 'mcp_servers.pipelex.url="http://localhost:3000/mcp"'` per invocation) **outranks the plugin declaration** (config tier beats plugin tier in Codex's MCP catalog; verified empirically). The baked URL carries the same interim-dev-tunnel caveat as Claude's until `pipelex-mcp` deploys.
- **Tool naming:** Codex exposes plugin MCP tools as `mcp__<server>__<tool>` — `mcp__pipelex__mthds_validate` / `mcp__pipelex__mthds_inputs_template` (no plugin-name nesting, unlike Claude Code). The skills' generic "the `mthds_validate` tool" phrasing works unchanged; the Claude-only `allowed-tools` frontmatter doesn't apply to Codex.
- **No trust gate:** unlike hooks, plugin MCP servers have no trusted-hash/approval step — the server connects when the plugin is installed and enabled (per-server `enabled` defaults to true). `codex mcp list` shows plugin-declared servers, which makes registration verifiable without a session.
- If auth lands on the hosted MCP later, Codex's server config supports `bearer_token_env_var` and `http_headers`/`env_http_headers` (a raw `bearer_token` is rejected for HTTP transports) — env indirection exists for auth even though URL templating doesn't.

## Dual-MCP flip: every baked declaration is the local workshop launcher (2026-07-21)

`pipelex-mcp` ships two servers from one capability core: the hosted **Skybridge console** (streamable HTTP, on Alpic) and the npm-distributed **local workshop** (`@pipelex/mcp`, stdio, resolves `{ path }` items from disk with cwd containment). Since `@pipelex/mcp` 0.5.0 the console is bring-your-own-key: it holds no server-side `PIPELEX_API_KEY`, and a plugin bakes a *literal* config with no channel for a per-user key — so a baked hosted URL produces verdicts for no one. Meanwhile the builder hosts the plugin serves (Claude Code, Codex — terminal, node present) are exactly where the launcher works, and the workshop was always their intended server: submitting local files through the hosted console pays the LLM hand-copy penalty, which no auth mechanism fixes. Full rationale: the Pipelex workspace's `wip/history/mcp-dual-deployment/pipelex-mcp-plugin-reconciliation.md` §8 (revision 2026-07-21). The decisions:

- **Every baked plugin MCP declaration is the local workshop launcher; the hosted console is never a plugin declaration.** Consumers who want the console add it as a connector in their host's own UI (`?api_key=` now; sign-in once console OAuth ships). The flip is **definitive, not a BYOK workaround** — it sits on the transport axis (local files need a local server), so console OAuth changes only connector-connection prose in the README: zero manifests, zero build mechanics. *(Amended 2026-09-12: console OAuth shipped, and bring-your-own-key was removed from the console in `@pipelex/mcp` 0.12.0, after which a `?api_key=` or `Authorization: Bearer plx_sk_` connector no longer connects at all. The README passage now says to add the connector by its plain URL and sign in, with an upgrade note for old connectors. As predicted, no manifest and no build mechanic moved for it. Amended again 2026-09-24: that passage moved to `docs/install.md`, "The Pipelex MCP, for chatbots", when the README was rewritten to the workspace's README standard, and its address is now `https://mcp.pipelex.com/mcp`.)*
- **Launcher: `npx -y @pipelex/mcp@latest`.** The plugin pins nothing (the hosted API stays the compatibility anchor); `@latest` re-resolves the dist-tag per spawn where a bare spec would reuse the cached install. Verified: warm spawn ~1s to MCP initialize, first-ever spawn ~11s (npx cache population). The pinned-and-bumped fallback was rejected after measurement showed pinning buys no offline resilience either (npx contacts the registry even for cached exact specs — registry-down means no MCP tools that session in both shapes, and the skills' stop-posture covers it).
- **Pinned manifest shapes** (verified live on both platforms, `mthds_validate` round-trips with a real key): Claude `{"type": "stdio", "command": "npx", "args": ["-y", "@pipelex/mcp@latest"]}` — the spawned server inherits the full shell env, so `PIPELEX_API_KEY` just works. *(Superseded for credentials by the userConfig decision below: the Claude entry keeps this direct spawn shape but now carries an `env` block injecting the user-config values.)* Codex: same minus `type` (transport picked structurally), **plus `"env_vars": ["PIPELEX_API_KEY", "PIPELEX_BASE_URL"]`** — Codex spawns MCP servers with a minimal whitelist env (shell env is not passed through; `shell_environment_policy` doesn't apply to MCP spawns), and `env_vars` forwards variables *by name* from the user's own env. `PIPELEX_BASE_URL` is forwarded too because a key is only valid against its own base URL (a dev key against the default prod URL gets `Forbidden`).
- **Server key stays `pipelex` in every shape** → flattened tool names unchanged (`mcp__plugin_pipelex_pipelex__<tool>` on Claude Code, `mcp__pipelex__<tool>` on Codex) → skills keep their tool references verbatim.
- **The renderer is command-only.** `mcp_server_url` is retired, replaced by the `[vars.mcp_server]` table (`command`/`args`/`env_vars`). The url shape is not carried speculatively ("don't port dead switches") — it returns the day a consumer-facing target actually wants a baked hosted entry, a post-OAuth question.
- **Vibe target unchanged:** no manifest declaration; docs point at manual registration of the launcher. *(Superseded 2026-09-12 — see "Vibe target bakes the launcher as a config fragment" below.)*
- **Skills' auth line rewritten:** "no API key is needed on your side" described the key-holding dev-tunnel server and is retired. The workshop authenticates with the caller's `PIPELEX_API_KEY`; the skills surface the `config`-class error `hint` when it's missing or rejected, exactly as they already do for an unreachable server.
- **Claude Desktop** is out of scope for the baked launcher (GUI apps inherit no shell env; node may be absent): Desktop users are pointed at the hosted-console connector in the README. The exact Desktop failure UX (silent skip vs error toast) is still unverified — tracked in `wip/dual-mcp-workshop-launcher.md` (V-P3, archived). *(Revised same day: the shell-env half of the problem is solved by plugin userConfig — see the next decision. Live Desktop sessions showed `npx` does spawn there; the failure was purely the missing credential.)*

## Claude credentials move to plugin userConfig (2026-07-21)

Field debugging of a Claude Desktop session proved the session-env credential channel structurally broken on GUI launches: the Dock-launched app carries no shell environment, so the spawned workshop sent unauthenticated requests to the default prod URL and surfaced the API's 401 as "check `PIPELEX_API_KEY`" — with a perfectly valid key sitting in the user's `~/.zshenv`. (Notably, the spawn itself worked: `npx` resolved and the MCP server connected; only the credential was missing.) The fix uses the plugin `userConfig` mechanism from the Claude Code plugins reference — the one channel a *shared literal artifact* has for a per-user secret:

- **The Claude manifest declares `userConfig`** (`api_key` sensitive + `base_url`), generated from the `[vars.mcp_server.user_config]` tables in `targets/defaults.toml`. Claude prompts for the values when the plugin is enabled; sensitive values go to the OS keychain, never `settings.json`.
- **The MCP entry spawns the `launch-pipelex-mcp.sh` wrapper, not the workshop directly.** `${user_config.*}` values are injected as `PIPELEX_PLUGIN_<KEY>` (option `foo` → `PIPELEX_PLUGIN_FOO`), and the wrapper promotes each to its real `PIPELEX_<KEY>` name **only when non-empty** before `exec`-ing the workshop, so an unfilled option leaves a shell-inherited value intact.

  **The non-empty guard is load-bearing — do not remove it again.** It was dropped on 2026-07-21 (0.3.1) as "needless indirection", on the reasoning that the workshop already treats empty strings as absent (`PIPELEX_BASE_URL || DEFAULT_API_URL`, `PIPELEX_API_KEY || undefined` in `shared.ts`) and therefore an empty option would "degrade to the keyless fail-open posture rather than to a broken credential". The premise is true and the conclusion is false, which regressed the exact bug 0.3.0 had just fixed. An absent key does not mean no request — it means an *unauthenticated* request, which the API answers with 401. Fail-open is a property of the **hook** (it skips validation and passes), never of the **MCP tools**: they surface it as a `config`-class `PIPELEX_API_KEY — Unauthorized`, and every MCP-backed skill's stop-on-`config` discipline turns that into a hard stop. So an empty option does not degrade gracefully — it shadows a working shell credential and bricks `pipelex-design`, `pipelex-organize`, `pipelex-edit`, and `pipelex-inputs` with a misleading error.

  Reproduced and re-verified when restoring the wrapper: with the options empty and a valid key exported in the shell, the direct-injection shape returns `Unauthorized` while the wrapper shape returns a normal `ok` verdict; with an option set, it still overrides the shell value (a plugin `base_url` of prod against a shell dev key correctly yields `Forbidden`). Both directions matter — the override is what makes Claude Desktop work at all.
- **The hook wrapper reads `CLAUDE_PLUGIN_OPTION_<KEY>`** (how Claude Code delivers userConfig to hook processes — `${user_config.*}` is rejected in shell-form hook commands) with the same non-empty-promotion and the same precedence.
- **`api_key` is not `required`.** The plugin stays enableable without a key: local lint/format and the no-MCP skills work offline, and the fail-open posture would be violated by a hard gate at enable time. The option descriptions state what a missing key costs.
- **Codex/Vibe unchanged:** Codex keeps `env_vars` name-forwarding (its own mechanism, terminal-hosted); Vibe keeps manual registration. *(Vibe superseded 2026-09-12 — see the next section.)*

## Vibe target bakes the launcher as a config fragment (2026-09-12)

Every plugin target now bakes the workshop launcher, Mistral Vibe included. Vibe has no plugin manifest, so until now its target shipped no declaration and the docs asked users to register the server by hand "if/where supported". Reading the installed Vibe 2.21.0 source settled the mechanics the Dual-MCP flip had left open:

- **Vibe registers MCP servers through `[[mcp_servers]]` tables in `~/.vibe/config.toml`.** A `transport = "stdio"` entry takes `command`, `args` and an `env` table (`vibe/core/config/models.py`, `MCPStdio`). The target therefore renders the launcher from `[vars.mcp_server]` into `pipelex-vibe/mcp/vibe-mcp.toml`, which the user copies into their config exactly as they already copy `hooks/vibe-hooks.toml`. The server keeps the name `pipelex`: Vibe uses the entry's name as the tool prefix, so the tools reach the model as `pipelex_<tool>` (`vibe/core/tools/mcp/tools.py`).
- **The key has to be written into the entry's `env` table.** Vibe hands the entry's `env` to the MCP Python SDK's `stdio_client`, which starts the child from a minimal whitelist (HOME, LOGNAME, PATH, SHELL, TERM, USER) rather than the parent environment, and Vibe expands no variables in its config. Vibe has no equivalent of Claude's `userConfig` or Codex's `env_vars`, so the fragment lists every variable named in `env_vars` with an empty value. The workshop treats an empty value as unset, so an unfilled fragment runs keyless and the MCP-backed skills surface the `config` hint, rather than sending a placeholder key.
- **`startup_timeout_sec` is raised to 60 seconds.** Vibe's default of 10 seconds is shorter than the first-ever `npx` spawn measured for the Dual-MCP flip (about 11 seconds while the npm cache fills), so a fresh machine would otherwise lose the server on its first session.
- **Installing the fragment is two deletions and an append, and every instruction says so.** Vibe's first run writes a default `~/.vibe/config.toml` through `tomli_w.dump(VibeConfig.create_default())` (`vibe/cli/cli.py`, `bootstrap_config_files`), and that default carries `mcp_servers = []`. TOML cannot add a `[[mcp_servers]]` table to an array already written inline (`Cannot mutate immutable namespace ('mcp_servers',)`), so a fragment appended to a fresh config leaves Vibe unable to load it. A second entry named `pipelex`, left over from a hand registration, fails `_validate_mcp_server_uniqueness`, and Vibe exits on either error. The entry goes at the end of the file because a TOML table header claims every plain key below it, so a fragment pasted above `skill_paths` would silently turn that setting into an environment variable of the server. The fragment, the install page (`docs/install.md`) and the skills' stop line all carry these steps, and `tests/unit/test_gen_skill_docs.py` pins the TOML behaviour behind the first.
- **The key is also copied into Vibe's session logs, and the fragment says so.** Session logging is on by default (`SessionLoggingConfig.enabled`), and `vibe/core/session/session_logger.py` writes `base_config.model_dump(mode="json")` into each session's `meta.json`, with MCP `env` values unredacted. The log is written owner-only, so its on-disk exposure matches the config file's; the risk is a log shared for diagnostics. The fragment and the install page tell users to redact the key before sharing one. Keeping the key out of Vibe's configuration altogether needs a credential channel Vibe does not offer today, such as a launcher wrapper that reads a key file or a file-based credential in `@pipelex/mcp`. That is tracked as L-260912-522eec.
- **The validation hook still reads the shell.** Vibe runs hooks through `asyncio.create_subprocess_shell` with no `env` argument (`vibe/core/hooks/executor.py`), so the hook inherits the full environment while the MCP server does not. A Vibe user who wants both needs the key in both places, and the install page says so.
- **Verified through Vibe's own code, not a live chat session.** Vibe 2.21.0's config model validated the rendered fragment, and its stdio discovery path (`list_tools_stdio`, called with the entry's argv and `env` exactly as the registry calls it) spawned `npx -y @pipelex/mcp@latest` and listed the workshop's tools. The user's `~/.vibe/config.toml` was not touched.
- **`scripts/check.py` enforces the fragment** (`check_vibe_target_artifacts`): it must parse as TOML and declare exactly one `pipelex` server over stdio with a command. The MCP-backed skills' Vibe stop line points at the fragment and says where the key goes.

## MCP-unavailable posture for skills (2026-07-14)

Unlike the fail-open hook, the MCP-backed skills **require** their tools to do their job. When the tool is absent from the session (harness didn't connect the plugin MCP server) or a call returns `status: "error"` with class `config` (server unreachable / upstream misconfigured / auth), the skill **stops with a one-line setup instruction** (check the MCP connection via `/mcp`; the plugin manifest must point at a running server; surface the error's `hint`). Never silently skip validation. Related skill-level adaptations are recorded in `TODOS.md` (D3–D6): honest graph surfacing (`available_view_specs`, no `dry_run.html`), no ported CLI-era shared references, the runnable gate replacing strict validation (the MCP always validates leniently), and the whole-bundle `files[]` submission convention.

One refinement (2026-07-16): the stop-posture applies to a skill's **required** tools only. Tools that power a convenience are soft dependencies — `pipelex-inputs`' closing offer-to-run needs the `mthds_run` family, and when those tools are absent the skill finishes without the offer instead of stopping. A skill must state which of its tools are which.

> **Superseded in part (2026-09-21)** — the rule stands, but its example is retired: the `mthds_run` family is no longer any skill's soft dependency. See *The run lifecycle is its own skill*.

## Registered-method ids in skills — only where the target can be remote (2026-07-22)

`pipelex-mcp` 0.6.0/0.7.0 taught `mthds_run`, `mthds_inputs_template`, and `mthds_validate` to take a registered method's catalog id (`mt_…`) as `method_id`, as an alternative to submitted files: a by-id call operates on the method's **current stored content** (methods are not versioned) and requires an API key, since the catalog is org-scoped. With both supplied, files win — except on `mthds_run`, where the files run and `method_id` is recorded as run-history linkage.

Skill adoption follows the target, not the tool surface: **only `pipelex-inputs` gains a by-id mode** (prepare inputs for, and offer to run, a catalog method with no local bundle — the one flow where the method legitimately isn't on disk). The file-based skills (`pipelex-design`, `pipelex-organize`, `pipelex-edit`) stay submitted-files only: their loops validate in-flight local content, where a by-id call would silently check the *stored* method instead of the edit under scrutiny — exactly the wrong verdict. Don't add `method_id` plumbing to a skill whose subject is a local working copy.

## Upload step in `pipelex-inputs`, and the light template stays pinned (2026-07-25)

`pipelex-mcp`'s next release adds **`mthds_prepare_inputs`** and flips **`mthds_inputs_template`'s `explicit` default to `true`**. Two independent decisions follow.

**The prepare step is adopted, as a required step.** `mthds_prepare_inputs` uploads a filled template's file-bearing values to Pipelex storage and rewrites them to `pipelex-storage://` references, so it is exactly the missing piece in `pipelex-inputs`: the skill copies the user's files into `<output_dir>/inputs/` and writes relative paths, which the hosted API can never read. The old `## Offer to run` gate coped by *refusing to offer* whenever a local path was present — a dead end for the skill's own most common output. It is now a real step between assembly and the offer (template → fill → **prepare** → run), required whenever a file-ish value isn't already `http(s)` or `pipelex-storage://`, and skippable when everything is already pass-through. Two consequences worth stating: the tool has **no produced-invalid arm** (an unresolvable closure is a no-verdict `input_domain` error, so the recovery path is `mthds_validate` / `mthds_inputs_template`, which do produce structured diagnostics), and preparation **changes the value shape** — a bare path or URL string at a file position comes back as the canonical content dict `{"url": "…"}`, which is what `inputs.json` holds from then on. *(Superseded 2026-09-21: the run-ready form goes into `inputs.prepared.json` and `inputs.json` is never rewritten — see "The run lifecycle is its own skill" below.)* Only the local-workshop deployment uploads; the plugin only ever declares the workshop, so the skills carry no console branching.

**A storage size rejection is terminal; the skill never works around it.** When an `inputs`-located `mthds_prepare_inputs` error reports that any file-bearing input exceeds the service limit, `pipelex-inputs` surfaces the exact message, hint, affected asset, and provided size/limit, then stops the preparation attempt. It must not compress, optimize, re-encode, resize, downsample, split, truncate, extract, convert, derive, or substitute the asset before or after the call, and a preflight size check cannot be used to do so proactively. The user's original, the copied bundle file, and the local-path `inputs.json` remain unchanged; there is no retry with altered content and no run call or offer. Work resumes only if the user supplies a different acceptable input/reference or the service limit changes. This boundary applies to every file type. It is deliberately separate from an unreadable-path failure, where retrying the exact same bytes with an absolute request path remains valid and does not rewrite `inputs.json`.

**The light shape stays pinned: every skill call passes `explicit: false`.** The flip's rationale (concept identity and canonical content shape visible by default) is real, but it is an *authoring-aid* argument, and the three call sites here don't need the aid: `pipelex-design` and `pipelex-edit` only ever *show* or *key-compare* the template, and `pipelex-inputs` fills it against the strategy tables it already carries. Adopting the envelope would mean rewriting Step 2's example, the value-shapes table, and all four fill strategies for no behavior change — `mthds_prepare_inputs` and `mthds_run` accept both shapes identically. So the flag is pinned, not the prose rewritten. Revisit as its own pass if concept identity turns out to improve synthetic-data quality or structured-input filling; the switch is one argument in three places. **One exception, added 2026-09-06: `pipelex-integrate` passes `explicit: true` on its fallback path** — when the validate verdict carries no `main_pipe` and the user has named the pipe to integrate — because it needs each input's declared concept ref to type a call-site parameter, and the light shape carries values without concepts. On its ordinary path it reads the signature from `structuredContent.main_pipe` and makes no template call at all; the pin stands everywhere else.

## Edit vs design — who owns method modification (2026-07-16)

The CLI-era plugin had `mthds-edit` next to `mthds-build`. The port splits that ground along the **contract line** instead of recreating a monolithic edit skill:

- **`pipelex-edit`** is the modification entry point for contract-preserving work — it owns the natural-language triggers ("change this pipe", "rename this concept"). It handles contract-preserving edits itself (prompts, descriptions, model refs, operator settings, mechanical renames) under a baseline-verdict discipline: whole-bundle `mthds_validate` before and after, never edit on a broken baseline, inputs-refresh check when a rename touches the client-facing template.
- **`pipelex-design`** owns structural and contract changes via its `## Re-entry` section and the `references/re-entry.md` it points at. Re-entry is complexity-adaptive: validate the baseline first, then edit the smallest coherent region directly when its complete shallow graph and propagated contracts can be understood together; use same-contract signatures and re-refinement for nested, uncertain, cross-module, or staged changes. Contract changes still propagate through parent wiring, concept reshapes still include every field-reading consumer, and organization runs only when re-entry leaves a construction-shaped layout. **The skill is model-invocable (changed 2026-09-06; it shipped `disable-model-invocation: true` through 0.5.0).** The original reasoning — a design run is a commitment the user opts into explicitly — turned the routing into a dead end: `pipelex-edit` classified a structural change correctly and could then only *tell* the user to type `/pipelex-design`, discarding the baseline verdict and classification it had just produced and costing a turn for a handoff the user had already asked for. The consent gate that matters is inside the skill, not on its invocation — it announces the captured contract in one line before writing anything, and infers the construction mode rather than asking. So `pipelex-edit` now names the affected pipes and invokes `/pipelex-design` directly, and the design skill's description carries natural-language triggers ("design a method", "create a pipeline", "add a step", "rewire this pipeline") so the model can reach it without a slash command. Removing the flag alone would have been inert: with a purely descriptive description, nothing would ever have triggered it.
- **Why the split:** the routing surface and the methodology have different homes. Both halves auto-trigger from natural phrases, so the split is no longer about invocability — it is that the cheap contract-preserving path must not drag the whole design methodology behind it, and the propagating-change discipline (contract identity, concept shapes, backlog draining) must live in exactly one skill or it drifts. The hook is not a substitute for either: its semantic-validation stage is fail-open (skipped without `PIPELEX_API_KEY`), so `pipelex-edit` always takes the whole-bundle MCP verdict as the authoritative check.

## MCP tool vs skill naming convention (2026-07-16)

Settled with `../pipelex-mcp` before anything ships, while every name is still free to change. The principle: **tools are the contract, skills are the manual** — their names follow their consumers.

- **Tools** (owned by `pipelex-mcp`): `mthds_<stem>`, snake_case — operations on MTHDS-language artifacts. Tool names and descriptions are self-sufficient and never reference the plugin skills, because many consumers (ChatGPT, claude.ai connectors, raw MCP hosts) never see them. Lifecycle families share a stem prefix (`mthds_run`, `mthds_run_status`, `mthds_run_results`) so they sort adjacently in tool lists. A noun-only name must state the artifact it returns — hence the rename `mthds_inputs` → **`mthds_inputs_template`** (2026-07-16, before any deploy). The server key stays `pipelex` (the product brand; the `mthds_` prefix on tools avoids a `pipelex` stutter in flattened names and keeps bare tool names collision-proof across servers). The server-side record is `../pipelex-mcp/SPEC.md` → "Naming Conventions".
- **Skills** (this repo): `pipelex-<stem>`, kebab-case — named after user tasks (product surface, per the brand-boundaries decision above), never 1:1 wrappers of tools. Several skills may use one tool (`pipelex-design` and `pipelex-organize` both call `mthds_validate`); a naming rule that forced skill↔tool symmetry would push toward the wrong granularity.
- **The shared stem is the join key** where a skill is the manual for one tool: `pipelex-inputs` ↔ `mthds_inputs_template`. Skills reference tool names verbatim (frontmatter `allowed-tools`, prose); the dependency is strictly one-way — skills know tools, tools never know skills.

## File synthesis is its own skill (2026-09-02)

`pipelex-inputs` inherited the full synthetic-strategy skeleton from `mthds-inputs`, but two things fell out of the CLI-free rewrite. Image generation vanished entirely — the strategy table sent `native.Image` to "Document Generation fallbacks" and that section covered only PDF, DOCX and XLSX — and the PDF know-how shrank from runnable canvas, Platypus and table recipes to one canvas recipe and a sentence. The old image recipe could not simply come back: it ran a `.mthds` bundle through the CLI, which is against this plugin's posture, and the bundle no longer exists in `pipelex`.

So file synthesis became **`pipelex-synthetic-inputs`**, a skill of its own. `pipelex-inputs` stays the input-preparation flow (template → fill → prepare → run) and delegates whenever a file has to be made; the new skill is also useful alone ("make me a sample invoice PDF"). The four rulings behind it:

- **No AI, and only what renders to standard.** (Superseded in part (2026-09-24): photographs are generated and handwriting is simulated — see "Photographs are generated and handwriting is simulated" under "What the proof lab changed".) Files come from `reportlab`, `Pillow` and `matplotlib` code the agent writes — no image-generation model, no hosted method, no image API. The consequence is a hard boundary: `chart`, `diagram`, `document_scan` and `screenshot` ship, and **`photograph` and `handwritten` do not.** A procedural scene or jittered type is not up to par, and an imitation is worse than a refusal because it lets a method run on the wrong kind of input and report success. The skill says so and asks for the user's own file. Neither format has a public last resort: images never had one by decision, and the PDF one inherited from `mthds-inputs` was dropped when it turned out to have already rotted — the `w3.org` URL answers `300 Multiple Choices` with an HTML page, which the hosted API would have fetched and handed to a method as its document. It was also offered at exactly the wrong moment, since the trigger is a machine that has just failed to reach the network.
- **Permissive packages only.** `reportlab` (BSD), `Pillow` (MIT-CMU), `matplotlib` (PSF-style), `numpy` (BSD), `python-docx` and `openpyxl` (MIT). Out: PyMuPDF (AGPL), anything needing a system binary the user may not have (poppler, cairo, wkhtmltopdf, Ghostscript), anything reaching the network at runtime.
- **Prose recipes, guarded by execution.** The reference files carry complete runnable blocks the agent copies and adapts, rather than shipped generator scripts — the content of a synthetic file differs every time, and a parameterized script would become a JSON DSL for documents. What was missing from the predecessor is the guard, and it is the reason the old image recipe rotted unnoticed: `tests/recipes` extracts every block, runs it, and checks the file's magic bytes, a PDF's page objects and a PNG's declared pixel size. Opt-in (`make test-recipes`), since a cold `uv` cache downloads packages. A router `SKILL.md` plus one reference per format keeps every invocation from paying for every format.
- **The skill owns its environment, and asks before installing a tool.** A ladder run once per invocation: `uv` with ephemeral `--with` packages first; failing that, a venv the skill creates under `${XDG_CACHE_HOME:-$HOME/.cache}/pipelex-plugins/synth-venv` and fills itself. Swapping the runner line is the only difference between the rungs, which `tests/recipes` proves by running real recipes through both. Nothing is installed into the user's project; installing a **tool** (`uv` itself, a system package) always asks first, in every mode, because a package in a cache and a binary on the machine are different commitments. When no rung is reachable the skill stops with the exact missing piece and the command that supplies it — and, called from `pipelex-inputs`, returns no path so that one input is left unfilled with its reason in the report, rather than aborting the whole inputs flow.

## The method reaches the code — `pipelex-integrate` and `pipelex-scaffold` (2026-09-06)

Every skill before these acts on `.mthds` files; none touched the codebase that calls the method, so the plugin stopped helping at the moment a user was happy with a method. Two skills close that gap, decided with Louis on 2026-08-30 (the integrate design's ten boxes) and 2026-09-06, the session that widened the campaign to greenfield projects with four rulings and ruled harness deference into the integrate design as a further box. The designs are `wip/pipelex-integrate/design.md` and `wip/pipelex-integrate/scaffold-design.md`; the tracker is `plan.md` beside them.

- **`pipelex-integrate` writes a complete typed call site, and stops there.** One module per method — an async function typed from the pipe's signature, running through the SDK's self-healing lifecycle call and narrowing `main_stuff` through the generated binder or model — plus exactly one shared helper, the client factory; no tests, routes or UI. The name `pipelex-codegen` was rejected: tools are the contract and skills are the manual, named after user tasks, and codegen is one step of integrating.
- **The write arm is the only arm.** Every `mthds_codegen` call passes `output_dir`; a refused or failed write is a refusal, never a fallback to writing the returned bytes from the conversation — a re-emitted artifact is one trailing newline from a broken stamp. Generated files are never edited, formatted or linted; the tooling exclusions go in before the tree exists, and name the copied drift-gate script beside the generated directory, because a refresh re-copies a script that differs byte for byte from the reference and a reformatted one would be re-copied every time; one directory per method; orphans are reported and never deleted.
- **The signature comes from the verdict.** `mthds_validate`'s `structuredContent.main_pipe` types the call site for every selector. The by-elimination heuristic the first design carried for by-ref and by-id sources was made obsolete by `pipelex-mcp` before it shipped and was never written; an older workshop takes a fallback (the template for inputs, the bundle for the output), and a by-ref or by-id source without a signature stops rather than guessing.
- **The sidecar `sources.json` is the skill's only state** — selector, target, pipe record, the bundle directory (`bundle_dir`) and a hash for every `.mthds` file under it — so refresh mode re-derives nothing and a bundle change is detectable; `pipelex-edit`, `pipelex-design` and a standalone `pipelex-organize` announce staleness from it. The directory is recorded because the hashes alone cannot see an added file: the call site loads every `.mthds` file under its bundle directory, so a file added there changes what runs while every recorded hash still matches. Both gates therefore list `bundle_dir` the way their language's call site lists it and report an unrecorded file as `stale-source`, a sidecar that records sources without the directory fails closed, and refresh mode re-reads the file set from the directory rather than from `method.files`.
- **The drift gate is the same shape in both languages, and never costs a consumer the runtime.** TypeScript gets `references/codegen-check.mjs` over `@pipelex/sdk`'s `runCodegenCheck`; a `python-pydantic` consumer gets `references/codegen_check.py` over `pipelex-sdk`'s `run_codegen_check`, which that SDK carries from 0.10.0 on; each is copied verbatim and wired into the project's existing gate, and the two fail closed on the same malformed sidecars. Neither reads its own failure to run as drift: an SDK that cannot be imported, fails while it loads or predates the check, or a check that throws or raises, is exit `2`, no verdict for that directory, never the `1` a gate acts on, and the directories after it are still checked. Nor can a line the Python script prints fail it: it escapes a character the locale's encoding lacks rather than raising on it. The skill first shipped with no Python gate at all, because the Python SDK then had no offline check and adding the `pipelex` runtime for one would reverse what the target means — that reason still rules out `pipelex codegen check` for a consumer, and the editing skills' staleness notice remains the guard that speaks before CI does.
- **No wire-null helper.** The design carried a schema-guided `wireOutput` helper against the ts-zod `.optional()` defect; the emitter fix (`.nullish()`) shipped in pipelex v0.56.0 before the skill did, and the helper — lossy once the emitter is fixed — is never written.
- **A project that owns a codegen harness keeps it.** A starter-derived project regenerates, checks and scaffolds through its own scripts; the skill defers to them and never writes a second layout beside the first. This is the personas split: the mechanism may move into the SDK, the policy stays with the consumer.
- **`pipelex-scaffold` is the front door, with two branches and no templates of its own.** A project comes from one of the two GitHub-template starters, run through the clone's own `bootstrap` skill (read from its `SKILL.md`, never reimplemented here), or from the ecosystem's initializer when the user wants their framework. Cookiecutter and copier were rejected: the starters are living apps with CI and end-to-end tests that a Jinja-ified template could not keep, and the rename is already a deterministic script with a dry run. The skill acquires with a fresh-history local clone by default (what the template button produces) or `gh repo create --template` after confirmation, makes exactly one commit — the pristine template, so the Python bootstrap's `git mv` works and the rename is a reviewable diff — fills the key only from the shell environment, adds no SDK dependency, and is the plugin's third MCP-free skill. Whether a CLI front door for non-agent users is still wanted is a separate open decision in the workspace ledger. (Superseded on 2026-09-23: the starters left the skill; see "`pipelex-scaffold` drops the starters and runs its initializer branch through scripts" below.)
- **Two skills, not one.** The integrate design is large and the trigger families differ ("use this method in my app" against "start a new project"); the greenfield tail is integrate anyway, so the hand-off chain is the plugin's existing pattern.
- **References carry the language detail, and two of them are scripts.** `pipelex-integrate` ships `typescript.md`, `python.md`, `codegen-check.mjs` and `codegen_check.py` — the gate scripts, copied byte for byte into every target and then into users' TypeScript and Python projects, so a change to either is verified by running it, not by rendering it; `pipelex-scaffold` ships `starters.md` and `initializers.md`. (Superseded on 2026-09-23: `starters.md` was deleted with the starters; see "`pipelex-scaffold` drops the starters and runs its initializer branch through scripts" below.)

## What the integrate and scaffold dogfood changed (2026-09-12)

Both skills were run as cold headless sessions against a local `pipelex-mcp` build of `dev`, in scratch projects and in scratch copies of both starters. The rules below are what those runs changed; the scenarios and their verdicts are in `wip/pipelex-integrate/plan.md`, and the designs carry the same amendments.

- **The validate verdict's `main_pipe` is absent for three reasons, and the skill asserts none of them.** The entry pipe is the API's `default_pipe_ref` — for a published package, its `METHODS.toml` entry rather than the bundle's own declaration, which is why the call site is typed and run against `main_pipe.pipe_ref`. The signature is omitted whole when nothing settles an entry pipe, when the pipe's contract does not narrow, or when the workshop predates the signature. The skill named only the first and the third, and told a by-ref or by-id source to blame an old workshop.
- **An occupied generated directory is refused even when the user names it.** Every method of a target emits the same file names, so generating a second method into another method's directory overwrites it and reports an empty `orphans[]` — a clean-looking generation. The guard is the sidecar: a directory is this method's only when a `sources.json` there names it, a lock with no sidecar included.
- **Containment is read before the first write, not after an error.** A path inside the workshop's working directory is legal wherever it points, so a harness launched beside the project accepts a write into the wrong tree; a run that hit this moved the tree across afterwards and left the project with a refresh that fails the same way every time. The skill now reads the path from the workshop's working directory first, and never moves a tree into place.
- **A file the skill does not own is never cleared, and never offered for clearing.** Integrate met a hand-written file at an artifact path and offered to delete it; scaffold met a non-empty target directory and offered to move its contents aside and merge them back. The answer in both cases is another directory.
- **A directory holding nothing but `.git` reads as empty; everything else still refuses.** (Ruled 2026-09-13, `L-260912-724b71`.) The non-empty refusal treated any existing entry as occupancy, which made the skill refuse a state it produces itself: `mkdir my-app && cd my-app && git init` is an ordinary way to arrive, branch B runs `git init -b main` in the directory it is working in one step later, and `references/initializers.md` already documents `uv init --package --no-workspace .` for the empty-"here" case. A lone `.git` is now read as empty. **The cruft list was declined in the same ruling** — `.DS_Store`, `.idea/`, `.vscode/` and `Thumbs.db` go on refusing until a real report names one — because a list that grows by guesswork is how this rule drifts back into the agent judging which of a user's files matter, which is the thing the refusal exists to forbid; so the exception is written as one directory entry by name and never as a predicate over ignorable files. The separate rule that the skill never *offers* to clear anything is untouched: a directory read as empty is never cleared either way.
- **Branch A acquires beside a directory that already holds a repository, so the lone-`.git` exception means one thing on both branches.** (Ruled 2026-09-13, `L-260913-f28d9d`.) The ruling above is implementable on the initializer branch, where `uv init` accepts such a directory, and unimplementable on the starter branch, whose first command on the chosen directory is `git clone` — which refuses any destination already holding a `.git`. The skill therefore admitted a directory it could not populate, and the founder's own motivating case dead-ended for anyone who wanted the opinionated starter rather than the initializer. **Scoping the allowance to the initializer branch was rejected**: the exception exists because `mkdir my-app && cd my-app && git init` is an ordinary way to arrive, which is not specific to initializers, so that user has exactly the same claim on the starter and would have met the refusal the exception was written to remove. Branch A now clones into a `mktemp` path beside the directory, discards the template's history there, re-reads the directory and copies the template in. The properties that make it safe are executed rather than asserted, in `tests/unit/test_pipelex_scaffold_skill.py`: **no `rm -rf` ever addresses a path under the chosen directory**, because the discard is spent on the temporary path before anything moves; **`cp -R "$tmp"/. "$dir"/` carries the entries beginning with a dot**, which `mv "$tmp"/*` drops while exiting `0`; and **the `ls -A` line admits exactly one entry**, `.git`, which the clone no longer has, so a collision is impossible rather than unlikely and anything else stops the run with nothing copied. The end state is the one the default recipe reaches — the template in place, no template history, no Pipelex remote — reached by a different route, and nothing is initialised because the repository is already the user's. **The destination is resolved to an absolute path before the temporary path is derived from it** (added in review round 2): the chosen directory is usually spelled `.`, since the user is standing in the directory they just `git init`-ed, and `dirname .` is `.` — so deriving the sibling from the spelling made the temporary directory a *child*, which the `ls -A` line then saw beside `.git` and refused. The recipe served every shape except the one the ruling was written for, and every recipe test bound `<dir>` to an absolute path, which is why it took an execution test spelled `.` to show it.
- **A runtime behind a version manager is not a missing toolchain.** Scaffold, on a `PATH` without `node`, found the machine's `nvm` and carried on — which installs nothing and is the useful answer. It now checks `nvm`, `fnm`, `volta`, `asdf` and `mise`, says which it used, and stops only when no runtime can be reached.
- **One upstream defect is named rather than worked around.** The `ts-zod` emitter writes `binder.ts`'s sibling import with no file extension, which a plain Node ESM project rejects at type-check and at runtime while a bundler resolution accepts — which is why the JS starter never met it. Filed as `L-260912-857a5a` against `pipelex`. The tree is stamped and hashed, so the skill reports it, never patches the file, never drops the tree from the type checker, and leaves a change of `moduleResolution` to the user.

## Orphans alone do not end the run — `orphans[]` non-empty with `drifts[]` empty (2026-09-13)

After writing a tree, `mthds_codegen` reports *orphans*: stamped files already in the destination that the new lock does not list. The skill said to report them and "do nothing else", which reads both as restraint toward the files and as an instruction to abandon the run, and the two readings leave different trees on disk — so the question went to Louis as `L-260912-3d5693` rather than being settled by a reviewer's preference.

**The ruling is the condition, not the verdict.** The run continues when **`orphans[]` is non-empty and `drifts[]` is empty**, read off those two fields directly and never inferred from `is_current`. Reading them carries one asymmetry of the tool contract with it: `orphans` is always present and empty when clean, while `drifts` is **present only when non-empty** (`pipelex-mcp/SPEC.md` → `drifts?: unknown[]; // present when non-empty`, and the same words on the field in `pipelex-mcp/src/capabilities/codegen.ts`). So in the continuing case there is no `drifts` in the payload at all, and its absence *is* the empty case — which the skill states in every place the branch appears, because a branch phrased on a field state the payload never presents is the mistake the first implementation already made once with `is_current`. That is exactly the case where the tree is non-current only because a previous generation left files behind, which is the benign cause: an earlier generation of this method, a target switch, an engine version that renamed an artifact. The skill goes on to write the sidecar, add the dependencies and write the call site, and it never deletes an orphan. **Anything that also drifted still ends the run**, because a non-orphan drift is the write itself being broken.

**The asymmetry with the stopping branch is conditional, and the condition is what makes it legible.** The check disowns *both* trees — `is_current` is `false` on each — so nothing about ownership distinguishes them. What distinguishes them is the empty `drifts[]`, stated in every place the branch appears, which is also why one non-orphan drift beside the orphans puts the result back on the stopping branch. The report says what the signal means — the directory holds artifacts this generation does not list, named by path, none deleted, a dedicated directory per generation as the fix, detection declared partial whenever `orphans_truncated: true` — and adds that the gate installed in step 10 counts every orphan as a drift, so that check stays red on the directory until it holds one generation and deleting an orphan to turn it green is forbidden — qualified by the project having the step-10 gate, since a project that owns a codegen harness skips step 10 for its own check. The qualification was first written for the `python-pydantic` consumer, for whom step 10 then installed no gate at all; that consumer has one now, in the same shape as TypeScript's, and the claim covers it.

**This replaces a first ruling of the same day, which was made on two premises a review then proved false.** Both are worth recording, because the first ruling was reasonable given them and unimplementable without them.

- **There is no "success with a non-empty `orphans[]`" state distinct from `is_current: false`.** Orphans force the verdict non-current: `pipelex-mcp/src/capabilities/codegen.ts:205` describes `is_current` as "False when the directory also holds orphans", `pipelex-mcp/SPEC.md:399` states the consequence as "a directory holding more than one generation stays non-current by design", and `drifts` at `codegen.ts:223` is "every check drift that is NOT an orphan". This skill already said so twice — its never-bend rule reads orphans as permanently non-current by design, and its step-6 success gate admits a written tree only on `is_current: true` with an empty `orphans[]`. So the first ruling's continue branch had no gate that reached it, its stopping neighbour matched every orphans result, and the continue branch's own justification ("the check says the tree is current") is the sentence an agent would read to choose — finding `false`, and stopping.
- **The overwrite hazard reports an *empty* `orphans[]`.** The first ruling made the loud report the whole protection against another method's same-named files having been overwritten by the write that just succeeded. Step 4 of this same skill says the opposite: every method of a target emits the same file names, so generating into a shared directory silently overwrites the other method's stamped files *rather than reporting an orphan*. Orphans therefore appear only where the prior tree held files the new generation does not emit, which is precisely where nothing of another method's was clobbered. The protection was bolted to the one signal that cannot indicate the danger, and the real guard was always step 4's refusal of a directory holding a `codegen.lock` that no sidecar names this method for.

**Two options not taken, in the order they become the way back.** Changing `pipelex-mcp` to report success-with-orphans when nothing else drifted would fix the conflation at its source rather than reading around it, but it spans the capability code, the `SPEC.md` tool contract other consumers read, and then this skill — so it is the answer if reading the two fields here proves insufficient. Branching on whether the orphan set resembles another method's complete current generation was judged most correct and most expensive when the decision was first framed, and the second premise above retires it: the hazardous case carries no signal at all, so no reasoning over the orphan set can detect it.

## The scaffold's env file takes the base URL from the shell (2026-09-13)

`pipelex-scaffold` filled `PIPELEX_API_KEY` from the shell and left `PIPELEX_BASE_URL` at the example's `https://api.pipelex.com`. A key is refused by every plane but the one that issued it — the same fact that made Codex forward both variables by name — so a shell exporting a dev or staging pair got an env file pairing that plane's key with production's URL. The session worked, because the SDK reads the process environment, and the project broke the first time something read the file instead. It was seen in the codegen sprint's acceptance walkthrough against the dev plane.

- **Whenever the skill writes the env file, a base URL the shell sets is copied, with a key or without one.** (The developer's ruling of 2026-09-13.) A base URL the shell exports is the plane the user has declared, and a keyless self-hosted runner — which the Python starter's `.env.example` documents at `http://127.0.0.1:8081` — is a plane too; a first version copied the URL only beside a key, which pointed exactly that project at production. The key is still copied only when the shell sets it, a shell that sets neither leaves the example as it came, and a file that already carried the user's key keeps both of its lines untouched.
- **One test on the file's key decides whether anything is written, in one command.** The example ships its URL line non-empty, so the URL cannot carry a presence guard of its own, and the key's guard repeated as a second command could find the key the first just wrote. A second test on the two variables together stops a shell that sets neither from appending even the comment, so the leading newline and the comment go out once, whichever line follows them. ## Skill bodies carry no argument placeholders (2026-09-17)

Claude Code rewrites a skill body before the model reads it. Read from the 2.1.273 bundle, the rule is this: `$ARGUMENTS` is always replaced, by nothing when the skill was invoked without arguments; `$ARGUMENTS[N]` and `$N` are replaced by the N-th whitespace-separated word of the arguments, counting from zero, when there are that many words, and are left as written otherwise; and a backslash before one of these tokens is removed, leaving the token as written. Reference files are not rewritten, because the model reads them with a tool. `pipelex-scaffold`'s dev-server block carried `"$1"` in its process-tree helper and `print $9` in the `awk` that read `lsof`'s address column. The second dogfood reading invoked the skill with a sentence as its arguments and received `kill -STOP "me"` and `print The`. As delivered, that block would have treated a server listening only on loopback as reachable from the network, stopped it and reported no URL.

- **The fix removes the tokens instead of escaping them.** A backslash escape works in Claude Code, but Codex and Vibe show the template text unchanged, so their shells would read the backslash as part of the command. The process-tree helper now loops over its arguments with `local p; for p; do … done`. The `local` is required: without it, the helper's recursive calls reuse the same `p`, so each outer call signals the last process its recursive call visited instead of its own, which leaves every stopped parent suspended. The listener's address is now read with `lsof -Fn`, not by column number: `lsof` prints the socket state `(LISTEN)` after the address, so `$NF` would read the state and not the address.
- **`make check` fails when any target's rendered `SKILL.md` contains `$ARGUMENTS` or a `$` followed by a digit** (`check_skill_argument_placeholders` in `scripts/check.py`). The check is stricter than Claude Code: it also flags `$1x` and a `$N` that the invocation has too few words to fill, so it does not depend on either detail of the current rule. `${1}` is not substituted and does not fail the check. A skill that declares named arguments in its frontmatter would also have `$<name>` substituted. No skill here declares any, so the first one that does must check its own body for those names.

## The run lifecycle is its own skill — `pipelex-run` (2026-09-21)

`pipelex-inputs` had grown a second job: it prepared inputs *and* ran the method. The run is now its own MCP-backed skill, and the boundary between them is where the inputs become run-ready.

The catalog skill therefore says so rather than routing a user who asks to publish at a skill that would ask them for the address instead.
- **The skill writes nothing to disk.** The pulled sources and the `pipelex-method.json` link are written by the workshop, which is the only party that knows which API host it talks to — that is what makes an unknown id diagnosable later, since the link records the host it was made against. The `allowed-tools` field pre-approves and does not restrict, so leaving `Write` and `Edit` off buys nothing while a bare `Bash` is listed — `cat > pipelex-method.json` writes as readily as either. The skill therefore pre-approves the readers and `Bash(git status:*)` alone, the one command it runs unprompted: any other write, hand-written link file included, stops for the user instead of recording the wrong plane. The one thing it ever removes is a dead link, and only after asking, because the workshop refuses a create into a directory another link claims rather than minting a duplicate nobody can delete.
- **It never validates on the way to a save.** `mthds_save_method` reads the files, validates them and stores those same bytes in one call, precisely so the saved bytes are provably the validated ones. A skill that took its own verdict first would read the files twice and pay for it twice, and the second read could differ from the first. `mthds_validate` stays declared for the one question the save cannot answer without doing it — *would this save?* — and for nothing else.
- **Which `.py` files are the method's is the skill's judgement.** The workshop gates on the `.py` extension and on the file really living under the bundle directory, and nothing else, so a sweep of the directory would upload whatever Python happens to sit beside the bundle to the organization's catalog, where nothing validates it. The rule is therefore a judgement read from the bundle's own Python, because a `function_name` names no file — it is a key in the runtime's flat, process-wide function registry, by default the decorated function's own name — so the set is the file defining each registered function plus the bundle files it imports, sent together since `python` replaces rather than merges. Send nothing at all when the bundle holds no `PipeFunc` — which preserves the stored set and cannot erase anything — and ask rather than guess. `python: []`, the one form that clears stored Python, is sent only when the user has asked for that.
- **A conflict and an ambiguous pull both stop and ask; neither is decided here.** The link records no source hashes, deliberately (box R, amended at ratification to the minimal link). The cost is stated rather than hidden: a pull into a linked directory whose files differ *after* the saved method moved cannot tell whose change it is looking at, so it asks before overwriting, and inside a git repository `git status` answers the question for the user. A save refused on `expected_updated_at` gives both timestamps and two ways forward — a comparison copy in a new sibling directory, or an overwrite on an explicit yes — and picks neither. The precondition is best-effort by construction, since the platform accepts no compare-and-swap; the skill says so when the user is choosing the overwrite.
- **A create is not retried, and delete is not offered.** `POST /v1/methods` honours an idempotency key that `@pipelex/sdk` cannot send yet, so a retry whose first response was lost mints a second method — and deletion is admin-only on the platform and erases every run the method produced, so there is nothing that could remove it. The skill lists the catalog instead of retrying, and names the Pipelex webapp when asked to delete.

## A catalog id is a target in every skill (2026-09-22)

Box H of `wip/plugin-skills-gaps/design.md`, with box A step 5, box F.4 and box R's notice. A registered method's `mt_…` id was a target in `pipelex-inputs` and `pipelex-integrate` alone; it is now one everywhere, reached natively where the work is remote and through a directory where the work is on files.

- **`pipelex-design`, `pipelex-edit` and `pipelex-organize` stay file-based, and a bridge is what an id means there.** They write `.mthds` files, so there is nothing for them to act on until a directory exists: one `grep -rl '<id>' --include=pipelex-method.json .` finds the directory already linked to that method, and where there is none the pull is `/pipelex-catalog`'s. The bridge is one shared include for the three, because the gesture is identical and only the step it resumes at differs. Two things it deliberately refuses to do: **pick between two hits**, since `/pipelex-catalog`'s own conflict path creates a second directory carrying the same link — a comparison copy, meant for reading — and **present the local files as the saved method's current content**, since the link records no hashes and the two can differ in either direction.
- **A published address is not a target for those three.** Nothing of it is on disk and there is nowhere to write a change back, so the bridge says so and points at `/pipelex-explain`. Cloning the repository to get its source was rejected in box F for a reason that holds here too: it would re-implement the runner's package resolution in a skill, and the two could disagree about which package an address names.
- **The save is never the tail of an edit.** Design, edit and organize end their report with a notice — a second shared include, beside the stale-types one — naming the linked method and saying that the catalog still holds what it held before. It offers `/pipelex-catalog` and does not call it: a save is a deployment, and the three skills that have just written files are exactly where an autonomous one would creep in. The two notices are separate includes rather than variants of one, because they answer different questions from different evidence — a sidecar beside a generated tree elsewhere in the project, against the link file in this directory.
- **A run of a linked directory is filed under its method, and that is all the id does.** `files` + `method_id` is the one legal selector pair, and it means the files run while the id is recorded on the platform's Run row — the same thing the webapp does with its editor's unsaved buffer. So `pipelex-run` reads the link and sends the id, says which method the run was filed under, and says plainly that the filing does not mean the saved method ran.
- **A linked run carries no stored Python, which is a fact about `PipeFunc` and not about linkage.** Verified in `pipelex-server`: a caller-supplied source takes precedence and the stored method is resolved only when no source was sent at all, so the assembled `.mthds` + `.py` run bundle is reached on the id-only path alone (`platform/src/pipelex_platform/routers/v1/execution.py`, `services/method_resolution.py`). Since a `files` submission carries `.mthds` only, a bundle whose `PipeFunc` names a function the plane does not already have registered has **no channel for its Python on any files run**. `pipelex-run` states that as the cause of such a failure rather than offering the `PipeFunc` as one suspect among several, and names the save-and-run-by-id path as the cure.
- **An unknown linkage id is read off its location, and the reason is written down.** On a mixed run the workshop's classification splits the locations deliberately: a rejected payload and a refused execution locus land at `files`, and only the unknown-method arm lands at `method_id`. That is the opposite of `mthds_save_method`, where one location carries several causes and the message has to be read — so the skill states *why* the location is enough here, rather than leaving an agent to carry either rule to the other place. The run is refused before anything executes, so nothing is spent, and the offer is the same run without the id.
- **`pipelex-explain` reads a saved method's source in full.** Box F.4's caveat — an id explained at contract level "until the release that carries `mthds_get_method`" — is spent: the tool shipped in `@pipelex/mcp` 0.16.0. An id names the user's own organization's method, so explaining it means reading it, through the **inline** arm with no `output_dir`. That split is what lets a strictly read-only skill hold a tool whose other arm writes a pull to disk, and it is the only guard that matters here. Three properties of the returned set are stated because each would otherwise be misread: the read is bounded, so a `truncated` answer makes the explanation partial rather than the library incomplete; the stored Python comes back, which is the one reading where a `PipeFunc`'s defining file can actually be named; and a method saved before the webapp's editor existed arrives as one unnamed file. `mthds_get_method` is the local workshop's alone, so on the hosted console an id falls back to contract level — a narrower explanation, never a stop, which is explain's posture throughout.
- **Design still does not search the catalog before it designs** (ruling 4). The bridge resolves an id the user supplied; it never goes looking for a method that might already exist.

## A skill fits in what a compaction keeps, its branches read on demand (2026-09-23)

The size diet (`wip/skill-size-diet/`, design ratified 2026-09-23) reshapes how every skill is written. Its rulings, and the reasons that belong here rather than in a shipped skill:

- **The read-before-act rule** decides where each sentence lives, by what happens if the model never reads it: a guard stays in `SKILL.md` once, a branch moves behind a pointer at its condition, a stop is a table row, rationale comes here. A caveat moves only when its need announces itself — a condition visible before acting, or a result that says so after a harmless act — because a caveat moved to a reference is a caveat that may not be read. `docs/build-targets.md`, "The size of a skill", states the rule and the shape for whoever writes the next skill.
- **The ceiling is 13,000 characters, counted on the rendered file.** Claude Code keeps an invoked skill whole after a compaction only while it fits 5,000 tokens (25,000 across skills), and carries a longer one forward as its head. Measured with the token-counting endpoint, the Claude 5 tokenizer runs 2.77 to 3.12 characters per token over the rendered skills, so the design's proposed 16,000 would have been about 5,780 tokens; 13,000 is 5,000 tokens at 2.77 less a margin. Claude Code 2.1.280 itself estimates those tokens as characters divided by four, keeping about 19,900 characters, so the ceiling holds under either reading. Codex and Vibe keep no skill body across a compaction at any size, so the ceiling is Claude's, and a smaller skill is what every harness re-reads. The check reported until the diet's last phase, and has failed since. The evidence is `wip/skill-size-diet/facts.md`.
- **The requirements block is its two stops.** What to tell the user when the workshop is absent, and where its key comes from, is a paragraph per harness that a model needs only when one of those stops fires, so it lives in `shared/credentials.md`, rendered per target, and each skill's stop points there. The stop itself stays in every skill.
- **The `runs/` exclusion is part of the submission convention**, stated once in `validate-call.md.j2`, so design, edit, organize, explain and inputs no longer submit a run's saved `.mthds` artifacts as method source. `pipelex-integrate` opts out with `validate_call_file_set = false`: the set it submits is the set its generated call site loads, which is the call site's to define.
- **The stale-types notice has one wording.** Its three call sites said the same thing about the same evidence and differed only in which change they named; the organize wording's explanation of why an equivalent layout still stales a tree is this sentence: a reorganization rewrites, moves and removes the very files a sidecar hashed.
- **The project's markers are one include**, `project-root.md.j2`, so design, integrate and catalog cannot disagree about where a project starts — integrate's list had drifted to "above the working area" while design said "at or above the working directory".
- **The skill-directory variable arrived with `pipelex-integrate`'s phase.** Claude substitutes `${CLAUDE_SKILL_DIR}` in a skill body; Codex and Vibe substitute nothing but tell the model the directory a loaded `SKILL.md` lives in. So `skill_dir` renders as `${CLAUDE_SKILL_DIR}` on Claude and as a `<skill-dir>` placeholder on the other two, defined in one sentence by the `skill-dir.md.j2` partial, and a script is run by its absolute path, from the user's project, through its interpreter — because on Codex and Vibe the model otherwise runs it from inside the skill's directory. It was held back until a skill named a script or a verbatim copy, since a template variable nothing reads is a dead switch; integrate's copy of its gate scripts was the first, and it is now a literal `cp` from `{{ skill_dir }}/references/`, because Vibe had performed that copy by reading the file and writing it back.
- **Links are checked both ways, and references are one level deep.** A pointer to nothing sends the model to a read that fails, and a file nothing names is a caveat no model reads; a reference reached only through another reference counts as named by nothing, since one read must be enough to take a branch.

## `pipelex-integrate`'s rationale, moved out of the skill (2026-09-23)

The size diet's second phase rewrote `pipelex-integrate` in the read-before-act shape: its main path, guards and stop table in `SKILL.md`, and its branches in references read on their condition — refresh mode, the harness branch, the signature fallback, the report on orphans and the gate failures — with the list-output narrowing code and the account of what a run's results carry in the language references. The skill used to ship the reason for each rule beside the rule. Most of those reasons were already recorded above, under "The method reaches the code", "What the integrate and scaffold dogfood changed", "Orphans alone do not end the run" and "A published address without a tag is accepted, never refused", and the skill now ships none of them; what follows is the rest. The paragraph-by-paragraph account of the move is `wip/skill-size-diet/classification-integrate.md`.

- **Containment is read at step 1, and with both sides resolved.** The workshop's working directory is the directory the harness was launched in — the host spawns the server there and the launcher does not `cd` — so a project is writable only at or below it. A lexical reading is wrong in both directions: a symlink inside the workshop pointing at a project outside it reads as contained, and on macOS a project under `/tmp` or `/var` reads as outside when the workshop's `process.cwd()` is the `/private/...` form of the same place. Both inputs are known as soon as step 1 names the project, which is why the check sits there: by step 6 a bundle may already have been copied in, a `git mv` staged and the exclusions written, none of which is the skill's to revert — so a containment refusal met that late says what is already on disk.
- **A bundle outside the project is copied in** because the call site loads it at runtime, and its sources must be versioned with the code that loads them.
- **A lock with no sidecar can be this method's own.** The lock is written at step 6 and the sidecar at step 7, so every stop between them — a non-current result step 6 does not let through, a partial write whose retry also failed — leaves exactly that state for the method being integrated. Relocating it would leave two trees for one method, which is the fragmentation step 4's rule exists to prevent, so the interrupted run is regenerated in place and given its sidecar.
- **The run's `pipe_code` is the bare code, and nothing catches a confusion.** The verdict and the sidecar carry the namespaced `pipe_ref`; the run route takes the code alone. A namespaced `pipe_code` type-checks and passes the offline gate, and fails only when the method is actually run, which neither gate does — the half-sentence the skill keeps, because a model would otherwise "tidy" the code into the ref. *(Superseded 2026-09-24: the run's `pipe_code` is the qualified `pipe_ref`, and it is the bare code that fails on a real run — see "The run's `pipe_code` is qualified, the same value as `pipe_ref`" below.)*
- **The helper budget is one, and reads as the whole budget.** It was two while the wire-output helper was the second; that helper was struck for being lossy (see "No wire-null helper" above), so "exactly one" is stated so that no reader takes it as a floor.
- **The floors step 8 installs** carry their meaning — the first release with everything the call site and the gate use, and the Python starter's own pin — in the comments of `[vars.floors]` in `targets/defaults.toml`; the skill states the number and leaves the reason there.
- **A 403 on `mthds_codegen` is a feature gate**: its hint says code generation is not enabled for the organization on the hosted API, and the shared `config` stop surfaces that hint verbatim, the plan-limit (`paywall`) hint included, so the skill says only that a 403 is not a key problem.
- **The orphans are one account, in one reference.** The skill stated what to do with them in its rules, step 6, step 11, step 12, refresh mode and its failure table, and several open ledger items are about that logic. The condition the run continues on is now stated once, at step 6; refresh mode branches as step 6 does, the stop table names step 6's case, and what the report says lives in `references/orphans.md`. The ruling itself is unchanged.
- **A `stale-source` file is never hashed by hand.** Adding its hash to `sources` turns the gate green over types that do not cover the file, because the types were generated before it existed; only a refresh, which regenerates from the re-read file set, may record it.
- **Exit `2` is not one case.** Both gates exit `2` when they cannot reach a verdict, and most causes lie outside the tree — an SDK the command cannot import, a check that threw — where regenerating clears nothing. A missing or malformed lock is the tree's own state, and there regenerating through the skill is the cure, so the gate-failures reference says which is which row by row rather than forbidding regeneration for every exit `2`.
- **A gate script is the skill's only when it says so.** Step 10 copies its gate into `scripts/` under a generic name, and a refresh re-copies one that differs from the reference; a project can already keep its own file there — `pipelex-starter-python` ships a different `scripts/codegen_check.py` — and `cp` replaces it without a word, unrecoverably when it was never committed. Both shipped scripts open with the line `Copied verbatim into a project by /pipelex-integrate`, so the copy and the re-copy go ahead over a file carrying it and ask over one that does not.
- **Neither script candidate became a script.** Box E of the size diet ships a procedure as a script when its text is its correctness. The containment check is two path resolutions and a comparison, one of whose inputs — the directory the session was launched in — is known to the model and not to a script run from the project; the tool refuses a climbing `output_dir` itself, and the one silent case left, a symlink, is what "compare the resolved paths" answers. The sidecar's hashes are checked by the very gate step 10 installs and step 11 runs, which reports a wrong or missing hash, or a file left out, as `stale-source` before the report is written; on a `python-structures` project, whose `pipelex codegen check` reads the tree alone, a wrong hash only makes the next refresh say the bundle changed, and that refresh regenerates anyway. Either becomes a candidate again if a smoke session shows a model getting it wrong.

## `pipelex-inputs`'s rationale, moved out of the skill (2026-09-23)

The size diet's third phase rewrote `pipelex-inputs` in the read-before-act shape: its target forms, template call, strategy choice, the path rule of `inputs.json`, the core of preparation and the conditions for offering a run in `SKILL.md`, with a stop table; and its branches in references read on their condition — the Synthetic and User data strategies with their worked examples, a published address, and the errors preparation returns. Most of the reasons the skill shipped were already recorded above, under "Upload step in `pipelex-inputs`", "File synthesis is its own skill", "The run lifecycle is its own skill" and "A published address without a tag is accepted, never refused", and the skill now ships none of them. The first of those predates the prepared file: where it says the prepared shape is what `inputs.json` holds, "The run lifecycle is its own skill" supersedes it, and preparation writes `inputs.prepared.json` beside an unchanged `inputs.json`. What follows is the rest. The paragraph-by-paragraph account of the move is `wip/skill-size-diet/classification-inputs.md`.

- **The user hears what leaves the machine before it leaves, even in automatic mode.** Preparation is the one point where the user's own files go to remote storage. Automatic mode states it and proceeds, because the user asked for run-ready inputs and this is what makes them run-ready; interactive mode waits for a yes. Either way the user learns which files are involved while they can still say no, swap a file or drop one, which a report written after the upload cannot offer.
- **Prepare takes the template call's `pipe_ref`.** The pipe's declared signature is what tells the tool which values are assets, so a prepare call that falls back to `main_pipe` after a template call that named another pipe inspects the wrong contract, and nothing reports it. The skill keeps a half-sentence of this, because a model would otherwise plausibly drop an argument that looks optional.
- **The prepared file is a plain inputs object** — the same keys, no envelope, no hash, no sidecar — so anything that accepts inputs accepts it as it stands. The copies under `<output_dir>/inputs/` stay where they are: they are the user's own reference, `/pipelex-run` reads their timestamps to decide whether the prepared file is still current, and the uploaded bytes no longer depend on them. A `pipelex-storage://` reference passes through both prepare and run unchanged, so the prepared file stays runnable until the sources it was made from move on.
- **Step 5 deletes an earlier `inputs.prepared.json` before it prepares** (decided by the second review of this rewrite, over a gap that predates it). A preparation that is skipped, declined or failed writes no prepared file, and one an earlier pass left behind would still be read. `/pipelex-run` judges a prepared file current by comparing its non-file values and its timestamps: after a pass that skipped preparation, the newer `inputs.json` makes the old file not current, so the run skill hands back here without anything having changed. After a failed re-preparation over a file moved into place with its old timestamp, the old file still looks current and its storage references run. Deleting it first means the only prepared file on disk is the one this pass wrote. The Template strategy is the exception (the third review): it prepares nothing and saves placeholders, so the prepared file may be the last run-ready copy of the values it just replaced, and it is left alone.
- **A list input's files live in a directory named after the input** (the third review). Indexing a list's files by the input's name (`photo_1.png`) or keeping their own names in the flat `inputs/` directory both let a list item take the file name of another input's copy, which replaces it silently and uploads the same bytes for two inputs. A directory per list input, its files named by their position (the fourth review, after an index given to a duplicate name turned out to be a name a real file could already hold), leaves no name two values can share.
- **The offer's conditions live in this skill** because they are statements about the inputs — no placeholder, every input filled, run-ready — and the run skill takes over only once they hold.
- **The template carries its own shape, so the skill stopped restating it.** The skill described the light shape under the template call, in a value-shapes table, and in the Synthetic strategy's concept table. The template returned with `explicit: false` already has each value in that shape, so the main path says to fill it in place and keep the Dynamic envelope as given, and the per-concept values live once in each strategy's reference.
- **The interactive questions are asked with their strategy.** The "interactive additions" were a list under the strategy table. Each belongs to one strategy — which file maps to which input to User data, the domain and edge cases to Synthetic — so each strategy's reference opens with its own, read at step 3 before anything is filled, which is when the old list was asked.
- **A published address is one branch.** An address is passed as a catalog id is, and differs from one in a handful of places: its default `<output_dir>` (the last path segment, tag dropped), what an untagged address floating means, an invalid package being upstream's to fix, and the two refusals only an address meets at prepare — a workshop older than the selector, and the deployment refusing in-process Python in the `config` arm. They are one reference, read at step 1 when the target is an address, and again from the stop table when prepare refuses it; the instruction to say that an untagged address floats stays at step 1.
- **The prepare errors are one reference, keyed on the error's `location`.** Their repairs are opposite — a size limit is terminal, an unreadable path is retried with the same bytes under an absolute path, an unresolved closure is diagnosed through `mthds_validate` — and the tool returns no `validation_errors[]` to tell them apart, so the one thing to read first is the location. The stop table keeps, beside its pointer, the fact a model must not miss before it reads: the size limit is terminal for the attempt. The file-fidelity rule that forbids working around the limit is a guard and stays at step 5, because a derived file uploaded in place of the user's is wrong with nothing later to say so.
- **"Prepare again whenever a file was replaced in place" stays in the skill.** A file moved over the original keeps its old timestamp, so `/pipelex-run`'s currency check cannot see the replacement, and a run on the stale upload reports success. Until uploads are keyed by the hash of their bytes, the sentence is the only guard.

## `pipelex-catalog`'s rationale, moved out of the skill (2026-09-23)

Spelled in verbatim, a name like `../../src` would climb out of `methods/` into the project's source tree, and the workshop, which bounds a write only to its own root, would accept it.

Nor does the status carry a progress signal or a heartbeat, so the reading is judged from the one thing it does carry, the time elapsed since `created_at`, and elapsed time cannot tell a slow run from a dead one: the skill stops waiting and reports the status, the elapsed time and the run id, names a failed workflow task as one possibility, and never calls the run failed.

- **A published address and a failed run are references, and their guards stay in the skill.** Each is a condition the skill sees before it acts: the target is a `method_ref`, or the run failed. So the address's floating, its inputs directory, its manifest's main pipe and its not-ours-to-repair routing are read before the first call on an address, and the failure table, the `PipeFunc` reading on a `files` run and the address's failure rule before a failed run is routed. ## The experiment loop is its own skill — `pipelex-lab` (2026-09-24)

The proof lab drove clean sessions from a plain-language brief to a method, a web app and a command-line tool. Its evidence was trustworthy because of the driver's own loop, which no skill owned: pick a use case, plant facts in test inputs, write down the right answers before the first run, run, read the output against those answers, record the verdict with the run id and the cost, fix, and run again. The subject sessions improvised the rest unevenly. Keys existed mostly because the driver asked for them, and each subject named and placed its own differently. Run ids of page runs were lost and dug out of server logs. The home-staging topic spent two paid rounds fixing a method whose test photographs were at fault. `pipelex-lab` owns that loop. Louis ruled on its design on 2026-09-24.

- **It is named `pipelex-lab`, because it covers both the exploring and the experimenting.** `pipelex-test` would collide with "a test run", which `pipelex-run` defines as a real run on test files, and `pipelex-evaluate` names only the scoring half.
- **Framing is the lab's first move rather than a skill of its own.** What "right" means, chosen while framing, becomes the seed of the keys, and splitting the two would lose that thread. `pipelex-design` has no room for framing, and it is about how to build a method rather than which one to build. If framing outgrows its reference, it can split into a skill later. A method the user already has gets a short brief without candidates, because its keys need what "right" means as much as a new method's do.
- **The agent in the session scores a run**, which is free and available now. Each key line names the output field it checks, so that a judge method, an MTHDS method scoring another, could take the same keys later and run the cases unattended.
- **The lab lives at `<project>/lab/<method>/`, outside the bundle directory.** The catalog saves the bundle directory and a packaged Python project ships it, and test files, which sometimes stand in for confidential documents, belong in neither. The brief is written before the bundle exists, so it is named with the domain the lab gives `/pipelex-design`, and moved when design names the directory otherwise; a session opened inside the bundle takes the bundle's parent as its project, so that the rule never puts the lab where the guard forbids it.
- **The builder's go on the budget covers an autonomous loop**, which is Louis's amendment to the recommended go per round. Its autonomy is bounded by stops, and each stop is a guard in `SKILL.md`. A round runs every case once, so that a fix for the trap case that breaks the clean one shows up at once. A round makes one fix, so that the log's "Changed" line stays true and a regression points at one change. The loop stops at the pass bar and at the budget, and it also stops when a failing line traces to the inputs, when the only fix would change a key, the inputs or the contract, when a round scores worse than the best one so far or two rounds in a row fail to beat it, when a run fails for a reason that is not the method's, and when the user interrupts. The stall stop is the answer to the home-staging topic: a fix that goes the wrong way costs one round, not a budget, and the loop does not undo that fix, because keeping or undoing it is the user's call. The keys and the budget end a turn of their own before the loop starts, because a credit notice written between two tool calls can land where the user never sees it. A go belongs to its series: a series left without a scorecard, by an interrupt or a lost session, is closed with one, and the loop waits for a new go rather than spend under one given in another session. A run fails for a reason that is not the method's when it timed out, was cancelled or terminated, or names a provider, a quota or the platform, because `/pipelex-run`'s routing sends every other failure to a skill that edits the method or its inputs.
- **Variants are left for later.** The proof lab never compared two models or two prompts on the same case, and the log's "Changed" line already gives a before-and-after comparison.
- **The lab starts no run and edits no method itself.** Each run goes through `/pipelex-run`, which keeps the credit guard, the run id and the failure routing, and each fix goes through `/pipelex-edit` or `/pipelex-design`. On Claude, the lab pre-approves only the tools that read a run. **The loop runs the bundle directory, never a catalog id or an address**, because a fix lands in the files and a saved method changes only when `/pipelex-catalog` saves it, which is a deployment. So a bundle with a `PipeFunc` over its own `.py` is a stop before the go: no files run carries its Python, and a round would spend credit on a failure known in advance.
- **A case of the user's own files is kept out of version control.** The lab sits in the project, which is usually a repository, and a key written from those files carries their facts. So the case directory goes into `.gitignore`, unless git already ignores it, before anything is copied into it, and a synthetic case, whose files are made to be shared, is committed like the rest of the lab.
- **The workshop is needed by the loop alone.** Framing and setting up read and write only files, so the lab stays out of the `MCP_SKILLS` roster and stops before the loop when the workshop is absent, as `pipelex-explain` works on without it.
- **An output cut at the workshop's size cap leaves its lines unscored, never passed.** The run results bound `main_stuff` to a size cap and mark the cut with `truncated`, and a line scored on what was cut away would claim a pass nobody saw.
- **The budget is a ceiling checked before each run, not a cap.** The platform caps no spending, and a run can cost more than its estimate, since a fix can add a step that calls a model. So the lab checks each run against the highest cost its case has had in the series, which bounds an overshoot to one run's rise, and says so at the go. The first round's estimate is the brief's rough cost of one run, so that no round runs unchecked. A run that failed or did not finish carries no cost in its results, and a partial cost is a lower bound, so both count at the run's estimate rather than at a figure nobody measured.
- **Only the Must and Must not lines are scored.** A planted fact describes the inputs, and an Also acceptable line changes how another line is scored, so counting either would let two equivalent outputs score differently and trip the stall stop. A line the pass bar allows to be partial meets the bar when it is partial, or its case could never pass.
- **A key change restarts the history of the lines it rewrites or adds, not of the whole case.** As first written, a key change reset every line of its case, and the replay that proved the skill showed the cost. A user asked for a change that rewrote one line of a case, and an unrelated edit then broke another line of the same case, one that had passed in every earlier run, yet the log said "No regressions". A line the change left alone still means what it meant, so its history still counts, and a side effect is exactly what a regression exists to name. The best round does count from the change, because the rounds before it were scored on different lines.
- **The capability map is tied to the MTHDS reference by a test.** It is the statement most likely to drift, and a wrong one sends a design to fail at its first run, as the Word-transcript method in the proof lab did. Each row names a pipe that the reference documents, and the claims that carry a limit are held to the reference's own words.

The lab shipped first with nothing pointing at it, so that it could merge on its own. The skills a builder already uses then gained one sentence each, which is all their size allows: every one of them sat within a few dozen characters of the ceiling, so each sentence displaced a restatement or a clause of rationale that is recorded here or elsewhere in this file.

- **`pipelex-design`'s hand-off names the lab** beside the test files with planted facts it already offered, because the end of a design is the moment a builder decides how to test the method.
- **`pipelex-run` offers the lab a run of a case that the lab did not start, rather than logging the run itself.** "Run it again" is `pipelex-run`'s phrase, so a builder who says it in the middle of an experiment reaches that skill, and the run spends credit whether or not the lab hears of it. The log is the lab's to write, in its format and against a case. The lab logs such a run in an entry outside any round: it counts in the log's total, since it spent credit, and it moves neither a series' budget nor its best round, which read only the runs the loop made. It does not. The files themselves are kept, a synthetic case being committed with the rest of the lab. A catalog save cannot carry them, because the workshop's resolver reads only `.mthds` files, plus `.py` files for a save's `python` (`pipelex-mcp/SPEC.md`, "Path trust boundary"). So in a git repository the skill now checks each copy's path with `git check-ignore` before writing it, and `inputs.json` when a value holds a file's text, and gives a path that is not ignored a `.gitignore` entry. The first review of this phase added the check and two rules the bare instruction missed, both reproduced in a scratch repository. A pattern is relative to the directory of the `.gitignore` it is written in, so `methods/foo/inputs/` written into `methods/.gitignore` ignores nothing. And git never ignores a path it already tracks, which is the ordinary case here: a synthetic file and a copy of the user's file for the same input share a name, `inputs/<input>.<ext>`, and a synthetic file is made to be committed. `git check-ignore` reports a tracked path as not ignored, so the one check catches both, and a path it still does not report ignored is not written until the user says so. Closing that gap means moving a packaged bundle's inputs out of the package, which changes a default two skills share. It is tracked as `L-260924-208499`.
- **`pipelex-inputs` stops at run-ready, with no run offer, when the lab hands it a case.** The plugins review of 2026-09-24 found that the lab hands each case to `pipelex-inputs` while it sets up, before it writes the case's key, and that `pipelex-inputs` always ended by offering the run. A yes to that offer ran the case before its key existed, which is what the lab's first guard forbids. A calling skill can now ask `pipelex-inputs` to stop at run-ready, and the lab does so for every case. The exemption is the caller's and never the user's. A Codex session told to prepare inputs and stop short of a run had already ended without the offer that the skill's last step requires (`L-260923-530eb0`), and an exemption worded loosely would have made that omission look allowed. The skill sat at the ceiling, so the bullet displaced three clauses that restated a step or gave a reason: the labels of the files step 6 names, why the Template strategy skips preparation, and what the tool does with a second selector.

## A saved run stays out of version control, and the ignore procedure is one include (2026-09-24)

The plugins review of 2026-09-24 found that `pipelex-run` saves every completed run's `main_stuff.json` into `runs/<run_id>/` under the workshop's working directory, which is usually the project root and usually a repository, and that nothing ignored it. That output carries what the run extracted from the user's files, while `pipelex-inputs` and `pipelex-lab` were already keeping the files themselves out of git. A `git add .` after a run would have committed the facts the other two skills keep out.

- **In a git repository, `pipelex-run` checks the run's folder before it saves, and ignores `runs/` when git does not.** It runs `git check-ignore -q` on `runs/<run_id>/`, and when that path is not ignored it adds `/runs/` to the nearest `.gitignore`, relative to that file's directory, says so, and checks again. Outside a repository it does nothing and says nothing. The rule holds whether the inputs were the user's files or synthetic ones, because the run skill cannot tell which, and `runs/` is output the skill writes one folder per run, not something a project commits: a run is kept by its id, and it can be saved again days later.
- **The check names the new run's folder, not `runs/`.** Git reports a directory that holds a tracked file as not ignored, so a `runs/` in which the user once committed a run would read as not ignored for good, entry or no entry, while the new run's folder, which nothing tracks, reads as ignored once the entry is there. Both behaviours were reproduced in a scratch repository.
- **The entry is anchored, `/runs/`.** The workshop writes only into the `runs/` at its own root, and an unanchored `runs/` would also hide every new file of a source directory that happens to be named `runs` further down, such as a Python package.
- **The tracked-path guard applies to the run as written.** The workshop never overwrites a file, so a save never lands on a tracked path; but a path git still does not report ignored after the entry, because of a negation rule or an entry written into the wrong file, means that the output would reach git, and the save waits for the user as the other two skills' writes do.
- **A folder the user named with `dir` is left as it is.** The user chose where that output goes, and ignoring a folder such as `docs/` would hide every new file in it. A refused `dir` is retried into `runs/<run_id>/`, which takes the check like any other save into it, and Follow a run's "save run X" goes through step 7, so a save days later is held to it as well.
- **`pipelex-synthetic-inputs` does not take the check.** It saves a generated photograph's run into `runs/<run_id>/` before moving the image onto its target, but that run's output holds a generated picture and its description, not the user's files.
- **The procedure is one include, `templates/skills/shared/git-ignore.md.j2`, now that three skills say it.** Each skill keeps its own bold subject and sets two parameters, what is checked and when, and the entry it writes; the include carries the rest, from `git check-ignore -q` to the tracked-path guard, so the three guarantees cannot drift apart: the entry goes into the nearest `.gitignore`, relative to that file's directory; it is confirmed with the check; and a path still not ignored waits for the user. `pipelex-inputs` renders exactly as it did. The lab used to add the case directory first and confirm afterwards, and it now checks first like the other two, so a case under a lab that is already ignored gains no redundant entry; run could not have taken the add-first order, since it saves after every completed run and would have appended the entry each time. The lab's reason for ignoring the whole case directory, that its key holds facts from the user's files too, is recorded under "The experiment loop is its own skill" and no longer ships, and its tracked-path guard now reads as the others do, a copy being one way of writing.
- **`pipelex-run` paid for the paragraph with rationale, which is recorded here.** The skill sat within a dozen characters of the ceiling. The run id is reported before anything else because it is the only handle a later session has on the run; the address's `method_provenance` is reported beside it because it is the only record of what ran, and nothing later recovers it. A dry run ends the turn because a flow shown and run past in the same breath leaves the user nothing to stop, as "A dry run is the validation step, shown" records, and a `PipeFunc` is named as a suspect for a failed run because nothing upstream of the run could have caught its failure, since validation never resolves the function, as "`PipeFunc` is warned about, never refused" records. Follow a run's restatement of step 6's two readings, a degraded status and a long `RUNNING`, became a pointer to them, since the skill states each guard once.

## A catalog save is linked, or the user is asked first (2026-09-24)

The plugins review of 2026-09-24 found that `pipelex-catalog` could save a method that nothing links to. The shared submission convention, `templates/skills/shared/validate-call.md.j2`, offered inline `{content, uri}` files as the fallback to the path form, and the catalog says never to pass `link_dir`. But `mthds_save_method` writes `pipelex-method.json` only beside a root file submitted as `{path}`, and refuses a `{path}` item that follows an inline root (`pipelex-mcp`, `src/capabilities/catalog-write.ts`: `linkDirectoryOf`, `writeLinkForSave` and `pathsOutsideBundle`). A method created from inline files was therefore linked to nothing, and the directory's next save created a second method, which nobody but an administrator can delete. The behaviour was read in `@pipelex/mcp` 0.18.0, the release the plugin's launcher resolved to on that day.

- **A save takes the path form.** The link is what makes a later save an update, so a save that cannot write one is a different act from the one the user asked for, and the skill says so before it happens rather than after. `link_dir` is no way around it: the workshop bounds it by the same working directory as a `{path}` item (`src/capabilities/workspace-boundary.ts`, `resolveSaveDir`), so where the bundle's path is refused, a link beside the bundle is refused too, and a link anywhere else is one no later save from the bundle's directory reads. The skill keeps "Never pass `link_dir`".
- **An unlinked save is asked for, not refused.** A one-off method saved from outside the workshop's directory is a legitimate thing to want, and the relaunch that would link it may cost the user a session. So the skill says that the save cannot be linked from this session, which leaves the relaunch open, and saves inline only on the user's yes.
- **The catalog's sentence rides on a parameter of the include.** The convention is one include because every skill that submits a bundle says it, and the catalog differs only in what it says of the inline form: for every other skill that form is the fallback and the only one the hosted console accepts, while `mthds_save_method` is the local workshop's alone, so the console has nothing to say there. `validate_call_inline` carries the difference, as `validate_call_file_set` carries integrate's, instead of a pasted variant of the convention.
- **The convention names the workshop's refusal of a path outside its working directory.** It used to say that the workshop resolves a path against its own working directory, "wherever the harness launched it, so pass an absolute one", which read as though an absolute path always worked. The local workshop refuses any `{path}` that resolves outside the directory it was started in, an absolute one included (`src/local/files.ts`), and a session launched below or beside the bundle met that refusal with no guidance (`L-260923-019e50`). The convention now names the refusal and the cure, relaunching the harness from a directory holding the bundle, and every other skill keeps the inline fallback beside it. The placeholder `<absolute path to the file>` still asks for an absolute path.
- **The reasons for preferring the path form moved here, and paid for the clause.** A path keeps the file's real location as provenance in the workshop's diagnostics, and it spares the model copying whole bundles into the request, which costs tokens in proportion to the bundle and can change a file silently. That was half a sentence of rationale in every skill that includes the convention; with it gone, each of them renders shorter than before, although design, inputs, run and integrate sat within a few dozen characters of the ceiling.

## The run's `pipe_code` is qualified, the same value as `pipe_ref` (2026-09-24)

The plugins review of 2026-09-24 found `pipelex-integrate` saying that the verdict's `pipe_ref` is namespaced while the run's `pipe_code` is not, its call-site templates setting `PIPE_CODE = "summarize_pdf"`, and `pipelex-run` saying to pass "a pipe's code". The workshop's `mthds_run` documents `pipe_code` as a qualified `domain.pipe_code`, the same value `mthds_inputs_template` and `mthds_prepare_inputs` take as `pipe_ref`, and passes it through unchanged (`pipelex-mcp`, `src/capabilities/run.ts`). The ruling: `pipe_code` is qualified everywhere the skills set it or describe it, and it is the same value as `pipe_ref`.

- **The run path accepts the qualified form and resolves it exactly.** The path was read end to end before any skill changed. The hosted platform types the start body's `pipe_code` as a non-empty string with no pattern and forwards it (`pipelex-server`, `platform/src/pipelex_platform/routers/v1/execution.py` and `services/pipeline_runner.py`). `pipelex-api` 0.27.3, the version the hosted plane pins, puts no validator on `RunRequest.pipe_code` and hands it to the pipeline setup (`api/schemas/models.py`, `api/routes/pipelex/pipeline.py`). Both SDKs pass it through: `@pipelex/sdk` in `src/client.ts`, unchanged at the 0.23.0 the workshop locks, and `pipelex-sdk` through the `mthds` 0.15.0 client it inherits (`mthds/runners/api/client.py`). The runtime, `pipelex` 0.64.1, resolves it in `get_optional_entry_pipe` (`pipelex/libraries/pipe/pipe_library.py`): a qualified code is an exact key, and a miss is refused with no fallback.
- **The bare form fails as ambiguous, never on the wrong pipe.** The same function searches a bare code across every domain of the bundle and refuses it when two domains declare it, so a bare `PIPE_CODE` runs until the bundle gains a pipe of the same code in a second domain, and from then on every run fails. The type checker, the offline gate and the sidecar comparison see none of it. The earlier ruling, recorded under `pipelex-integrate`'s rationale above, that a qualified code fails only on a real run, does not hold against the runtime the hosted plane pins.
- **The qualifier is the pipe's own domain**, the one declared by the file that defines the pipe, which in a multi-file bundle need not be the root file's, and which may itself be dotted (`legal.contracts.summarize`). `pipelex-integrate` takes the ref verbatim from the verdict's `main_pipe.pipe_ref` and, when the verdict carries no signature, builds it that way from the bundle; `pipelex-run` says it in a clause at step 1. A pipe of a dependency package is named through its alias (`alias->…`), which a `domain.pipe_code` does not reach, so the rule is stated for a bundle's own pipes.
- **The generated tree names no pipe, so the call site keeps its literal.** `mthds_codegen` asks only for the concept-set-wide `types` projection and never sends a `pipe_ref` (`pipelex-mcp`, `src/capabilities/codegen.ts`, `CODEGEN_KIND`), so the tree holds concept schemas and parsers and no constant for the entry pipe. `PIPE_CODE` stays a literal the skill writes from the verdict, the same value as the sidecar's `pipe` record.
- **A refresh sets a bare `PIPE_CODE` to the qualified ref.** A project integrated before this ruling runs the bare code, and none of refresh mode's other triggers fires on it, since it type-checks and the `pipe` record is compared to the signature, not to the constant.
- **`pipelex-run` paid for its clause with rationale.** It carries the `pipe_ref` through every call so that the template call's drift check and the run inspect the same pipe's contract; that reason is recorded here and no longer ships.
- **No live run has exercised a qualified code yet.** The evidence above is read from source. The end-to-end legs in `pipelex-sdk-js` (`tests/e2e/artifacts.e2e.ts`) and `pipelex-sdk-python` (`tests/e2e/test_artifacts_e2e.py`) would record one.
