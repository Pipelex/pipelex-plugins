# Photographs — generated through the workshop

Read this at step 1 of the skill when the brief is a photograph, before drafting anything. It replaces steps 2, 4 and 5 for that file: no Python, no recipe. Step 3's draft becomes the description the image model receives, and step 6's report gains the run id and its cost.

A photograph is the one file this skill does not render from code, because code cannot draw one that a method should be tested on. It is generated by `gpt-image-2` through the workshop's `mthds_run`, so it needs the `pipelex` MCP server connected with its API key, and each photograph spends a little inference credit.

## 1. Write the description

The description is where the test's ground truth goes in. Write it as a photographer's brief, not as a caption:

- **Plant every fact the method must find, visibly and unambiguously.** For a damaged car: which car, which side, which panel, what kind of damage ("the front bumper is cracked and pushed in on the driver's side; the rear of the car is intact and clean"). For a room: which room, what is in it, what is not. A fact the brief needs but the picture does not show is not planted.
- **Say what must not appear**, when its absence is itself a fact the method will be checked on: "no people", "no other vehicles", "the walls are bare".
- **Ask for realism**: "a realistic smartphone photo", the light, the angle and the distance, as a person taking the picture for that purpose would stand. Nothing staged or cinematic unless the brief is a marketing shot.
- **Keep text out of the picture** unless the method reads it. Image models garble lettering; when a plate, a label or a sign must be read, give the exact characters and keep them short.
- **Fictional subjects only**, as in step 3: no real people, no brands or logos, no real addresses.

Show the description to the user in the reply before the run, with the one-line cost notice below; it is the draft they can redirect.

## 2. Generate it

The bundle is one pipe, submitted inline. Pass it exactly as written, with `aspect_ratio` set to what the method expects (`landscape_4_3` for a phone photo held sideways, `portrait_3_4` for one held upright, `square` for a product shot):

```toml
domain      = "synthetic_photograph"
description = "Generate one realistic photograph from a description, as a test input for another method"
main_pipe   = "take_photograph"

[pipe.take_photograph]
type         = "PipeImgGen"
description  = "Render the description as a realistic photograph"
inputs       = { description = "Text" }
output       = "Image"
prompt       = "$description"
model        = "gpt-image-2"
aspect_ratio = "landscape_4_3"
```

One line before the call: how many photographs, the model, and that each spends inference credit. Then call `mthds_run` with `files` set to `[{ "content": "<the bundle above>", "uri": "synthetic_photograph.mthds" }]` and `inputs` set to `{ "description": "<the description>" }`. Start every photograph of the request before polling any of them: the runs are independent.

Follow each run with `mthds_run_status` at the hint it gives, then `mthds_run_results` once it is terminal. A failed run is reported with its `failure_message` verbatim, and that photograph is left without a path; do not retry it with a reworded description on a guess.

## 3. Save it

Call `mthds_download_artifacts` with the run id and `dir` set to the target's directory, relative to the directory the workshop was started in. It never overwrites and reports the path it wrote, which may carry the image's own extension (`.png`, `.jpg`, `.webp`). Move that file onto `target`, keeping the extension the download reported: a `native.Image` input accepts any of them, and the target's name follows the file, never the reverse. An existing file at `target` is still the user's: confirm before replacing it.

## 4. Verify

Look at the saved picture. Where the harness can show an image to the model (Claude's `Read` tool can), check each planted fact from step 1 against what the picture shows, one by one. A fact the picture does not show, or shows wrongly, earns one more run with a sharper description that names it first; after that second attempt, keep the better picture and report the fact it misses, so the user knows the test does not cover it. Where the harness cannot show images, say that the facts were not checked by eye.

## 5. Report

Per photograph, beside step 6's line: the path, the pixel size, the run id, the cost from `usage.cost_usd` in the run's results, each planted fact with whether the picture shows it, and the words "AI-generated", so nobody mistakes it for a real photo later.
