# What a file the user gives is for

Read this when the user gives a file, attached to a message, named by its path or its URL, or picked from the team's files, before using it for anything, and whenever a file given earlier in the conversation is about to be used and its role was never settled. A file is not an input until its role says so: users brief by file as often as they hand over data, and a procedure made into an input gives a method that reads the procedure on every run instead of following it. The skill that sent you here keeps its steps and its guards; this file only settles what the file is for.

## The roles

- **A sample input** is one case of what the method will take, such as an invoice, a CV or a contract to review. It shapes the input concept, since its contents show what the method must read, and it becomes a test input, prepared by `/pipelex-inputs`.
- **A brief** is instructions for building the method: a process, a procedure, requirements or rules. It is the request itself, so its steps become the method's steps and its rules the prompts' rules, and it is never an input. Building or changing a method from one is `/pipelex-design`'s work, whichever skill met the file first.
- **An example output** shows what the result should look like, such as a report the user once wrote by hand. It shapes the output concept's fields and the prompt's format.
- **A template** is a blank form or layout to fill, with empty fields or placeholders. It is placed among the method's files for a `PipeDocGen` step to fill; what a template holds, and how a step names it, is in [the `PipeDocGen` section of writing-mthds.md](writing-mthds.md#pipedocgen--print-a-document-file).
- **Reference material** is knowledge the method applies on every run, such as a style guide, a grading rubric or a price list. It is written into the prompts when it is stable, verbatim when it is short and condensed to the rules the method applies when it is long, and it is made an input when it changes from one run to the next, such as one style guide per client, and the file the user gave then fills that input as its sample input. When the context does not say which, that is a doubt, and the rule for doubt below applies.

**Roles combine.** An input sent with its expected output is a worked example, the strongest signal there is: the input becomes a test input, and the output shapes the result and says what a right answer is. A brief often holds an example output, which is read as one. A sample input always says something of what the method should do, so read it for that too, without taking it for the brief.

**Files given together are one batch or several cases.** Several files of one kind given together as what the method takes, attached to one message or named in one breath, are read one of two ways, and the two give different methods. When the words act on them together, as "total these invoices", "rank these CVs" or "compare these quotes" do, they are the items of one batch the method takes at once, a list input, and they fill it in the order given. When the words offer them as examples of what the method will get, as "here are some CVs like the ones it will receive" does, they are several cases of an input it takes one at a time: one of them fills the test inputs, and your closing message names the others as cases to try next. Once the method is built, its inputs settle the reading: a list input takes the files no input of one claims, and an input of one with no list beside it takes one of them, the others named as cases to try next, unless the user's words ask to change the method. Before that, the choice changes what the method takes in, `Invoice[]` against `Invoice`, so when the words do not settle it, the rule for doubt below applies: ask before fixing the contract or filling any input. Where this says to name the others as cases to try next, `/pipelex-lab` makes each of them a case of its own instead, as its framing reference says.

## What each role asks of the method

- **An example's values appear nowhere in the method, and in its test inputs only as a sample input the user gave.** The names, dates, amounts, percentages, readings and identifiers in a sample input or an example output become structure, fields and format, never text of the method, which ships with every run and every published version. None of them goes into a prompt or into any description, a field's, a pipe's or the bundle's, not even as a format example: a format example takes made-up values of the same shape, numbers too, never the example's own amounts or percentages. The test inputs are saved with the method, so a method built from an example output gets test inputs made up in the same shape, such as an invented client with invented people and figures, never the example's own case rebuilt from its values; only a sample input, a case the user gave the method to run, becomes a test input as it was given. When the bundle's `description` says what the method was built from, name an example by its kind, such as "a sample client report", never by its client, its people or its figures; a brief that is the user's own procedure may still be named. Write the example's values in only when the user asks for it: your closing message may offer to load its own figures as test inputs, so that the user can compare the result with their document, and you load them only on their yes. Before that message says the values are not in the method, search every file you wrote, the test inputs included, for the example's names, dates and numbers, and rewrite any you find, except a given sample input's own values in its test input, which stay as they were given; never say it from memory.
- **A brief goes through [fit.md](fit.md).** A process document is full of steps no method does, such as "email the client" or "file it in the CRM": the method takes the part a method does, and you say what carries the rest, as fit.md teaches.
- **A brief is not kept with the method.** Never copy it into the bundle's directory, which travels whole with every validation, run and save. Let the bundle's `description` say in one sentence what the method was built from, so that a reader who never saw the document knows where its rules came from, and leave the document where the user keeps it.
- **An example output becomes a template too only when the user wants the result as that kind of file.** A Word, Excel or PowerPoint example given as the file the team sends or fills in, "we send this report to clients" or "fill in this sheet", is also a template; an example that shows only a tone or the content to cover shapes the text and nothing else. When it is unclear whether the user wants the file or only its text, ask.

## How to tell

Read every file before deciding: its name and its type do not say what it is for. Then weigh the clues, strongest first.

1. **The user's words.** Ask what the words do with the file. Words that hand it over as the way the work is done, a process to follow or guidelines to respect, make it a brief or reference material; words that show what the result should be make it an example output; words that offer it as one case among many make it a sample input; words that ask for it to be filled make it a template. Read the meaning, never a phrase alone: "use this" after a method is built offers a case to run, and the same words beside a procedure, before any method exists, hand over the brief.
2. **The file itself.** Step-by-step instructions or rules point to a brief or reference material, a single case full of real values to a sample input, a finished deliverable to an example output, and blanks or placeholders to a template.
3. **Where the conversation stands.** A file that matches the input of a method already built is a test input, and so is one given to try the method on after a build. Before any method exists, a file is as often the brief or an example as a sample.
4. **The file's type, the weakest clue.** A Word document or a PDF can be any of the five.

## When to ask

- **When the clues agree**, act on them, and state your reading in one plain line of your closing message, so that the user can correct it: "I read `claims-procedure.docx` as the procedure the method follows, not as a document it takes in."
- **When they conflict, or when a wrong guess would change what the method takes in or gives back**, ask before fixing the contract or filling any input. Offer the readings in plain words, such as "Is this document the procedure the method should follow, or a document the method will be given to read?", and ask the way the host lets you: through its question tool where it has one, and otherwise with a question that ends your reply.
- **A role sticks.** Once settled, it holds for the rest of the conversation, so a later request for test inputs never takes a brief, an example output or a template as an input. Only the user's own words change it, as when they give the same file again to run the method on.

## Cases

- **A process document, with "build me this".** `claims-procedure.docx` says how the team handles a claim: read it, check it against the policy, decide, email the customer and log the decision. The words and the file agree, so it is the brief. The method's steps follow the document's reading, checking and deciding, the email and the log go to a carrier, no input is made from the document, and the closing line states the reading.
- **A CV, with "match CVs to this job ad".** The words make CVs what the method takes, and the one CV given is a single case of them, so it is a sample input: it shapes the input concept and becomes a test input. The job ad is reference material written into the prompt when the method serves that one opening, and a second input when each opening brings its own; the words leave that open, and it changes what the method takes in, so ask unless the conversation has said.
- **Invoices attached together, with "total these invoices".** `march.pdf`, `april.pdf` and `may.pdf` come in one message, and the words act on them together, so they are the items of one batch: the method takes a list, `Invoice[]`, and the three files fill that one input in the order given. Had the words been "here are some invoices like the ones it will get", the same files would be cases of what arrives: the method would take one `Invoice`, one of the files would fill the test inputs, and the closing message would name the other two as cases to try next. Words that fit either reading, such as "use these", leave the method's input open, so ask before fixing the contract: "Should the method take these invoices together, as one batch, or one invoice per run?"
- **A filled report, with "it should produce this".** `site-visit-march.pdf` was written by hand and holds a real client's name, address and findings. It is an example output: its sections become the output concept's fields and the prompt's format, the client's name, address and findings appear nowhere in the method, not even as a format example, its test inputs describe a made-up visit, and the bundle's `description` says it was built from a sample report. It becomes a template too only if the user wants the result as that same kind of file.
- **A contract, with no words.** The user drops `supplier-agreement.pdf` before any method exists and says nothing. It could be one of the contracts the method will review, the agreement other documents will be checked against, or the source of the rules a review applies. Nothing settles it, and each reading gives the method a different input, so ask before designing: "Should the method review contracts like this one, or check other documents against this agreement?"
