# Smoke sessions — `pipelex-integrate`, phase 2

The smoke sessions that close phase 2 of [`plan.md`](plan.md), under box H of [`design.md`](design.md): a fresh session walks the rewritten skill's main path and each of its branches, and the transcript must show each branch reference read on its branch and none read on the main path. They ran on 2026-09-23 against the worktree build at `332965b` (`feature/Integrate-diet`), whose rendered `SKILL.md` is the one the plan's size bullet records.

**Every scenario passed.** No session read a branch reference on the main path, every branch session read its reference before acting on the branch, no guard was broken, and no template fix was needed. Scenario 5 needed more than one Codex run: the earlier runs failed for reasons in the smoke setup, not in the skill, and each is recorded below with what the model did.

## How the sessions were driven

**Claude Code 2.1.280**, model `claude-opus-5-5` (the user default), headless from each scratch project: `claude -p "<prompt>" --plugin-dir <worktree>/pipelex --settings '<json>' --permission-mode bypassPermissions --output-format stream-json --verbose`. The session-only settings disable the published `pipelex@pipelex-plugins` plugin and the workspace-internal plugins (`ledger`, `rev`, `sprint`, `agent-watch` and the rest of `pipelex-internal`), so the worktree's plugin is the only `pipelex` loaded and no workspace tooling speaks in the session; nothing on disk changed. Every session's init message lists one `pipelex` plugin, at `<worktree>/pipelex`, and its MCP server `plugin:pipelex:pipelex` as connected. The stream omits the injected skill text, so the skill's origin was read from each session's own transcript under `~/.claude/projects/`, where every session carries `Base directory for this skill: /Users/lchoquel/repos/Pipelex/_pipelex-plugins--integrate-diet/pipelex/skills/pipelex-integrate`. The workshop was the plugin's own launcher, `npx -y @pipelex/mcp@latest` (0.17.0 on the day, engine 0.61.0), with the key and base URL inherited from the shell, pointing at api-dev.

**Codex CLI 0.153.4**, model `gpt-6-astra` at medium reasoning effort, in an isolated `CODEX_HOME` as phase 0 did it ([`facts.md`](facts.md) section 3): only `auth.json` copied in, the marketplace added from the worktree root with `codex plugin marketplace add`, the plugin installed with `codex plugin add pipelex@pipelex-plugins`, and the cache copy of `skills/pipelex-integrate/` checked identical to `pipelex-codex/skills/pipelex-integrate/` with `diff -r`. Each run was `codex exec -m gpt-6-astra --json -s workspace-write -C <project> "<prompt>"`. The manifest forwards `PIPELEX_API_KEY` and `PIPELEX_BASE_URL` by name from the environment. Every rollout carries the skill as `<skill><name>pipelex:pipelex-integrate</name><path>…/codex-home/plugins/cache/pipelex-plugins/pipelex/0.7.0/skills/pipelex-integrate/SKILL.md</path>`. The user's own `~/.codex` was left untouched: its `config.toml` hash and timestamps, and its plugin cache, are the same after the runs as before them.

**A Codex fact the eval suite will need.** `codex exec` runs with the approval policy `never`, and Codex asks approval for an MCP tool its server does not annotate as read-only, so `mthds_codegen` is refused with *"MCP tool call requires approval, but approval policy is never"* while `mthds_validate` goes through (scenario 5, run 1). An unattended run pre-approves the one tool in the isolated `config.toml`, which stands in for the approval a person gives interactively:

```toml
[plugins."pipelex@pipelex-plugins".mcp_servers.pipelex.tools.mthds_codegen]
approval_mode = "approve"
```

The key is read by `apply_plugin_mcp_server_policy` in `codex-rs/core-plugins/src/loader.rs` at `rust-v0.153.4`.

**What counts as a read.** A reference is read when a `Read` call names `references/<name>.md`, or when a shell command prints it; the models on each harness often read a reference with `cat`. The projects are scratch directories outside every repository, each a git repository with a committed baseline, so that no workspace `CLAUDE.md` or `AGENTS.md` loads and the diff after a session is exactly what the session did. The transcripts and projects were kept in the orchestrating session's scratch directory (`/private/tmp/claude-501/…/scratchpad/smoke-integrate/`), which is temporary; the session ids below are the durable handles.

**The scenario shape.** `L-260921-479a8e` names `claude plugin eval` as the runner but states no scenario shape, so each scenario is written as setup, prompt, expected references and expected outcome, followed by its runs.

**The base projects.** The first base project is a TypeScript service with `"type": "module"`, `moduleResolution: "bundler"`, a `tsc` build and `"start": "node dist/index.js"`, `@pipelex/sdk` pinned at the 0.18.0 floor, `zod`, and the `extract-entities` bundle copied from `pipelex-starter-js/methods/extract-entities/` (`main_pipe = "extract_entities"`, a text input, one structured output) into `mthds/extract-entities/`. That combination type-checks under bundler resolution but runs the `tsc` output under plain Node, where `binder.ts`'s extensionless `./types` import fails with `ERR_MODULE_NOT_FOUND`. The sessions noticed it, and it sent one Codex run off the skill's path (scenario 5, run 2), so another base project replaced it for the main path: the same service with `noEmit`, run through `tsx`, which resolves an extensionless import. Scenarios 2, 3 and 4 kept the first base, where the runtime plays no part in what they test.

## Scenario 4 — a refresh that meets orphans

- **Setup.** The `ts-zod` target emits the same file names for every method (`types.ts`, `binder.ts`), so renaming or removing a concept changes their content but never leaves a file behind; an orphan comes from an earlier generation into the same directory, a target switch, or an engine version that renamed an artifact. The setup therefore simulates the last: scenario 1's first run, with a stamped `schemas.ts` (a copy of the stamped `types.ts`) in `src/generated/extract-entities/` and listed in `codegen.lock` with its stamp's content hash, as an earlier engine would have left it, committed with the gate green. Then, uncommitted, the concept `ExtractedEntities` is renamed to `NamedEntities` in `main.mthds`.
- **Prompt**, by the slash command: `/pipelex:pipelex-integrate I renamed the output concept of mthds/extract-entities/main.mthds (ExtractedEntities is now NamedEntities). Bring this project's integration of that method up to date.` followed by the same project, unattended and no-run sentences as scenario 1.
- **Expected references.** `refresh.md` and `typescript.md`, then `orphans.md` once `mthds_codegen` returns `orphans: ["schemas.ts"]` with no drift.
- **Expected outcome.** The refresh carries on past the orphans; `schemas.ts` stays on disk and no clean-up is offered; the call site follows the renamed output concept and the type checker runs after that edit; the report names the orphan, says it was not deleted, says the gate counts it as drift so `codegen:check` stays red, and gives the tool's dedicated-directory fix as the user's to take.

**Run** — Claude Code 2.1.280, session `caa56d2b-26bd-45d0-8f19-196f8338841b`. **References read:** `refresh.md`, `typescript.md` and `orphans.md`, in one batch. **Outcome:** the model regenerated in place, read from the content hashes that the artifacts moved (*"this is a real rename, not just a new stamp line"*), renamed the call site's imports and the sidecar's `pipe.output`, rewrote the sidecar's hash, and ran the type checker (green) and the gate (red over the orphan alone). `schemas.ts` is still on disk. The report says: *"`src/generated/extract-entities/schemas.ts` is a leftover from the earlier engine. The new lock doesn't list it, and nothing imports it. The regeneration reported it as an orphan and found no other problem."*, *"I didn't delete it. It's harmless to the type check, but the gate counts it as drift, so `codegen:check` will keep failing until the directory holds only one generation."* and *"The generator's advice is to give each generation "a DEDICATED generated directory such as `src/generated/<method>/`". That fix is yours to make."* **Verdict: pass.**

**An observation on timing.** `orphans.md` was read before the `mthds_codegen` call returned, not after it. The batch came right after the model had printed `codegen.lock`, which listed `schemas.ts`, an artifact the `ts-zod` target does not emit; the transcript shows no reasoning for the read. It was read on a scenario whose branch was taken, and nothing was done differently because of it, so it is not a main-path read. In scenario 2, which had no orphan, `orphans.md` was not read.

## Found on the way

None of these is a defect of the diet, and none was fixed in this phase. The first is for the caller to file.

- **The known-defect note in `typescript.md` misses one project shape.** It says the extensionless import in the generated `binder.ts` bites a plain Node ESM project with a `nodenext` or `node16` resolution, and that a bundler resolution is unaffected. But a project that type-checks under `bundler` and runs its `tsc` output under plain Node gets the same `ERR_MODULE_NOT_FOUND` at runtime, with no `TS2835` to trigger the stop row. Claude reported it and left the runtime to the user (scenario 1, run 1). Codex changed the build instead (scenario 5, run 2). The note should say that this runtime choice is the user's too. It is a pre-existing gap, so by box G it waits for the phase and lands afterwards.
- **Codex reports use Claude's spelling of a skill** (*"Refresh types with `/pipelex-integrate` after method edits"*, scenario 5, run 3). This is `L-260923-0964b0`, already filed.
- **A paraphrased sidecar comment** (scenario 5, run 2) did not recur on run 3, and the gate reads none of the comment. Recorded in case the eval suite sees it again.
