# Classification — `pipelex-explain`

Phase 6 of the size diet ([`plan.md`](plan.md), [`design.md`](design.md) box A). Every paragraph, bullet, list item and table row of `templates/skills/pipelex-explain/SKILL.md.j2` as it stood at `2fd7120` (the phase 1 landing; the template did not move between that commit and this phase's base, `44e7fde`), with its kind under the read-before-act rule and where it went. Line numbers are that version's. Read the rewrite against this table as a move: a row whose destination is the new `SKILL.md` names the section or step it landed in, a row that moved names the reference, and a row that left the shipped text names `docs/decisions.md` or the statement it duplicated.

The kinds are the design's — **guard**, **branch**, **stop**, **rationale** — plus **main path** for the steps themselves. "Duplicate" means the statement already lived in the named place, which now holds it alone. Each row quotes the conditions, qualifiers and remedies of what it classifies, in the source's words, and says so when its destination drops one and why.

The new files are `SKILL.md` (the targets, a Requirements block, a Guards section, steps 1 to 5, a stop table and a References index) and one reference under `skills/pipelex-explain/references/`, `not-on-disk.md`, read when the target is a catalog id or a published address, before the first call on it. The old step 8 is that reference, less the guards it carried, which stay in `SKILL.md` at the pointer or in the stop row their condition keys on. The old steps 5, 6 and 7 are one step, since all three describe the walkthrough's body. The workshop's posture is unchanged: its absence never stops the skill from explaining local source, both bullets of the shared requirements block stay scoped to a target that lives on the platform, and an absent `mthds_get_method` is a narrower explanation, not a stop. The skill stays outside `MCP_SKILLS`.

## Behaviour changes

Box G allows a phase to change behaviour only by resolving a contradiction found while consolidating, and by the deferrals the plan assigns to it. The plan assigns this skill no deferral. One contradiction was resolved.

1. **A verdict with no `main_pipe` no longer makes a local bundle's contract "not described".** The old stop row (line 164), unscoped, said "says the contract could not be described and which of the three causes the tool points to; never reconstructs one". Step 8, which is where that case was defined, scoped it to a target with no source: "A local bundle always has its source to fall back on … a published address has none" (line 140), and step 3 says the source reading "is not a guess" and is the skill's to state (line 63). Read literally on a local bundle, the row told the model to withhold a contract its own reading describes. The row now says "say so, and which cause the tool's message points to. Do not reconstruct a signature from the input template.", which holds on every target; `not-on-disk.md` keeps "that it carries no signature to describe the contract with" for the targets with no source, where the old step 8 put it. The prohibition, the one guard of the row, is unchanged.

Not behaviour changes, but worth a reviewer's eye:

- **The not-on-disk branch is read, not carried.** The old step 8 (lines 114–144, about 5,000 characters rendered) is needed only when the target is a catalog id or a published address, a condition the skill sees before its first call. It moved to `references/not-on-disk.md`, pointed at from step 1 "before the first call on it". Its guards did not move: the one that keeps the skill read-only — `mthds_get_method` with **no `output_dir`**, "not even to a temporary directory" — is stated at that pointer; the truncated read's "Never describe a withheld file's pipes as absent." and the no-`main_pipe` case's "Do not reconstruct a signature from the input template." are stated in the stop rows their conditions key on, and all three are registered. What stays in the reference is what the model needs only on that branch and what a result or a refusal announces: how an id is read and an address described, the three properties of a stored read, the two causes of an absent `mthds_get_method`, the three causes of a missing `main_pipe`, the routing of an invalid remote method, and the two meanings of a refused id.
- **The rows of the old stop table that repeated a step are gone.** "the reading and `pending_signatures` disagree" (line 160) was step 2's rule restated, and step 2 holds it alone. "a catalog id holds no stored source" (line 157) is merged into the refused-id row, and "the user wants the saved method's files on disk" (line 158) into the routing row.
- **The Mode section is one sentence of the opening**, "Reading costs nothing and changes nothing, so there is no confirmation to ask for."
- **The stop table is in the imperative**, "Condition | Do this", as in the skills the diet has already rewritten; the rows keep their remedies.
- **The size.** The Claude render is 11,087 characters (10,886 on Codex, 10,893 on Vibe), under the phase's target of about 12,000. The shared blocks explain carries render to about 2,500 characters — the frontmatter (818), the requirements include with its two scoping suffixes (834), the `validate-call` include (702) and the `PipeFunc` warning (about 200) — against about 4,900 in `pipelex-design`, which is why the margin here is wider than design's.

## For `docs/decisions.md`

A new section, **"`pipelex-explain`'s rationale, moved out of the skill (2026-09-23)"**, placed after "`pipelex-scaffold` drops the starters and runs its initializer branch through scripts", in the shape of the design, inputs and integrate sections:

> The size diet's sixth phase rewrote `pipelex-explain` in the read-before-act shape: the targets, the requirements with the workshop optional, the read-only guard, the five steps of an explanation and a stop table in `SKILL.md`, and a method that is not on disk — a catalog id or a published address — in `references/not-on-disk.md`, read before the first call on one. Most of the reasons the skill shipped were already recorded under "`pipelex-explain` reads a library, and pre-approves nothing that writes" and "A catalog id is a target in every skill", and the skill now ships none of them. What follows is the rest. The paragraph-by-paragraph account of the move is `wip/skill-size-diet/classification-explain.md`.
>
> - **The not-on-disk branch is a reference, and its guards stayed behind.** Reading an id or describing an address is needed only when the target is one, which the skill sees before its first call, so the old step 8 is a reference pointed at from step 1. Three of its sentences are guards and did not move. `mthds_get_method` with no `output_dir`, not even to a temporary directory, is stated at the pointer: it is the only thing that keeps a read-only skill from writing a pull, since the tool list pre-approves the tool and no argument matching exists. "Never describe a withheld file's pipes as absent." and "Do not reconstruct a signature from the input template." are stated in the stop rows their conditions key on — a `truncated` read and a verdict with no `main_pipe` — because each result announces its case while the misreport each forbids is silent. The rest of the branch is text the model needs only there, or that a result or a refusal announces: the two causes of an absent `mthds_get_method`, the three causes of a missing `main_pipe`, the routing of an invalid remote method, and the two meanings of a refused id.
> - **Routing an invalid remote method to the file-based skills is a branch, not a guard.** A catalog id sent to `/pipelex-edit` or `/pipelex-design` reaches their bridge, which finds the linked directory or hands the pull to `/pipelex-catalog`, and an address sent there is refused by the same bridge, so a misroute is announced by the skill it reaches. The rule stays in the reference, with its reason: a stored method is fixed where it is edited, and a published address in the repository it names.
> - **The explanation opens on complete or scaffold because an accurate description can misinform.** A user who asked what a method does, and got a confident walkthrough of a half-built one without being told it was half-built, has been misinformed by an accurate description; so the first thing said is whether the method is complete or a scaffold with a backlog.
> - **The walkthrough follows the library's layout** — the root file for the contract and the top-level flow, then one passage per module file — because that is the shape `/pipelex-organize` produces and the one a reader discovers progressively, so the explanation and the files read in the same order.
> - **The explanation stays in the conversation because that is where the user can read it, correct it and keep what they want of it.** Merge this with the "Strictly read-only" bullet of "`pipelex-explain` reads a library", which records why the skill writes nothing and why "document this pipeline" left its description.
> - **A verdict with no `main_pipe` no longer silences a local bundle's contract.** The stop table's row said the contract "could not be described", unscoped, while the step that defined the case scoped it to a target with no source and the offline step made the source reading the skill's to state. The row now says the verdict carries none and why, and never reconstructs a signature from the input template, which holds on every target; the reference keeps "no signature to describe the contract with" for the targets with no source.
