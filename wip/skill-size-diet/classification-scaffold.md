# Classification — `pipelex-scaffold`, phase 5a

Phase 5a of [`plan.md`](plan.md) under box A of [`design.md`](design.md): every paragraph of `templates/skills/pipelex-scaffold/SKILL.md.j2` as it stood at `cda0ea3`, its class and where it goes. Line numbers are that file's. This phase does three things of box E's amendment and leaves the method app's path for phase 5b, so a row the phase does not touch says so rather than being classified twice.

- **The starter path is deleted**, with `references/starters.md` and its tests: the Python starter, the gallery, the starter's acquisition, bootstrap and env-file step, the GitHub-template form, and the starter half of the fresh-clone shortcut. A deleted row is identified, not quoted.
- **Branch B's programs become scripts** under `skills/pipelex-scaffold/scripts/`: the repository test with the pristine commit (`commit-pristine.sh`) and the env-file write (`write-env-file.sh`). Each prints one verdict line the stop table keys on, and the unit suite executes it. A row moved to a script quotes the conditions and remedies the script now carries, and the script's comments state the defences.
- **Two branches move to references read on their condition**: the version-manager activation (`references/version-managers.md`) and the GitHub form (`references/github.md`). Branch B's per-framework detail is already in `references/initializers.md`.

## The behaviour changes

Each is named in the pull request, as box G requires.

- **The starters are no longer scaffolded from.** A Python CLI, script, worker or service, which went to `pipelex-starter-python`, goes to the language's initializer and then to `/pipelex-integrate`, like every project that is not a TypeScript web app. A user who names `pipelex-starter-js` or `pipelex-starter-python` is told the skill no longer scaffolds from them and is offered the method app or the initializer. This is box E's amendment.
- **The template-checkout stop names the method-app family alone.** The fresh-clone block's `origin` test matched the starters' repositories as well; with the starters gone, a starter's checkout is an ordinary directory to the skill.
- **Branch B's `.gitignore` check completes.** The skill told the model to confirm that a `.gitignore` covers the dependency tree and to write one where the initializer left none; an existing one that did not ignore `node_modules/` was left to the model's judgement. The script writes the three lines when there is none, as before, and adds `node_modules/` to an existing one that does not ignore a `node_modules/` directory present.
- **Branch B's `.env.example` keeps an initializer's own.** The skill said to write it; the script writes it when it is absent and adds the two Pipelex lines to one the initializer wrote only when it has neither.
- **Branch B's ignore rules are the project's own.** A `.env` or a `node_modules/` that only this machine ignored, through the user's global excludes file or the repository's `info/exclude`, used to count as ignored, so the project got no line and a teammate's clone would take it. Both scripts now count only a `.gitignore` the project carries. The smoke sessions found it on a machine whose global excludes ignore `.env`.
- **A Python project gets Python's `.gitignore` lines.** Where `uv init` writes none, inside an enclosing repository, the skill wrote Node's three lines and left `__pycache__/` to be committed. The script now writes Python's lines when `pyproject.toml` is at the root.
- **Branch B confirms a commit on the user's own repository.** The Mode section's exception named branch A's acquisition alone, so a directory holding only the user's `.git` took the initializer's commit on their branch with no question. The exception now names either branch, and branch B's step 3 asks before running the script.
- **The scripts close what the review rounds found.** A `.env` the initializer wrote is ignored before the pristine commit rather than after it. A `.env.example` that an initializer's `.env*` rule hid gets a `!.env.example` line. A `.env` whose key is written `export PIPELEX_API_KEY=…`, spaced or quoted, counts as carrying one, and the plane is read the same way. An inherited shell trace is switched off before any value is expanded, an exported `CDPATH` no longer moves `<dir>`, and a project with both a `pyproject.toml` and a `node_modules/` keeps the dependency tree out. Round 2 added a `refused: write-failed` on every write either script makes, a new `.env` created readable by its owner alone, the two Pipelex lines added to a `.env` the initializer wrote without them, and `not-a-repository` for a `<dir>` that is not its own repository's root. Round 3 added each missing Pipelex line on its own, so a file carrying one gains only the other, and closed an existing `.env` to other users before a key is written into it.
- **Branch B creates a Python project on a Python `pipelex-sdk` installs into, one the machine already has.** The starter's range was the only statement of it, and a project created on another Python fails at `/pipelex-integrate`'s first `uv add`. uv downloads a Python it lacks on first use, which is the toolchain install the skill forbids, so `uv python find` must print an interpreter inside the range before anything is created, and `uv init` is pinned to it. uv and `uv sync` are required only where `uv init` runs, never beside the poetry, pdm or hatch the user named.
