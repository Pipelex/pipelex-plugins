# Smoke sessions — `pipelex-scaffold`, phase 5a

The smoke sessions that close phase 5a of [`plan.md`](plan.md), under box H of [`design.md`](design.md): a fresh session walks the rewritten skill's initializer branch in each shape the phase names. The transcript must show each reference read on its branch before the action it governs and none read off it, `initializers.md` read before any initializer ran, both scripts run by path and never retyped, and no guard broken. They ran on 2026-09-23 against the worktree build at `8defee6` (`feature/Scaffold-no-starters-branch`); `make build` at that commit left the tree unchanged. The method-app branch is not exercised here: it stays as it stands until phase 5b, whose own smoke sessions walk it.

**Every guard held and both scripts carried the branch in every session that reached them, but one reference was read off its branch.** `initializers.md` was read before the initializer in every scenario, on both harnesses, and `github.md` in none, since no scenario asked for GitHub. Every session that reached the pristine commit ran `commit-pristine.sh` and `write-env-file.sh` by path, through `bash "<skill dir>/scripts/…"`, and none retyped a step of either. Each printed `committed:`, and each env verdict matches the file on disk. No key was printed or asked for, no env file was read back, no `gh` or `git push` was attempted, no session added an SDK dependency or a `methods/` directory on scaffold's account, and nothing was written into a directory that held anything but a lone `.git`. The exception is `version-managers.md`. In both runs of the lone-`.git` scenario, the model saw that `node` lives under `~/.nvm` and read the reference although `node` answered on the `PATH`, which is not the reference's condition. The likeliest trigger is a pointer the phase shortened, and the fix is a wording change in the template, reported below and not made here. The sessions also found that `write-env-file.sh` counts a global ignore rule as the project's, so a project can leave `.env` unignored for anyone who clones it (see "Found on the way").

## Found on the way

None of these was fixed in this phase. The first two concern text this phase wrote, so they belong on its branch; the others are older, or are for the eval suite.

- **The version-manager pointer lost its condition** (scenario 4). `templates/skills/pipelex-scaffold/SKILL.md.j2:239` at `8defee6` puts the hand-off exception on *"a machine where step 1 reached `node` through a version manager"*, and the closing index at line 273 describes the reference as *"`node` or `uv` reached through a version manager the machine already has"*. The pre-diet text said *"a `node` only reachable through `nvm` or `fnm`"*. On a machine whose `node` comes from `nvm`, which is common, the new wording matches a `node` that answered, and both runs of scenario 4 read the reference off its branch. Saying in both places that step 1 found `node` missing from the `PATH`, or restoring "only reachable", would restore the condition the reference itself opens with.
- **`write-env-file.sh` counts a global ignore rule as the project's** (scenarios 2 and 5). The script tests `git -C "$dir" check-ignore -q .env` (`skills/pipelex-scaffold/scripts/write-env-file.sh:50`), and `check-ignore` honours the user's global excludes file and `.git/info/exclude`, neither of which travels with the repository. On this machine `~/.gitignore_global:6` ignores `.env`, so the script added no `.env` line to the `.gitignore` that `uv init` wrote, and the project's own rules leave the key file unignored for anyone who clones it. `tests/unit/test_pipelex_scaffold_scripts.py` sets `GIT_CONFIG_GLOBAL` to `os.devnull` (line 49), so the unit suite cannot see it. One fix is to test the project's own rules alone, for example with `git -c core.excludesFile=/dev/null check-ignore`, beside a test that sets a global excludes file ignoring `.env`. `commit-pristine.sh:50` tests `node_modules` the same way, at a smaller cost. Scenario 2's model took the result for uv's doing and said so in its report; scenario 5's checked with `git check-ignore -v` and warned the user.
- **The script's default `.gitignore` is the TypeScript recipe's, whatever the language** (scenarios 1 and 6). Inside an enclosing repository, `uv init` initializes no repository and writes no `.gitignore`, so `commit-pristine.sh` writes `node_modules/`, `dist/` and `.env` into a Python project, and `__pycache__/` is left unignored (`.venv/` carries its own `.gitignore`). The pre-diet text prescribed the same three lines wherever the initializer left none, in its paragraph on the TypeScript recipes, so the gap is older than the script, which now applies it to every language. Scenario 1's model flagged it in its report.
- **Branch B commits on the user's branch without a stated confirmation** (scenario 4). The Mode section's confirmation for a commit that lands on the user's history is worded for branch A's acquisition (*"The acquisition into a directory that already held a repository is the exception"*), and the pre-diet text words it the same way. So in a directory holding only `.git`, branch B's pristine commit lands on the user's `main` unconfirmed, and `commit-pristine.sh`'s `add -A -- .` would sweep in any deletion their worktree showed. Here the worktree was clean and the commit held only the initializer's output. Whether branch B should confirm there too is a question for the skill's owner.
- **The shared closing sentence names the working directory as the project** (scenario 3, run 1). For scaffold, *"The project is the current working directory"* reads as the target, and the non-empty guard then stops the session with nothing written. That is the guard working. For the eval suite `L-260921-479a8e`, a scaffold scenario's prompt should say where the project goes.
- **`initializers.md` sends the model to another skill's reference.** It names `pipelex-integrate`'s `references/typescript.md`, "Known defect", and scenario 4's first run read that section, while `docs/build-targets.md:141` says a reference never sends the model to another.
