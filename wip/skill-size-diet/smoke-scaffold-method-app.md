# Smoke sessions — `pipelex-scaffold`, phase 5b

The smoke sessions that close phase 5b of [`plan.md`](plan.md), under box H of [`design.md`](design.md): a fresh session walks the rewritten method-app path, which is now the family's initializer and the template's `make serve`, from a local bundle and from a catalog id, and one Codex session walks the main path. Two more scenarios walk the rows the rewrite added: a shell with no key, and a copy of the template that `make create` has not run in, which enters the new `references/uncreated-copy.md`. The transcript must show each reference read on its branch and none on the main path, both commands run as the skill spells them, each verdict read from its line, and no guard broken. They ran on 2026-09-23 against a snapshot of the worktree at `a6eae4e` (`feature/Scaffold-method-app-via`), taken with `git archive` so that edits made on the branch while they ran could not reach them.

**Every guard held, and every reference was read on its branch and none on a main path.** On Claude Code, the local bundle and the catalog id each went from `npm create --yes @pipelex/method-app@latest '<dir>' -- --method '<method>' --quiet` to `created`, then from `make -C '<dir>' serve` to `serving http://127.0.0.1:<port>/ — "<title>"`, with no reference read, and each report led with the URL. The second server took port 4301 because the first held 4300, which is `make serve`'s own step. With no key, the initializer refused with `refused: no-key` and wrote nothing, and the report offered the two ways a key reaches `make create` without asking for it. In a copy left by `--no-create`, the model read `uncreated-copy.md` before running anything, ran the reference's `make create` block with the bundle as an absolute path, and then served. On Codex, the main path reached `serving` once the sandbox was lifted. Under Codex's `workspace-write` sandbox it could not: the template's own `make all` and `make serve` need `ps`, which that sandbox denies, and the skill handled the resulting `failed: create` as written, reporting no URL. No session printed or asked for a key, read an env file back, started the server any other way than `make serve`, or ran anything through the method. The sessions found one harness behaviour that the eval suite will meet (a headless session kills a command it backgrounded), and three wordings worth tightening, listed under "Found on the way".

## How the sessions were driven

**Claude Code 2.1.281**, model `claude-opus-5-5`, driven as [`smoke-scaffold.md`](smoke-scaffold.md) describes: headless with `claude -p` from each scratch project, `--plugin-dir <snapshot>/pipelex`, `--permission-mode bypassPermissions`, `--output-format stream-json --verbose`, and stdin closed. Session-only settings, passed with `--settings`, disable every plugin the user's settings enable, the workspace-internal ones included, and `pipelex@pipelex-plugins`. Every init message lists the `pipelex` plugin at the snapshot (`pipelex@inline`, 0.7.0) beside the two built-in plugins `agents-md` and `telemetry`, with its MCP server `plugin:pipelex:pipelex` connected. The same settings carry a `PreToolUse` hook that logs every MCP tool a session calls and refuses the run tools, and refuses any Bash command that runs `gh` or `git push`, logging it as an attempt. No session called an MCP tool or reached for GitHub.

**One harness rule was added after the first run.** In S1's first run the model started the initializer with `run_in_background`, since the skill says it takes several minutes, and then ended its turn to wait. A `claude -p` session ends with its turn, so the command was killed with it (see S1). The hook therefore also refuses a backgrounded Bash call, and `ScheduleWakeup` and `Monitor`, with the message that this headless session ends with its turn and the command should run in the foreground with a timeout of up to 600,000 ms. It fired once, in S4, and the model reran the same command in the foreground.

**Codex CLI 0.153.4**, model `gpt-6-astra` at medium reasoning effort, in an isolated `CODEX_HOME` holding only a copy of `auth.json`. The marketplace was added from the snapshot's root with `codex plugin marketplace add`, the plugin installed with `codex plugin add pipelex@pipelex-plugins`, and the cache copy checked identical to the snapshot's `pipelex-codex/` render with `diff -r`, for `skills/pipelex-scaffold/` and for the whole plugin. The user's own `~/.codex` was left untouched: its `config.toml` has the same hash, modification time and size after the runs as before them.

**The base projects** are scratch directories outside every repository, so no workspace `CLAUDE.md` or `AGENTS.md` loads. ## Found on the way

- **A headless session kills a command it backgrounded, and the skill's "several minutes" invites the background.** In S1's first run the model backgrounded the initializer and waited, and in S4 it tried to background the reference's `make create` block; both follow step 1's *"It never prompts, reads a bundle path from where it runs, and takes several minutes."* In an interactive Claude Code session that is harmless, since the task's completion re-invokes the model, but `claude -p` ends with the turn and kills the command, leaving a half-made project that holds a `.env.local`. For the eval suite `L-260921-479a8e`, a scaffold scenario needs the harness rule these sessions used. For the skill, step 1 could say to run the command in the foreground with a long timeout, since its verdict decides the next step, and the reference's block likewise.
- **Under Codex's `workspace-write` sandbox, the method app cannot be created or served.** The template's `make serve` reads process start times with `ps` to prove that a recorded process group is its own, and Codex's sandbox denies `ps`, so both `make all`, through `serve.test.mts`, and `make serve` fail. `make serve` reports it as `failed: exited — the dev server exited (at once) before it could be recorded.`, which names a symptom rather than the denied `ps`. npm also cannot write its cache under `~/.npm` in that sandbox. Both belong to `pipelex-method-apps` rather than to the skill: `make serve` could refuse with a verdict naming `ps`, as it does for `lsof` with `refused: no-lsof`, and its lifecycle tests could skip where `ps` is denied. The skill handled the failure as written, but its `failed: create` path assumes a cause the model can fix: `uncreated-copy.md` says *"A red `make all` is fixed, never handed off."*, and a cause that is the harness's own sandbox can only be handed off.
- **The `no-key` row says "offer", and an unattended model took the second arm itself.** In S3 the model ran `--no-create`, which writes the template and its commit into the user's directory and nothing else, and then offered the rest. If the row means that nothing is created until the user answers, it should say so: *"offer … and run neither until the user chooses"*. If creating the copy is acceptable, the row is fine as it stands.
- **A copy the initializer made is not recognised as one when the user merely stands in it.** `uncreated-copy.md` sends a copy the initializer made straight to `make create`, but a user standing in a copy does not say who made it, so in S4 the model ran the git reading for a hand-made copy, adapted and with probes of its own, and only then found the commit. The reference could say that a copy whose history already holds the commit `Start from Pipelex/pipelex-method-apps/webapp-js …` is one the initializer made, and goes straight to `make create`.
- **The model ran `make serve` after a red `make all` on Codex.** The reference says *"On `0`, go on to `make serve`"*, which implies not on a non-zero exit, and the model served anyway. It changed nothing, since `make serve` failed and stopped what it started, but the reference could say it outright: after a non-zero exit, `make serve` waits until `make create` has succeeded.
