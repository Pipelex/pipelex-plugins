# Classification — `pipelex-run`

Phase 6 of the size diet ([`plan.md`](plan.md), [`design.md`](design.md) box A). Every paragraph, bullet, list item and table row of `templates/skills/pipelex-run/SKILL.md.j2` as it stood at `2fd7120` (the phase 1 landing; the template did not move between that commit and this phase's base, `44e7fde`), with its kind under the read-before-act rule and where it went. Line numbers are that version's. Read the rewrite against this table as a move: a row whose destination is the new `SKILL.md` names the step it landed in, a row that moved names the reference, and a row that left the shipped text names `docs/decisions.md` or the statement it duplicated.

The kinds are the design's — **guard**, **branch**, **stop**, **rationale** — plus **main path** for the steps themselves. "Duplicate" means the statement already lived in the named place, which now holds it alone. Checkpoint 2's correction binds this table: each row quotes the conditions, qualifiers and remedies of what it classifies, in the source's words, and says so when its destination drops one and why.

The new files are `SKILL.md` (the Requirements, the steps of Start a run, Follow a run, a stop table and a References index, and no longer a Mode section) and references under `skills/pipelex-run/references/`: `published-address.md` (read at step 1 when the target is a `method_ref`, before the first call), `failed-run.md` (read at step 8 when the run failed, after giving `failure_message` and before routing) and `linked-run.md` (read from the stop table when `mthds_run` refuses a linked run with `input_domain` at `method_id`, before replying).

## Behaviour changes

Box G allows a phase to change behaviour only by resolving a contradiction found while consolidating, and by the deferrals the plan assigns to it. The plan's Deferred list assigns nothing to `pipelex-run`. This is the only change.

1. **A run stuck in `RUNNING` is named at step 6, where the run is followed.** Step 6 said to poll `mthds_run_status` until a terminal state (line 104), and the reading of a run that "stays `RUNNING` with no error and no progress" — "a workflow task that failed out of sight. It is not a slow run" — sat in step 8's failure table (line 122), which a run reaches only once it is terminal. A stuck run never is, so a model walking the steps in order polled forever and never met the row. Step 6 now carries the reading, in the same words; what the skill says about such a run is unchanged, and it is now said while the run is being followed rather than never.

Not behaviour changes, but worth a reviewer's eye:

- **The Mode section is gone.** "Automatic. The user asking for the run is the consent, and step 4 states what is about to happen rather than asking again" duplicated step 4, which keeps it. "The only questions this skill asks are the stops in the table at the end" was already inaccurate — step 1 asks for the id when `mthds_list_methods` is absent, which no row listed — and it becomes more so with a stop table that holds only what a tool reports; the questions the skill asks are unchanged, each at its step.
- **The stop table holds only what a tool reports**, and each other condition is stated once, at its step or in its reference. The old rows that restated the requirements, a step or a branch (lines 148–155 and 157) are deleted as duplicates, and what they restated keeps every remedy the row gave. The rows that remain are the linked-run refusal (now a pointer to `linked-run.md`) and the `mthds_download_artifacts` rows.
- **A published address is read from a reference, and so is a failed run.** Where an address is genuinely unlike an id — floating, its inputs directory, its manifest's main pipe, and a failing verdict that is not the user's to repair — is `published-address.md`, pointed at from step 1 before the first call, as `pipelex-inputs` does. The failure routing table, the `PipeFunc`-on-a-`files`-run reading and the address's failure rule are `failed-run.md`, pointed at from step 8. The guards those branches touch stay in `SKILL.md`: the question when an address and another target are both in hand, the provenance reported beside the run id, `failure_message` verbatim, no re-run with altered inputs.
- **The `PipeFunc` warning stays in `SKILL.md`, at step 8.** It is a shared include, a static reference cannot carry an include, and `TestSharedSkillIncludes` requires it in this skill; the files-run reading it leads to is the reference's.

## For `docs/decisions.md`

Merge as a new section, "`pipelex-run`'s rationale, moved out of the skill (2026-09-23)", after "`pipelex-design`'s rationale, moved out of the skill":

> The size diet's sixth phase rewrote `pipelex-run` in the read-before-act shape: the steps of Start a run with their guards, Follow a run, and a stop table holding only what a tool reports, in `SKILL.md`; a published address, a failed run and a refused linked run in references read on their condition. Most of the reasons the skill shipped were already recorded above, under "The run lifecycle is its own skill", "A published address without a tag is accepted, never refused" and "A catalog id is a target in every skill", and the skill now ships none of them. What follows is the rest. The paragraph-by-paragraph account of the move is `wip/skill-size-diet/classification-run.md`.
>
> - **The user's values are laid over the prepared set, never swapped for it.** Restating one input of a filled set is an ordinary thing to say, and it must not cost the whole set: taken alone, the request's values would drop every other key and fail the template check as drift.
> - **One template call checks every target for drift.** It answers which inputs the pipe declares and catches drift in the same call, and it is made for every target because every target can drift: a bundle edited after its `inputs.json` was written drifts exactly as a saved method does, since a run by id executes the method's current stored content and a run by an untagged address executes whatever its default branch holds at that moment. A renamed, added or dropped input changes the key set; a retyped or reshaped one does not, which is why the skill checks the JSON kind and a structured value's field names per key.
> - **Artifacts are downloaded at once, and the skill keeps half a sentence of why.** The links beside a run's `pipelex-storage://` references are presigned and expire within the hour, so a report that only relays them goes dead; the stored files themselves stay, which is why Follow a run can still download them days later. The skill says "their links expire within the hour" and no more, because without it a model would plausibly relay the links instead of downloading.
> - **Per-pipe bisection is not the run skill's** and belongs to a debug-run skill that does not exist yet; until it does, a failed run is reported and routed once, and never re-run with altered inputs, which would spend credit on a guess.
> - **A run stuck in `RUNNING` is named while it is followed.** The reading — a workflow task that failed out of sight, not a slow run — sat in the failure table, which a run reaches only once it is terminal; a stuck run never is, so the reading moved to the step that polls.
> - **The Mode section went.** It said the skill was automatic, which step 4 says where it applies, and that the only questions the skill asks are the stops in its table, which was never true: step 1 asks for a method's id when `mthds_list_methods` is absent.
> - **The stop table holds only what a tool reports.** Most of its rows restated the requirements, a step or a branch — an absent tool, inputs not run-ready, a stale prepared file, drift, a failed verdict, a failed run, an address's failure, two targets in hand, a `PipeFunc` failure on a `files` run — and each is now stated once, at its step or in its reference. What remains is the linked run refused at `method_id` and the two ways `mthds_download_artifacts` can fail a completed run.
> - **A published address and a failed run are references, and their guards stay in the skill.** Each is a condition the skill sees before it acts: the target is a `method_ref`, or the run failed. So the address's floating, its inputs directory, its manifest's main pipe and its not-ours-to-repair routing are read before the first call on an address, and the failure table, the `PipeFunc` reading on a `files` run and the address's failure rule before a failed run is routed. What skipping would make unrecoverable or silently wrong stays in `SKILL.md`: the question when an address and another target are both in hand, the provenance reported beside the run id, `failure_message` given verbatim, and no re-run with altered inputs. The `PipeFunc` warning stays at step 8 too, because it is a shared include and a static reference cannot carry one.
> - **A linked run refused at `method_id` is a reference read from the stop table.** The refusal spends nothing and names its location, which is the condition; the reading — why that location discriminates the unknown-method arm, the org-scoped catalog, the link file's `api_host` and the offer to run without the id — is a recovery longer than a line.

Also amend the existing section "`PipeFunc` is warned about, never refused (2026-09-21)": in its "Where it is given" paragraph, "`pipelex-run` says it under its failure table" becomes "`pipelex-run` says it at step 8, where a failed run is routed", since the failure table now lives in `references/failed-run.md` and the warning, a shared include, stays in `SKILL.md`.
