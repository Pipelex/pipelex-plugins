# Classification — `pipelex-catalog`

Phase 6 of the size diet ([`plan.md`](plan.md), [`design.md`](design.md) box A). Every paragraph, bullet, list item and table row of `templates/skills/pipelex-catalog/SKILL.md.j2` as it stood at `2fd7120` (the phase 1 landing; the template did not move between that commit and this phase's base, `44e7fde`), with its kind under the read-before-act rule and where it went. Line numbers are that version's. Read the rewrite against this table as a move: a row whose destination is the new `SKILL.md` names the section or step it landed in, a row that moved names the reference, and a row that left the shipped text names `docs/decisions.md` or the statement it duplicated.

The kinds are the design's — **guard**, **branch**, **stop**, **rationale** — plus **main path** for the steps themselves. "Duplicate" means the statement already lived in the named place, which now holds it alone. Each row quotes the conditions, qualifiers and remedies of what it classifies, in the source's words, and says so when its destination drops one and why.

The new files are `SKILL.md` (an opening paragraph, a Requirements block, a Guards section, List and find, Save as steps 1 to 5, Pull as steps 1 to 4, a stop table and a References index) and three references under `skills/pipelex-catalog/references/`, each static and opening with its entry condition: `python.md` (read at Save step 3 when the bundle holds a `PipeFunc`, before choosing any file), `conflict.md` (read when a save is refused with an `input_domain` error at `expected_updated_at`, before replying) and `unknown-id.md` (read when a save answers an `input_domain` error at `method_id`, before concluding anything about the link).

## Behaviour changes

Box G allows a phase to change behaviour only by resolving a contradiction found while consolidating, and by the deferrals the plan assigns to it. The plan's Deferred list assigns nothing to this skill. One contradiction was found and resolved.

1. **The comparison copy is the user's to remove.** The conflict path's first way forward told the model to "remove it once the comparison is done" (line 138), while the unknown-id path says "Removing a dead link is the one thing this skill ever takes off disk, and it is never done without asking" (line 149), and `docs/decisions.md` ("The catalog is one skill, and a save is a deployment") records "The one thing it ever removes is a dead link, and only after asking". The ratified record wins: `conflict.md` now says the copy "is the user's to remove once the comparison is done", and the skill still takes nothing off disk but a dead link, on a yes. The copy's other rule — it is for reading, never saved from — is unchanged.

Not behaviour changes, but worth a reviewer's eye:

- **Three rows of the old stop table became guards at their step.** "The pull's landing path falls outside the workshop's working directory", "the pull targets a method app" and "the catalog name yields no usable directory segment" (lines 163–165) are conditions the model observes before it acts, and no verdict, exit code or refusal announces them: skipping each one writes the files somewhere the rule did not choose, with nothing later to say so. By box A that is a guard, and a guard lives once, at the step it governs, so each is stated at Pull step 2 or 3 and registered, as `pipelex-design` states "On a method app, ask first" at its bundle-home step. The old table stated each twice, once in its row and once in the Pull section. "A `.py` file's ownership is unclear" (line 170) is the same case at Save step 3.
- **The pull's refusal table and the stop table are one table.** The old skill had a four-row refusal table inside Pull (lines 117–122) and two stop-table rows restating half of it (lines 167–168). The four refusals are the stop table's rows now, each once, and Pull step 4 names the table.
- **The update arm's rename caveat is the conflict reference's.** Line 59 warned that the link's `name` was taken at the last sync, so an update sends back a stale name over somebody else's rename. On the normal path that cannot happen: a rename is a save, it moves `updated_at`, and `expected_updated_at` refuses the save. The caveat bites only on a forced save with `expected_updated_at` omitted, which is `conflict.md`'s second way forward, where "**The name goes with it**" already said it (line 139). Step 2 keeps "keep the `name` it records unless the user is renaming"; the reason goes to `docs/decisions.md`.
- **The size.** The render lands at 11,822 characters on Claude (11,550 on Codex, 11,557 on Vibe), from 21,088. The shared blocks this skill must carry render to about 2,700 of them — the frontmatter with its description (1,001 on Claude), the requirements include, the `validate-call` include, the `PipeFunc` warning and the project-root markers — and the stop table, which absorbed the pull's refusals, is about 2,100.

## For `docs/decisions.md`

A new section, placed after "`pipelex-design`'s rationale, moved out of the skill" and before "`pipelex-scaffold` drops the starters…", titled **"`pipelex-catalog`'s rationale, moved out of the skill (2026-09-23)"**, ready to paste:

The size diet's sixth phase rewrote `pipelex-catalog` in the read-before-act shape: list and find, the save as five steps and the pull as four in `SKILL.md`, with a Guards section and one stop table; and its three branches in references read on their condition — which `.py` files a `PipeFunc` bundle sends, a save refused because the saved method moved, and an error at `method_id`. Most of the reasons the skill shipped were already recorded above, under "The catalog is one skill, and a save is a deployment" and "A catalog id is a target in every skill", and the skill now ships none of them. What follows is the rest. The paragraph-by-paragraph account of the move is `wip/skill-size-diet/classification-catalog.md`.

- **The root file goes first because nothing else orders the files.** The platform derives the method's listed description from the first file submitted, and the tool neither reorders the files nor guesses which one carries the `domain` header, so a save that led with a module file would list the method under that module's description, and nothing would report it. The skill keeps the half-sentence of reason beside the rule, because a model would otherwise plausibly submit the files in directory order.
- **The link's name is stale only where the precondition is bypassed.** The `name` in `pipelex-method.json` was copied at the last sync, and an update rewrites the catalog row's name from whatever the call sends. On the normal path that is harmless: a rename is a save, it moves `updated_at`, and `expected_updated_at` refuses the save. It bites only on the forced save that omits the precondition, so the warning lives in the conflict reference, which tells the model to read the current name from the catalog before that call.
- **`link_file` is relayed as the tool reports it.** It distinguishes three states — linked and refreshed, linked but stale, genuinely unlinked — that the skill cannot re-derive from disk, since a stale link and a fresh one look the same. Only the genuinely unlinked state risks a second method on the next save, and the workshop refuses a create into a directory another link claims rather than minting one silently.
- **A scaffold is saved.** A valid bundle whose signatures are still pending is saved, because the catalog holds drafts the same way the webapp does. The skill says plainly that such a method does not run yet, since a user told only "saved" would believe it does.
- **The pull measures `output_dir` from the workshop, and stops outside it.** The workshop resolves `output_dir` against its own working directory, which is where the harness launched it and not necessarily where the user is standing, and accepts any path inside that root. So a landing directory computed from the session's directory, or a project root outside the workshop replaced by some path inside it, writes the files somewhere the rule did not choose, and nothing downstream notices. The skill says so and stops instead.
- **A catalog name is free text, and never a path.** The name reaches the landing directory as one segment in the project language's casing, folded and filtered, so a `/`, a `\` or a `..` is spent by the rule. Spelled in verbatim, a name like `../../src` would climb out of `methods/` into the project's source tree, and the workshop, which bounds a write only to its own root, would accept it.
- **Two pull results are relayed verbatim.** A method saved before the webapp's editor existed carries no file names, so the tool names the file from the method's name and says so, and the next save sends that name back to the catalog, which is why the user hears it. A method whose stored source is empty is a different answer from an unknown id, and the two are never collapsed.
- **Three conditions the old stop table listed are guards at their step.** A landing directory outside the workshop's root, a method app, and a catalog name that yields no usable segment are seen before the pull runs, and no result announces them afterwards, so by the read-before-act test each is a guard stated once at the step it governs, as `pipelex-design` states "On a method app, ask first" at its bundle-home step. The stop table keeps the conditions a verdict, a refusal or an error announces, the pull's four refusals among them, which the old skill stated twice.
- **The branches read on demand are the ones a result or a visible condition announces.** Which `.py` files a `PipeFunc` bundle sends is decided only when the bundle holds one, which the model sees before choosing a file; a save refused at `expected_updated_at` and an error at `method_id` are announced by the tool. The guards each branch protects stay in `SKILL.md` at the pointer: stored Python is never swept or cleared unasked, the model never chooses between the conflict's two ways forward, and a dead link is removed only on the user's yes.
