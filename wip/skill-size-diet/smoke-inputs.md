# Smoke sessions — `pipelex-inputs`, phase 3

The smoke sessions that close phase 3 of [`plan.md`](plan.md), under box H of [`design.md`](design.md): a fresh session walks the rewritten skill's main path and each of its branches, and the transcript must show each branch reference read on its branch and none read on the main path. They ran on 2026-09-23 against the worktree build at `8647ee2` (`feature/Inputs-diet`), whose rendered `SKILL.md` is the one the plan's size bullet records; `make build` at that commit left the tree unchanged.

**Every scenario passed box H's test.** No session read a branch reference on the main path, every branch session read its reference before acting on the branch, no guard's protection was broken, no session called a run tool, and no template fix is needed for the diet. One expected outcome was missed, on Codex alone: no Codex session made the run offer that step 6 asks for. A control run of the pre-diet skill missed it the same way, so it predates the diet. It is recorded under "Found on the way" for the caller to file.

## How the sessions were driven

**Claude Code 2.1.280**, model `claude-opus-5-5`, driven as phase 2's record says ([`smoke-integrate.md`](smoke-integrate.md)): headless from each scratch project with `--plugin-dir <worktree>/pipelex`, session-only settings disabling the published `pipelex@pipelex-plugins` plugin and the workspace-internal plugins, `--permission-mode bypassPermissions`, `--output-format stream-json --verbose`, and stdin closed. Every init message lists one `pipelex` plugin, at `<worktree>/pipelex`, and its MCP server `plugin:pipelex:pipelex` as connected. Every session's own transcript under `~/.claude/projects/` carries `Base directory for this skill: /Users/lchoquel/repos/Pipelex/_pipelex-plugins--inputs-diet/pipelex/skills/pipelex-inputs`. The workshop was the plugin's own launcher, `npx -y @pipelex/mcp@latest` (0.17.0 on the day), with the key and base URL inherited from the shell, pointing at api-dev (`pipelex-hosted` 0.19.0 by `/v1/version`).

**One addition to phase 2's settings: a run is refused before it reaches the server.** A run spends credit, and these scenarios end at the run offer, so the session-only settings add a `PreToolUse` hook on `mcp__.*` that denies any tool whose name ends in `__mthds_run` and logs the attempt. The tool stays in the session's tool list, so a model that reaches for it anyway shows in the transcript and fails its scenario. No session reached for it: the log stayed empty and no transcript holds a `mthds_run` call.

**Codex CLI 0.153.4**, model `gpt-6-astra` at medium reasoning effort, in an isolated `CODEX_HOME` as phase 2 did it: only `auth.json` copied in, the marketplace added from the worktree root, the plugin installed with `codex plugin add pipelex@pipelex-plugins`, and the cache copies of `skills/pipelex-inputs/` and `skills/pipelex-synthetic-inputs/` checked identical to the `pipelex-codex/` render with `diff -r`. Each run was `codex exec -m gpt-6-astra --json -s workspace-write -C <project> "<prompt>"`, and every rollout carries the skill as `<skill><name>pipelex:pipelex-inputs</name><path>…/codex-home/plugins/cache/pipelex-plugins/pipelex/0.7.0/skills/pipelex-inputs/SKILL.md</path>`. The approval entry phase 2 needed for `mthds_codegen` is needed here for `mthds_prepare_inputs`, which the workshop also annotates as not read-only:

```toml
[plugins."pipelex@pipelex-plugins".mcp_servers.pipelex.tools.mthds_prepare_inputs]
approval_mode = "approve"
```

`mthds_run` was deliberately left out of it, so under `codex exec`'s approval policy `never` a run call would have been refused. The user's own `~/.codex` was left untouched: its `config.toml` hash and timestamps, and its `pipelex-plugins` plugin cache, are the same after the runs as before them.

**What counts as a read**, as in phase 2: a `Read` naming `references/<name>.md`, or a shell command printing it. A read of another skill's reference, such as `pipelex-synthetic-inputs`' own `references/pdf.md` in scenario 3, belongs to that skill and is not a branch of this one. The projects are scratch git repositories outside every repository, each with a committed baseline, so no workspace `CLAUDE.md` or `AGENTS.md` loads and the diff after a session is exactly what the session did. The transcripts and projects were kept in the orchestrating session's scratch directory (`/private/tmp/claude-501/…/scratchpad/smoke-inputs/`), which is temporary; the session ids below are the durable handles.

**The base project.** A git repository holding a `.gitignore` (`.DS_Store` only), a README, a local bundle at `methods/summarize-pdf/main.mthds`, and a one-page PDF the user already has, `docs/q3-report.pdf` (979 bytes, a short operations report written without any PDF library). The bundle was written for the smoke: `main_pipe = "summarize_pdf"`, a `PipeSequence` taking `document: Document` through a `PipeExtract` to `Page[]` and a `PipeLLM` to `Text`. It validates through the workshop (`is_valid: true`, `is_runnable: true`, main pipe `pdf_summary.summarize_pdf`, one required `native.Document` input, a `native.Text` output). No project carries a `package.json` or a `pyproject.toml`, so step 6's `/pipelex-integrate` line has nothing to fire on.

**The published address** is `github.com/Pipelex/methods/documents@v0.1.0`, the example address of this skill's `published-address.md`, of `pipelex-run` and of the workshop's tool descriptions and tests. It validates through the workshop by `method_ref` (`is_valid: true`, `is_runnable: true`, main pipe `documents.extract_document_markdown`, one required `native.Document` input, a `native.Text` output) and ships no Python, so the deployment's refusal of in-process Python does not apply to it.

**The prompts** each end with the same sentences: `The project is the current working directory. This is an unattended session: nobody can answer questions, so work automatically and take the defaults. Do not start a run of the method.`

**Checking `inputs.json` against preparation.** `inputs.json` does not exist before a session, so "untouched by preparation" is read from the transcript: the last write to `inputs.json` precedes the prepare call, nothing writes it afterwards, and the file on disk after the session has the SHA-256 of what that write put there. The copied PDF is compared with the user's original the same way.

**The scenario shape** is phase 2's: setup, prompt, expected references and expected outcome, followed by the runs.

## Scenario 1 — the template strategy

- **Setup.** The base project.
- **Prompt**, by the slash command: `/pipelex:pipelex-inputs I need an inputs template for the method in methods/summarize-pdf/: just the placeholders, so I can fill it in myself later.` followed by the shared sentences.
- **Expected references.** None: the Template strategy is the main path.
- **Expected outcome.** `mthds_inputs_template` with the bundle as `files` and `explicit: false`; the file-ish mock URL replaced by the placeholder that says the path is relative to `inputs.json`; `inputs.json` saved in `methods/summarize-pdf/`; no prepare call; no run offer, since a placeholder remains; an offer of synthetic data or the user's files.

**Run** — Claude Code 2.1.280, session `321dbaf4-9917-4b45-8d1a-89b3326ace8e`. **References read:** none. **Outcome:** `mthds_inputs_template` with `files: [{path: <absolute path to main.mthds>}]` and `explicit: false`, which returned `{"document": "https://mock.invalid/url"}`; `methods/summarize-pdf/inputs.json` saved as `{"document": "<document-url-or-path-relative-to-this-inputs-file>"}`; no prepare call and no run offer. The report explains the path rule (*"Relative paths are read from where `inputs.json` is, not from the project root. An absolute path also works."*), says preparation was skipped *"because a placeholder isn't a real file"*, and ends *"I can also fill it with a generated sample PDF or with a file of yours."* **Verdict: pass.**

## Scenario 2 — a user's PDF, prepared and offered

- **Setup.** The base project.
- **Prompt**, by the slash command: `/pipelex:pipelex-inputs Prepare inputs for the method in methods/summarize-pdf/ using my file docs/q3-report.pdf, so the method is ready to run on it.` followed by the shared sentences.
- **Expected references.** `user-data.md`, read at step 3 before any file is matched to an input. No other branch reference.
- **Expected outcome.** The PDF copied unchanged into `methods/summarize-pdf/inputs/`; `inputs.json` naming it relative to itself; the upload announced before the call; `mthds_prepare_inputs` with the bundle and the path sent absolute; `inputs.prepared.json` written with the `{"url": "pipelex-storage://…"}` form; `inputs.json` never rewritten; `inputs.prepared.json` added to `.gitignore`; the run offered, naming `inputs.prepared.json` and the bundle, and not taken.

**Run** — Claude Code 2.1.280, session `03b273cd-cd73-404a-96af-dd05daa402a9`. **References read:** `user-data.md`, the third tool call, before the template call and before any file was matched. **Outcome:** in one shell call the model copied the PDF to `inputs/document.pdf`, named after the input as the reference's copy step says, wrote `inputs.json` as `{"document": "inputs/document.pdf"}`, and checked the copy with `cmp`. It announced the upload before the call: *"I'll upload `methods/summarize-pdf/inputs/document.pdf` (a copy of `docs/q3-report.pdf`, 979 bytes) to Pipelex storage using your API key, proceeding since this session is unattended."* It called `mthds_prepare_inputs` with the bundle and the absolute path, wrote `inputs.prepared.json` with the returned `{"url": "pipelex-storage://…"}`, found no ignore rule covering it, and added it to the root `.gitignore`. `inputs.json` on disk matches what was written before the prepare call, and the copy matches the user's original byte for byte. The report ends with the offer: *"Next step: use `/pipelex-run` to run the bundle in `methods/summarize-pdf/` with `inputs.prepared.json`. A run spends inference credit, so it only starts when you ask."* **Verdict: pass.**

The closing message says what is ready and ends *"No method run was started."*, with **no run offer** and no mention of `/pipelex-run`. **Verdict: pass on box H's test, with the run offer missing.**

**Run 2** — the same prompt on a fresh copy, thread `01a0cce4-578c-7122-a820-83d6fa21d9dd`, to see whether the missing offer was incidental. **References read:** `user-data.md`. **Outcome:** as run 1, with the offer missing again.

**Control** — the same prompt against the pre-diet skill, thread `01a0cce5-ac93-75b3-a607-0ed9a4a31de3`. The `pipelex-codex/` render at `e243373` (the classification commit, whose template is still the old one) was extracted with `git archive` into a second isolated `CODEX_HOME` and installed the same way. **Runs 3 and 4** — two variants of the prompt, to find what suppresses the offer, each keeping an instruction to stop short of a run. Run 3 (thread `01a0cce6-eba9-7723-9d21-631bfa850b0b`) drops the unattended sentence and keeps `Do not start a run of the method.` Run 4 (thread `01a0cce7-fef5-7b52-959a-de800e310f07`) keeps the unattended sentence and replaces the prohibition with `Prepare the inputs and stop there.` **References read:** `user-data.md` in both. **Outcome:** the main path as in run 1, and no offer in either.

Every Codex rollout carries step 6's **"Offer the run, never start it"**, so the model had the instruction and did not follow its first half. The second half, the one that protects credit, held in every run. The case left untested is a prompt that says nothing about stopping, which the smoke rules forbid because a run spends credit.

## Found on the way

None of these is a defect of the diet, and none was fixed in this phase. The first is for the caller to file.

- **On Codex, the run offer is not made when the user has asked to stop short of a run.** Claude made the offer in every scenario that reached step 6 with run-ready inputs, under the same prompt. Codex (`gpt-6-astra`, medium effort) never did, after the diet or before it, whether the prompt said "Do not start a run" or "stop there", and with or without the unattended sentence. Whether the offer appears when the prompt does not mention stopping is untested. If the offer should stand even after a user has said to stop, step 6 needs a sentence saying so; that is a behaviour change, so by box G it lands after the phase.
- **Sessions pass the template's resolved `pipe_ref` to prepare when step 2 passed none** (scenarios 2 and 3, and every post-diet Codex run; scenario 4, by address, and the pre-diet control passed none). Step 5 says "step 2's `pipe_ref` if it passed one". The resolved ref names the main pipe, which prepare would have defaulted to, so the contract inspected is the same and nothing changes. It is recorded in case the eval suite grades the call's arguments.
- **The mock URL the template tool returns has changed shape.** Step 3's Template bullet quotes `https://mock-xxxxxxxx.invalid/...`, as the pre-diet text did, but workshop 0.17.0 against api-dev returns `https://mock.invalid/url`, in the light shape and in the explicit one. Scenario 1's session recognised it anyway. The bullet could name the tool's `.invalid` mock URL rather than a shape it no longer has; it predates the diet, so by box G it lands after the phase.
- **The pre-call announcement reaches the stream in two forms.** In scenarios 2 and 3 the model's narration between tool calls, the announcement included, is recorded as a `thinking` block carrying plain text; in scenario 4 it is a `text` block. A grader in the eval suite `L-260921-479a8e` that checks the announcement must read both.
- **The workshop refuses a `{path}` outside the directory it was launched in.** Validating the smoke bundle from the orchestrating session, whose workshop was launched in the plugins checkout, answered at `files[0].path` with *"Path resolves outside the server's working directory"* and a hint to inline the contents. The shared submission convention says to pass an absolute path because the workshop resolves against its own working directory, but not that the path must also lie inside that directory. No smoke session met it, since each launched its workshop in the project. It belongs to the `validate-call` include that every MCP-backed skill shares, not to this phase.
- **An unattended Codex run must pre-approve `mthds_prepare_inputs`**, as phase 2 found for `mthds_codegen`. The eval suite needs both entries and must leave `mthds_run` out.
- **Not exercised by any scenario:** `prepare-errors.md`, since no preparation failed; `published-address.md`'s second entry, from the stop table, since preparing by address succeeded on workshop 0.17.0; the Mixed strategy; interactive mode. The plan's scenario list does not include them; the link check and `tests/unit/test_pipelex_inputs_skill.py` hold their pointers.
