## Found on the way

None of these is a defect of the diet, and none was fixed in this phase. The first two are for the caller to file; a search of the ledger found no item naming either.

- **The stepwise mode cannot validate a construction with more files than the hosted API accepts in one call.** `stepwise.md` adds one `<code>.mthds` file per refinement and keeps the construction files until organization, and every validation submits the whole bundle. The hosted API caps `mthds_contents` at `MAX_MTHDS_FILES_PER_REQUEST`, whose default is 16 (`pipelex-api/api/limits.py:13`, applied at `pipelex-api/api/schemas/models.py:528`), so a graph with more pipes than that gets *"Validation was not run: the Pipelex API rejected the request"* partway through (scenario 2, run 1). The model improvised a mid-construction regrouping and disclosed it, but nothing in the skill tells it what to do. The one-file rule reads the same in the pre-diet text (`git show ecf6e90:pipelex/skills/pipelex-design/SKILL.md`, the loop's step 2 and "One concrete definition per refinement file"), so it predates the diet. A fix, whether `stepwise.md` saying how to fold satisfied definitions before the cap or the cap reconsidered in `pipelex-api`, is a behaviour change that by box G lands after the phase.
- **A validation's dry run follows one outcome of a `PipeCondition`.** In scenario 2, run 2, a branch sequence whose last `result` name did not match what its parent expected made the dry run fail on one branch. After the fix there, the bundle validated as valid although the sibling branch carried the same defect, and an inline variant forcing the other outcome failed until that line was fixed too. So a bundle can pass `mthds_validate` with a branch that would fail when it runs, and the model found it only because it tested the other outcome on its own initiative. It belongs to the validation in `pipelex`, not to the plugins.
- **zsh aborts a chained read at an `=` separator.** Models separate files in one shell call with `echo =====`, and zsh's `=` expansion turns that into `===== not found` and drops the rest of the line, so a reference `cat` placed after it never prints. It happened in scenarios 2, 3 and 4 on Claude, and each time the model saw the file missing and read it again, with `Read` or a second `cat`, before acting. It matters to the eval suite `L-260921-479a8e`: a grader must count a read by what the tool result printed, not by the command text.
- **The workshop's path containment, met again.** In both stepwise runs, a candidate layout staged under `/tmp`, by the model in run 1 and by `pipelex-organize` in run 2, was refused and then staged inside the project and removed afterwards. That is `L-260923-019e50`.
- **`pipelex-catalog` probes the catalog with an id fragment before the pull.** In scenario 4, runs 1 and 2, it called `mthds_list_methods` with `query: "fd6c9163"`, which returned nothing because the query matches names and descriptions, then listed again by name or in full before the get. It costs one call and changes nothing; it is recorded in case the eval suite grades that skill's calls.
- **Dropping the formatting-hook sentence did not show.** The phase dropped design's formatting-hook include as a stop.
