# When the saved method moved since this directory synced

Read this when `mthds_save_method` answers an `input_domain` error at `expected_updated_at`, before replying to the user. The error carries both timestamps, the stored method's `updated_at` and the link's `synced_updated_at` the call passed, and nothing was written — not the method, not the link.

**First, is it this session's own save?** When the stored `updated_at` the refusal names equals the `updated_at` this session's last save of this method reported, and that save was inline or its `link_file` came back `written: false`, nobody else saved: the link never recorded that save and still carries the sync time before it. Say so, and never say that somebody saved over the method. The save the user asked for then goes ahead: the same call, with `expected_updated_at` set to that stored `updated_at`, which still refuses a save anybody else landed since. Say too that the link stays behind until the workshop can write in this directory, where a path-form save, or a pull of this method while the files still match it, then refreshes it: a workshop that refused the path needs the harness relaunched from a directory holding the bundle, and a write that failed for another reason needs that reason fixed. Until then every save from this directory meets this refusal, and a later session, which cannot tell the save was its own, reads it as the conflict below.

Otherwise somebody saved over this method after this directory last synced with it, or nothing here can tell that apart from it. Give the user both timestamps and the two ways forward below; the skill's guard holds, and choosing between them is the user's alone.

1. **Compare first.** Pull the saved version into a **new** sibling directory — one that does not exist yet, since the pull refuses a directory that already holds a bundle. That copy gets its own `pipelex-method.json` and is therefore linked to the same method, so it is for reading: do not save from it, and it is the user's to remove once the comparison is done.
2. **Save over it**, on an explicit yes and nothing less: the same call with `expected_updated_at` omitted. Say what that costs — whatever the other writer saved is replaced, and the catalog keeps no earlier version to give back. **The name goes with it**: an update rewrites the catalog row's `name` from this call, and the refusal carries timestamps only, so if the other writer also renamed the method, sending the link's copy reverts their rename. Read the current name with `mthds_list_methods` before this call and carry that one, unless the user is deliberately renaming.

When the user is choosing the second way, say in one line that the check is best-effort: the tool reads the stored method and then writes, and the platform accepts no compare-and-swap, so a save landing inside that window is still overwritten.
