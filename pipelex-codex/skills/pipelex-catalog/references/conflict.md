# When a save is refused at `expected_updated_at`, or a version is restored

Read this when `mthds_save_method` answers an `input_domain` error at `expected_updated_at`, or before saving a directory that holds a pulled version because the user asked to restore it, before replying to the user. A refusal names the draft's current `updated_at` and the token the save was sent under, and nothing was written — not the draft, not the link. Only the draft is at stake: published versions never change, and nothing below publishes.

**First, is it this session's own save?** When the draft's `updated_at` the refusal names equals the `updated_at` this session's last save of this method reported, and that save was inline or its `link_file` came back `written: false`, nobody else saved: the link never recorded that save and still carries the sync time before it. Say so, and never say that somebody saved over the method. The save the user asked for then goes ahead: the same call, with `expected_updated_at` set to that stored `updated_at`, which still refuses a save anybody else landed since. Say too that the link stays behind until the workshop can write in this directory, where a path-form save, or a pull of this method while the files still match it, then refreshes it: a workshop that refused the path needs the harness relaunched from a directory holding the bundle, and a write that failed for another reason needs that reason fixed. Until then every save from this directory meets this refusal, and a later session, which cannot tell the save was its own, reads it as the conflict below.

**Then, does the directory hold a pulled version?** When `pipelex-method.json` records a `synced_version`, or the refusal says the directory holds one, the files here are version n, pulled to read or to start over from, and saving them replaces the draft with that version: a restore. Unless the user asked for it, say so and give the two ways forward: pull the draft back into this directory, which writes over the version's files freely since the catalog stores them, to go on working on the draft; or restore. A restore, made only on the user's request or an explicit yes, is the same call with `expected_updated_at` set to the draft's `updated_at` the refusal names, and `python` as the version's `.py` files, or `[]` when it has none, since an omitted `python` keeps the draft's. It publishes nothing; a publish of the restored draft is a request of its own.

Otherwise somebody saved over the draft after this directory last synced with it — a teammate, or the webapp's autosave of an editor left open — or nothing here can tell that apart from it. Give the user both timestamps and the two ways forward below; choosing between them is the user's alone.

1. **Compare first.** Pull the draft into a **new** sibling directory — one that does not exist yet, since the pull refuses a directory that already holds a bundle. That copy gets its own `pipelex-method.json` and is therefore linked to the same method, so it is for reading: do not save from it, and it is the user's to remove once the comparison is done.
2. **Save over it**, on an explicit yes and nothing less: the same call with `expected_updated_at` set to the draft's current `updated_at`, which the refusal names. Say what that costs: whatever the other writer saved in the draft is replaced, while every published version stays as it was. The platform compares the token as it writes, so a save somebody lands after the refusal refuses this one too.
